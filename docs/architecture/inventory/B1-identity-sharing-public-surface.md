- Public ID/URL compatibility: cookie names visible to web only via browser; `GET /auth/session` → `{signedIn, method, passkey, credential, account, name, providers, claimed, canClaim, registration}` (`index.ts:280-298`, `accounts.ts:256-259`).
- Explicit settings: none.

## GUEST / VISITOR IDENTITY TRACE — how identity crosses between spaces (`pimOf(ownerId)` and the Worker's hand-offs)
---------------------------------------------------------------------------

Method: every `pimOf(`/`getAgentByName(env.Pim, …)` caller in `src/` was listed (`rg "pimOf|getAgentByName\(env\.Pim"`), each RPC method it reaches was read, and `rg "@callable|routeAgentRequest|routePartykitRequest" src` was run. Result [V]: **no `Pim` method is decorated `@callable`** and `routeAgentRequest` is not used, so none of these RPC methods is reachable from HTTP or a WebSocket; the only external entry to the Worker is `serve()` (`src/index.ts:16-18`). The RPCs below are reachable only by code in this repository holding the `env.Pim` binding. A Durable Object RPC carries **no caller identity**: the callee sees only its arguments.

**Stage A — the Worker authenticates and tells a space who it is.** `toAgent` sets `x-pim-owner: <account.ownerId>` and, only for browser-session requests, `x-pim-signed-in: 1`, deleting any client-sent copy (`gateway.ts:187-200` [V]). The space checks the owner header equals its own DO name (421), then closed (410), then suspended (403) (`pim.ts:1941-1946` [V]). Trusted: the header (nothing but the Worker sets it). Not checked: anything about the caller beyond that — "inside, no per-route role logic" (see notes under the matrix).

**Stage B — visitor → host (a circle member using the host's space).** All five calls come from the *visitor's* space with `me = this.me()`, i.e. `{ownerId: <the caller DO's own name>, username: <its PROFILE_KEY username>}` (`sharing.ts:104-108` [V]; `PROFILE_KEY` is written only by `provision`, which refuses a profile whose `ownerId` ≠ the DO's name, `pim.ts:1969-1975` [V]). The target is `pimOf(share.ownerId)` where `share` is the visitor's own `pim_shares` row.

**Stage E — bot guest → bot author.** The guest's space (`installBotTools`, `sharing.ts:911-925`) calls `pimOf(guestBot().owner).runBotTool(guest.bot, this.host.name, name, args, call)` where `call = {session, callId, username}` and `username = this.me()?.username` (`sharing.ts:921`, `bot-tools.ts:19-20`). The tool-call cap is counted first, in the guest's own space (`usage.reserveToolCall()`, `sharing.ts:917-920`; `usage.ts:362-371` [V]).

**Stage F — in-space code → Worker functions that re-verify.** `adminAsMajordomo(env, space, agentId, request)` (`extensions/meta-admin.ts:95`) is not trusted: it re-reads the Directory (`status==="active" ∧ role==="admin"`) and compares `agentId` with `Pim.majordomoId()` (`accounts.ts:728-736` [V]). `assertHostOpsCaller` does the same for host operations (`hostops.ts:120-128` [V]); only `kind:"agent"` callers pass, and the agent id comes from in-space state (`extensions/hostops.ts:138`). This is sound today because the argument is always built from the calling DO's own name (`sharing.ts:104-108`, `:921`, `approvals.ts:218-220`, `sharing.ts:131,146`) and no external input reaches those arguments [V by listing the call sites above].

## GAPS / AMBIGUITIES — resolved as far as the code permits
---------------------------------------------------------------------------

Classification: **EXPLICIT** = an exact rule exists (path:line). **ABSENT ENFORCEMENT** = I searched the stated routes/tools and none checks it, so *current behavior = no check*. **UNCERTAIN** = what the code cannot show. Each gap ends with **PRESERVE AS-IS** (what a compatible migration must keep doing) separately from **PROPOSED HARDENING** (a change, not compatibility).

1. **Inter-space RPC identity is vouched, not verified.** ABSENT ENFORCEMENT for caller authentication (searched all 15 RPC methods in the trace above, `pim.ts:1582-1624,1861-1872,2156,2361-2386`; `rg "@callable|routeAgentRequest" src`: none); EXPLICIT for the semantic checks (`sharing.ts:154-165` etc.). *Consequence now:* none exploitable from outside; but any space-side code could run a bot's non-`ask` tool for any string `guest` (`runBotTool` verifies `bot.ownerId===this.name` and that the tool is shared, nothing about `guest`, `sharing.ts:776-783`), read any guest's bot images given `botId`+`guest` (`:894-904`), write a `pim_shares` row into any space via `shareReceived` (`visits.ts:112-121`), and record any `username` in activity/approvals (`sharing.ts:358,367`). **PRESERVE AS-IS:** every check listed in Stages B–E, including re-check on each call and idempotent `g-`/`b-` approval ids. **PROPOSED HARDENING:** when spaces stop sharing one trust domain, give each inter-process call an authenticated caller identity (signed claim or mTLS) that the callee compares with `guest.ownerId`/`owner`; have `runBotTool` verify `accounts.bot === botId` for `guest`; derive `username` from the host's own `pim_circle_members` row instead of the argument.
2. **Bot per-guest daily tool-call cap is enforced only in the guest's space.** ABSENT ENFORCEMENT at the author: searched `runBotTool`, `#runBotTool`, `#askForBotGuest`, `botImage` (`sharing.ts:776-904`) — no counter. EXPLICIT in the guest's space: `reserveToolCall()` before each stand-in call (`sharing.ts:917-920`, `usage.ts:362-371`), limit written into the guest's `LIMITS_KEY` from the bot at sync (`sharing.ts:596-603`, `bot-tools.ts:40-45` comment). Circle visitors, by contrast, are counted in the host (`circles.ts:199`, `sharing.ts:299`). *Consequence:* the author's space will run unlimited calls for anyone who reaches `runBotTool` (see gap 1); within the product the cap is as strong as the guest space's own meter. **PRESERVE:** counting in the guest's meter, per-bot `dailyToolCalls` semantics (null = deployment limit, 0 once the link is off). **PROPOSED HARDENING:** an author-side counter keyed `(botId, guest, UTC day)`.
3. **API tokens are all-powerful and unscoped.** EXPLICIT as design: `docs/reference.md:825` "an API token opens your whole API"; `auth_tokens(id,name,hash,created_at,last_used_at)` has no scope or expiry (`auth/store.ts:68-74`); `MAX_TOKENS=20` (`auth/index.ts:595`). The **complete** list of session-only operations is: `/auth/*` management and consent (`auth/index.ts:463-465`, `gateway.ts:567-575`), `DELETE /account` (`accounts.ts:459`), `/admin/*` (`accounts.ts:801`), `/hostops` admin reads and credential (`hostops.ts:750`), desktop and displays sockets (`gateway.ts:650-654`), `POST /artifacts/:id/backend/run` (`routes.ts:1103`), approving an `ADD_CUSTOM_CONNECTOR` approval (`routes.ts:1687-1689`), `POST /app-actions/*` (`routes.ts:2134`), `POST /mcp/callback/apps` (`routes.ts:2122`, `gateway.ts:297-303`) — found with `rg "viaSession|SIGNED_IN_HEADER"` over `src/` and `packages/`. For everything else (approve incl. `always`, `PUT /permissions`, circles, publish, coding vault keys and threads, share bot if admin, delete agents, `/hostops/ops`) the absence of a check is verified: no route, extension or the Worker tests `viaSession`. **PRESERVE:** token grammar `pim_<owner>_<43 b64url>`, SHA-256 hex storage, unscoped behavior and the exact session-only list above. **PROPOSED HARDENING:** scopes/expiry; make always-approve, permissions and vault keys session-only (a breaking change for API clients). → *User choice U1.*
4. **Admin role + API token.** EXPLICIT split: `/admin/*` needs `viaSession` or the majordomo path (`accounts.ts:801`, `adminAsMajordomo` `:728-736`); share-bot needs only `role==="admin"` (`accounts.ts:657`); Gitea `admin()` needs only role (`git-broker/gitea-api.ts:30-32`, used `:44,52,71`). ABSENT ENFORCEMENT of `viaSession` there (searched `accounts.ts`, `coding/**`: only `:459,:801` and `hostops.ts:750` test it). *Consequence:* an admin's API token can share/unshare bots and connect/disconnect Gitea; it cannot call `/admin/*`. Intent is not recorded anywhere (UNCERTAIN as intent; certain as behavior). **PRESERVE** current behavior. **PROPOSED HARDENING:** require a session for admin mutators. → *User choice U2.*
5. **Suspended authors' published content.** EXPLICIT design: the Gallery is kept apart from the Directory "so browsing never touches accounts" (`gallery.ts:26-28`). ABSENT ENFORCEMENT for templates, published apps and public `/p/<id>`: searched `accounts.ts:523-632` (all gallery routes), `servePublicArtifact` (`accounts.ts:89-98`), `Gallery.publicArtifact` (`gallery.ts:985-991`), `WITH_AUTHOR` (`gallery.ts:393`): none reads account status. EXPLICIT gating exists for bots (`sharedBot`: author active ∧ admin, `accounts.ts:112-122`) and `/people/:username` (`someone()`, `accounts.ts:505-509`). *Consequence:* a suspended author's templates stay listed and adoptable, published apps stay listed/usable, public links keep rendering (their files stay in the author's R2 prefix); deletion removes them (`Gallery.forgetOwner`, `gallery.ts:1139`). **PRESERVE** as is. **PROPOSED HARDENING:** push status to the Gallery on suspend and filter at read. → *User choice U3.*
6. **Admin continuity.** EXPLICIT: one admin exists when `role='admin' ∧ status IN ('active','suspended')` or a live pending claim (`directory.ts:295-300`); role is set only at registration (`:455`) and never updated (no `UPDATE … role`); `DELETE /account` has no role check (`accounts.ts:457-464`) so the admin may delete themselves, after which `admin()` is null and registration yields an admin for whoever holds a claim (`directory.ts:455-461`): the code printed to the logs by anonymous `POST /auth/setup-link` (`accounts.ts:319-324`, `directory.ts:304-312`) or, **on Cloudflare, anyone at all within 15 min of any deploy** (`runtime.ts:171-176`, `CLAIM_WINDOW_MS` `:32`). `/admin` refuses suspend of self (`accounts.ts:993`) and delete of self (`:1028`, "Delete your own account from Settings."). ABSENT ENFORCEMENT: no role transfer, no second admin, no "last admin" guard on `DELETE /account` (searched `accountApi`, `adminApi`, `Directory`). *Consequence:* a Pim whose admin deletes themselves is claimable by the next claimant while members and their data remain. **PRESERVE** single-admin model, claim window and code. **PROPOSED HARDENING:** block self-delete for the last admin or add transfer. → *User choice U4.*
7. **Sign-out is client-side only.** EXPLICIT: `POST /auth/sign-out` clears the cookie and voids that credential's device links only (`auth/index.ts:328-333`); cookie `Max-Age` 30 d (`:80`); a session is valid iff the sealed cookie verifies and `store.hasCredential(credential)` (`:220-224`). ABSENT: a server-side session table (Auth store tables: passkeys, identities, meta, tokens, recovery codes, device links, `auth/store.ts:55-107`), "sign out everywhere", and any code that rotates `cookie_key` (only read/created at `directory.ts:236-241`). *Consequence:* a copied cookie works for up to 30 days unless the passkey/identity it names is deleted (which kills it at once). **PRESERVE** statelessness or accept forced re-login at cut-over. **PROPOSED HARDENING:** server-side sessions with revocation. → *User choice U5.*
8. **Guests and `POST/PUT/DELETE /mcp` (connector management).** ABSENT ENFORCEMENT: `/mcp(/…)` is in `GUEST_ROUTES` for all four methods (`accounts.ts:159`); the handlers `POST /mcp` (`routes.ts:2153-2168`), `PUT/DELETE /mcp/:id` (`:2169-2196`) and `Connectors.connectApp` (`connectors.ts:77`) never test role or `guestBot()` (searched `rg "guestBot|role" src/space/routes.ts src/space/connectors.ts`: guestBot only at `routes.ts:307,1300,1338`). *Consequence:* a guest can connect any directory connector in **their own** space (`app` must be in `appDirectory()`, `routes.ts:2160-2162`); the OAuth return `GET /mcp/callback/<guestOwner>` is open to guests (`gateway.ts:245-248`). UNCERTAIN: whether the connected tools reach the bot agent's chats (the guest copy is created with `apps: []`, `sharing.ts:529,582`). The only comment of intent, "connect nothing else to their space", is on `notForGuests` and is applied to `/mcp` OAuth, consent and hosted-enter (`gateway.ts:117-118`, `:175,182,430,567-575`), not to `/api/mcp`. **PRESERVE** only if existing guests do this; **PROPOSED HARDENING:** refuse `/mcp` writes for guests.
9. **Guest accounts can create API tokens/passkeys/device links.** ABSENT ENFORCEMENT in `handleAuth` (no role test; `rg role src/auth/index.ts` → type only, `:52`), and `/auth/*` is dispatched before the guest allow-list (`gateway.ts:577`). It must stay absent for passkeys/identities, since a guest registers and activates through the same routes. Tokens made by guests are still confined by `GUEST_ROUTES`, which runs after `admit()` for token and session callers alike (`gateway.ts:627-630`). *Consequence:* up to 20 guest tokens, usable only on the allow-list. **PRESERVE.** No hardening needed beyond optional blocking of token creation for guests.
10. **Bad bearer + valid cookie, and tokens in URLs.** EXPLICIT: `authorize` tries the token, and on any failure falls through to the cookie session (`gateway.ts:128-139`); `fromAnotherSite` is applied only on the cookie path (`gateway.ts:150-151`) because tokens are not ambient. `?token=` is accepted on every API route (`gateway.ts:108-112`), not only sockets; only publish routes refuse it (`accounts.ts:563-566`). UNCERTAIN: what Cloudflare/ingress access logs record of query strings (outside the code; the Worker's own logs are structured events, e.g. `gateway.ts:555-561`). **PRESERVE** both behaviors (clients rely on `?token=` for WebSockets). **PROPOSED HARDENING:** accept `?token=` only on upgrade requests.
11. **Caches.** EXPLICIT: per-isolate account cache 30 s (`accounts.ts:33,42-50`), bot cache 30 s (`:112-122`), `forget()` clears only the calling isolate (`:52`; called at `:236,276,368,397,1000`), `synced` map cleared at 10 000 entries (`:176-177`). Suspension reaches the space at once and the space refuses 403 itself (`accounts.ts:998-1000`, `pim.ts:1946,1996-2003`). *Consequence:* un-suspension, deletion state and a bot's link on/off can lag ≤ 30 s on other isolates; role never changes (gap 6), so no role lag exists. **PRESERVE** ≤30 s staleness as the acceptable bound. **PROPOSED HARDENING:** none needed except shared invalidation if the cache moves out of process.
12. **Circle semantics.** EXPLICIT: usernames are copied into host `pim_circle_members` and visitor `pim_shares` (`circles.ts:179-188`, `visits.ts:112-121`) and are immutable (gap on role: no `UPDATE … username`); moving a person between circles upserts the row and calls `shareReceived` **only for a first-time member** (`sharing.ts:131`, `circles.ts:179-188`), so their space is not told; their brief refreshes before each of their turns in the visit (`conversations.ts:154`, `sharing.ts:693-707`) and every call is re-checked (`:154-165`). ABSENT ENFORCEMENT: retry of failed `shareRevoked` (`tellRevoked` warns and moves on, `sharing.ts:142-150`; callers `:139`, `routes.ts:2061`; no queue). *Consequence:* the visitor's own `pim_shares.revoked` can stay 0 so `GET /visits` shows `available:true` (`routes.ts:2079-2088`) while the host refuses every call with "doesn't share their space with you". **PRESERVE** both behaviors and the re-check-on-call design. **PROPOSED HARDENING:** a reconciliation job comparing `pim_circle_members` with `pim_shares`.
13. **Guest-asked approval alert.** EXPLICIT: the host files the approval, broadcasts `approval` to open sockets, then `deliverNotification(notification, {sockets:false})` (`sharing.ts:346-371`, bot variant `:849-866`), which calls `#pushNotification` unless `push:false` (`pim.ts:1400-1407,1466-1488`) — so **every Web Push subscription of the host receives title+opening sentences of the summary** (`"<name> asked your agent"`, `"<name> (<circle>) wants: <summary>"`), and a failed push (410) deletes the subscription (`pim.ts:1485`). UNCERTAIN: nothing about push delivery itself (external services). **PRESERVE.**
14. **Rate limits.** EXPLICIT: numbers are one table for both runtimes (`runtime.ts:35-45`: auth 30, api 600, public 600 per 60 s); Cloudflare uses the two bindings (`runtime.ts:162-164`; `public` shares `API_LIMITER` under key `public:<address>`), celld uses `Directory.hit` fixed windows with ≤10 000 keys per limit, **refusing when full** (`directory.ts:344-360`); a Cloudflare deployment **without the binding has no limit** (`runtime.ts:157-158,163`); an unknown runtime refuses everything (`runtime.ts:165`). The `auth` limiter covers all non-GET `/auth/*` and `/oauth/*` without distinguishing endpoints (`gateway.ts:555-561`); `api` is per owner and counts each WebSocket upgrade as one request (`gateway.ts:156-167,622`). ABSENT: per-endpoint limits. **PRESERVE** the numbers and fail modes per runtime; **PROPOSED HARDENING:** per-endpoint limits on `/auth/sign-in`, `/auth/register`.
15. **Browser live vs desktop.** EXPLICIT policy in code: desktop (`/computer/screen`) and displays are session-only (`gateway.ts:650-654`); `/browser/live` and `/notes/live` take token or session (`gateway.ts:644-648` only checks path/upgrade). `/browser/live` is a view/control of **an agent's chat window** (mouse and keyboard over it, `sockets.ts:227-232`), not the person's own desktop. ABSENT ENFORCEMENT of a session requirement on it. **PRESERVE.** **PROPOSED HARDENING:** session-only for `/browser/live` input.
16. **Gallery secrets at rest.** ABSENT ENFORCEMENT: shared model-provider and compute-provider credentials are stored as JSON in `providers.provider` / `compute_providers.provider` (`gallery.ts:311-322`); `rg "seal|encrypt|APP_CREDENTIALS_KEY" src/gallery.ts` → none. (Storage-level encryption belongs to the platform, not Pim.) Per-space connector credentials are sealed elsewhere (other fragment). **PRESERVE:** migration must carry these rows and treat the destination store as holding secrets. **PROPOSED HARDENING:** seal with a key held outside the database.
17. **Export without import.** ABSENT ENFORCEMENT (a feature): `rg "/import|importData" src` → nothing; `GET /account/export` excludes secrets by design (`accounts.ts:441-456`, `docs/reference.md` export). **PRESERVE:** export shape; migration reads stores directly.
18. **HTTPS assumption.** EXPLICIT: session/challenge/oauth cookies are always `Secure` and `__Host-` prefixed (`auth/index.ts:75,186-187`); `PIM_PUBLIC_URL` accepts `http:` or `https:` (`deployment.ts:69-72`); WebAuthn RP ID is the hostname (`auth/index.ts:267-268`). *Consequence:* over plain HTTP the cookie is set with `Secure`; browsers that refuse it (all except localhost, by browser policy) never keep a session. UNCERTAIN only as to each browser's handling; the Pim itself neither warns nor rejects `http:`. **PRESERVE.**

### Unavoidable user choices (code cannot decide; need a product call)
- **U1 token scope (gap 3):** keep unscoped tokens forever, or add scopes/expiry? *Recommend:* keep behavior and hash format for the cut-over (hashes must keep working), add optional scopes later; do not silently make always-approve/permissions session-only.
- **U2 admin token reach (gap 4):** should an admin's token share bots and manage Gitea? *Recommend:* preserve now; make those session-only together with `/admin` in a separate, announced change.
- **U3 suspended authors' public content (gap 5):** keep serving, or hide on suspension? *Recommend:* hide, because suspension is an abuse tool; implement as a Gallery status filter, after the migration baseline is established.
- **U4 admin continuity (gap 6):** allow transfer/second admin, or guard last-admin delete? *Recommend:* keep single admin at cut-over, add a "last admin can't delete self" guard first (smallest change).
- **U5 session revocation (gap 7):** require server-side sessions? *Recommend:* yes in the new architecture (it needs a session store anyway), accepting one forced re-login at cut-over unless `cookie_key` is copied.
Not a user choice (engineering only): gaps 1, 2, 8–13, 15–17. Gap 18: *recommend* keep HTTPS-only.
