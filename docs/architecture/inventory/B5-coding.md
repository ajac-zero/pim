## 0. Headline facts the design must respect (verified)

1. **Selectable harness ids** are exactly `pi`, `claude-code`, `codex`, `mistral-vibe`, `amp` (`CODING_HARNESSES`, `packages/coding/src/thread-store.ts:23`; `HARNESSES` for the vault is the same minus `pi`, `packages/shared/src/harnesses.ts:21`). There is NO Gemini/Cursor/Aider/OpenHands etc. `docs/coding-api.md` "harness … `pi` by default" and the type comment in `src/coding/api.ts` ("The others aren't available yet") is stale; code accepts all five (`src/coding/threads.ts:226-229` harness check in `startThread`).
2. **Three execution families** (not four harnesses on one model):
   - A. **Sandbox-hosted, Pim's own agent loop**: `pi` (loop runs inside `CodingThreadDO` on pi-durable `PiHarness`; only tools run in the workspace).
   - B. **Sandbox-hosted vendor CLI**: `claude-code`, `codex`, `mistral-vibe` (`CLI_HARNESSES`, `packages/coding/src/harness/index.ts:11`). One CLI process per turn via `workspace.exec`; resumable via the CLI's own session id.
   - C. **Remote vendor API (agent-hosted "orb")**: `amp` only (`providerKind:"agent-hosted"`, `AmpHttpOrbClient`, `packages/coding/src/orb/amp-http.ts`). No workspace, no slot, no scheduler involvement. The old workspace Amp CLI harness is RETIRED (`docs/coding-amp.md`; `TD:1251 #isLegacyAmpWorkspace`, `LEGACY_AMP_WORKSPACE_MESSAGE` TD:81); old rows stay readable.
3. **The `pi` coding harness is NOT independent of the normal pi harness**: `CodingThreadDO` imports `PiHarness` from `agents/harness/pi`, `createRegistry`/`Harness`/`section` from `@earendil-works/pi-durable`, `Lifecycle` from `agents/lifecycle` (`TD:7,9,10` imports, `harness = new PiHarness(...)` `TD:280-303`, `Lifecycle.install` `TD:305`, `lifecycle.use(this.harness)` `TD:308`). Its transcript lives in the thread DO's SQLite under `pi_*` tables next to `coding_*` (`TS` header comment). The design claim "normal agents keep pi-durable, coding agents are separate" is therefore false for the `pi` coding harness: Forge either keeps pi-durable for `pi` threads or must reimplement/port that transcript+resume loop (see §Pi harness).
4. **No blocking "wait for completion" API exists.** Normal agents learn of completion by a **push wake**: thread emits `thread.turn_ended` → `supervisorSink` (`supervisorSink`, `src/coding/supervisor.ts:15`) → `Pim.codingTurnEnded(chat, text, key, agent)` (`src/space/coding.ts` `codingTurnEnded`) → `submitTo(... whenBusy:"followUp")` into the chat. Stalls use the same wake path (`codingStalled`/`#notifyStalls`). Cross-system coupling Forge must preserve (see §Completion wake).
5. **The model gateway (`/api/coding/gateway/...`) is implemented and tested but has NO production caller wiring CLI harnesses to it**: `CodingThreadDO.modelGatewayEnv` (TD:1942) is referenced only from `test/coding-model-gateway.test.ts` and `test/coding-thread-workspaces.test.ts`; `authEnv` (`packages/coding/src/harness/auth.ts`) says gateway mode is "not built". `docs/reference.md` ("Model gateway for coding threads") describes it as if in use. Treat as shipped-but-dormant surface (routes live at `src/gateway.ts:619`).
6. **Cost for coding threads never reaches the space's usage ledger** (`docs/reference.md` "TODO: coding threads": `run_kind='coding_thread'` "Not recorded yet"). Spend lives only in the thread DO (`coding_event`, `coding_thread.spent_usd`) and is mirrored to the scheduler index (`pim_coding_threads.spent_usd`).
7. **Repository hosts**: GitHub (via GitHub App, secrets) AND one Gitea instance (OAuth2 connection, `PIM_GITEA_*`) — docs ("Coding threads work only with repositories on GitHub", `reference.md:216`; `coding-api.md` "`repo` must be https://github.com/...") are stale; code `deploymentProviders` (`src/coding/git-broker/worker.ts:71-73`) registers both and `startThread` resolves through it. Amp threads (orb) clone with Amp's own creds, not the broker.

## 1. Identity / ID shapes (cross-cutting, verify before any migration)

- **Thread ID** = deterministic UUID-shaped hash `sha256("pim coding thread\n<space>\n<operationId>")` truncated to 8-4-4-4-12 hex (`src/coding/threads.ts` `codingThreadId`, `src/coding/threads.ts:194-197`). Re-POSTing with the same `operationId` returns the same thread (`created:false`). `operationId` defaults to `crypto.randomUUID()` at the API/tool; agents' `coding_start` memoizes it via `api.memo("operation")` (`src/extensions/coding.ts:131`) so a replayed tool call starts the same thread.
- Thread DO name = thread ID (`env.CodingThread.getByName(threadId)`, TD:4521; `#threadId()` TD:2187). Scheduler DO name = space owner ID (`env.CodingScheduler.getByName(spaceId)`, SD:619). Vault entries live in the **Pim (space) DO** named by owner ID (`src/coding/vault/worker.ts`).
- Web page `/coding/<threadId>` (`threadPath`, `src/coding/api.ts` end). Public API under `/api/coding/threads[/:id/...]`, `/api/coding/vault/...`, `/api/coding/repos/:owner/:name/settings`, `/api/coding/git/<owner>/<name>.git` (broker), `/api/coding/gateway/<anthropic|openai>/...`, `/api/coding/gitea/{authorize,callback,status,connection}`, admin `/api/admin/coding/pools` and `/api/admin/compute` (`src/gateway.ts:616-637`, `src/accounts.ts:934-937`).
- Tools additionally accept: page URL `/coding/<id>` (with/without origin), Amp `T-…` id, `https://ampcode.com/threads/T-…` (`threadRef`, `src/coding/threads.ts:50-57`).
- Approval id for app-initiated push: `cp-<sha256(thread\nbranch\nhead)[0:32]>` (`codingRequestPush`, `src/space/coding.ts`); session `coding:<threadId>`.
- Wake key: `coding:<threadId>:<operationId>`; dedupe meta `coding_woken:<key>` in the space store (`CODING_WAKE_KEY`).
- Branch name `pim/<slug-of-task>-<id>` (`branchName(task, threadId)`, TD:1067 (call) and `branchName` TD:4978).
