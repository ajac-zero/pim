# v2 implementation status

What `pim/v2-canonical` implements of the audit ([rearchitecture-foundations-audit.md](rearchitecture-foundations-audit.md), inventory in `inventory/`), where it is tested, and what is not proven. Written at the integration of all six workstreams; read the gaps before relying on a claim.

**What "tested" means here.** Each module's own tests run against a real PostgreSQL (and, where named, NATS, an S3-protocol server, real WebSockets, real processes). The cross-module claims are tested in `packages/v2-server/test/`. **Every one of the audit's 162 entries is mapped, one row each, in [v2-inventory-coverage.md](v2-inventory-coverage.md)** (generated by `scripts/v2-coverage/build.mjs`; a test fails if an entry is unmapped or the file is stale): 138 verified, 20 partial, 0 gap, 4 not behaviour. The statuses are judgments recorded in `scripts/v2-coverage/rules.mjs`.

## The processes

`@pim/v2-server` (`node --import tsx src/main.ts <role>`, image `deploy/Dockerfile.v2`) runs `migrate`, `gate`, `live`, `runner`, `forge`, `canvas`, `relay`, `maintenance` or `all-in-one` from `loadProcessConfig`. Each serves `/healthz`, `/readyz` and `POST /drain` on `PIM_HTTP_PORT` and Prometheus metrics on `PIM_METRICS_PORT`; with `PIM_INGRESS_SECRET` set it refuses requests that lack the proxy's header. Each process connects as its own database role (`pim_gate`, `pim_runtime`, `pim_live`, `pim_forge`, `pim_maintenance`), none a superuser or `BYPASSRLS`.

| Role | Runs |
|---|---|
| `gate` (also `canvas`, `relay`) | The application API and sockets (`@pim/v2-app`), the projections' snapshots at `/api/snapshot/**`, Forge's coding API at `/api/coding/**`; publishes revocations on Pulse; carries a decided approval to the runtime. |
| `live` | WebSocket at `/api/ws`, snapshots at `/snapshot/**`, the projector (runtime commits and Forge's feed, woken by `pg_notify` and polling). |
| `runner` | The runtime's `Runner` and the command relay (Gate's inbox to the runtime's), with the default agent host (`agent-host.ts`, `agent-tools.ts`): model providers, prompt context and the agent tools. Not ready until any restore has been reconciled (`pim_ops.ops_restore`). It also reads `PIM_APP_DATABASE_URL` (a login in the gate role, for what tools write), `PIM_FORGE_DATABASE_URL` (coding), `PIM_DEFAULT_MODEL`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `PIM_AI_GATEWAY_URL`, `PIM_AI_GATEWAY_KEY`, `PIM_AI_GATEWAY_MODELS` and the key ring (`PIM_KEK_*`); without the databases the tools that need them say so. |
| `forge` | Forge's pool and connectivity, and `startForgeLoops`: the worker, scheduler and stall supervision over `pim_forge`, with the harness ports configured from the environment. Its HTTP surface on the Gate: threads, pools, harness logins (vault), git broker, Gitea and (with a provider key) the model gateway. |
| `maintenance` | Moves Forge's wakes into the chats that started threads (`coding_wake`) and Forge's spend into the cost ledger; delivers approval timeouts to the runtime; trims Forge's outbox. |

How the schemas are joined (migrations `0600`–`0602` in `packages/v2-server/migrations`, one ledger, one migrator):

- **Gate to runtime:** the Gate admits a command into `pim_app.command_inbox` (202 at once). The Runner's relay claims it through `pim_app.relay_claim` (a `SECURITY DEFINER` function), creates the chat's family partition and conversation under the application's ids, hands the command to the runtime's inbox, and marks it `runtime_committed` once pi has taken it.
- **Runtime to Live:** `runtimeOutboxSource` turns commits (receipts, outbox references, the live document) into projected events; partials are replaced by the final message.
- **Forge to Live and to the runtime:** Forge's outbox is numbered per owner without gaps (`0601`), projected as coding topics, and its wakes and costs delivered.
- **Live's identity:** two `SECURITY DEFINER` functions (`live_authenticate`, `live_valid`) give `pim_live` a credential's owner and validity without any grant on `pim_app`.

## Promotion of an imported snapshot

`@pim/v2-ops` lands a legacy export in `pim_ops`; `promote` (`node --import tsx src/main.ts promote`, or `scripts/v2-migrate/promote.mjs`) writes it into the live schemas, idempotently per tenant (`migration-bridge.ts`):

- `pim_app`: accounts and usernames, passkeys (rebound to the new relying party id), OIDC identities, recovery codes, API token hashes as legacy tokens, the chat directory with forks.
- `pim_runtime`: each tenant's pi history through the runtime's own importer, ids, `asOf` ancestry, document revisions and commit sequences kept; public chat ids equal the application's; a task whose effect was unknown at the cutover is orphaned, never replayed; missing built-in pi documents are created and `pi.agent` names the deployment's default model.
- `pim_projection`: a baseline of every imported chat and sidebar row, with the watermark just before the partition's next commit, so snapshots show history at once and new commits continue without a gap.
- `pim_forge`: coding threads and their events; a remote Amp thread keeps its handle and Forge adopts it without starting it again.

`packages/v2-server/test/migration-cutover.test.ts` rehearses it end to end: synthetic legacy export, import, audit, promote, then real gate and live processes (an imported passkey signs in, forked chats read over the snapshot API), a Runner answering a new message in an imported chat after the imported history, and Forge adopting the imported Amp thread (the fake cloud sees no second start).

**Promoted** per owner from `pim_ops.legacy_rows`, the sealed envelopes and the object copy: agents (and which chat answers as which), skills with every version and file, memories, goals and steps, triggers (a time trigger counts from the later of the cutover and the activation, so nothing the fence missed fires; a computer trigger waits paused for a grant), providers and connectors (re-sealed under the key ring), circles, chat links, profiles, apps with every version, notes (the Yjs document as the first update), object metadata and explicitly set settings only. A chat cut off mid-tool has its orphaned run cleared from its live document, so its next message runs at once. Templates, bots and the agent everyone starts with come across whole (role, description, connectors, contacts, the agents that come with them and every uploaded icon), as do a guest's bot, the admin's connector catalog and turned-off built-in apps, the bell, and a repository's setup script. **Not promoted**: legacy schedules (they are triggers), and standing approvals (an admin re-issues those through the Gate); coding grants are given to whoever had coding threads. The ops synthetic snapshot's pi records are not pi-faithful (no usage on assistant messages, no task state, string document scopes, stub `pi.agent` documents); the rehearsal adds what it needs, and the bridge rebuilds task and document records from the landing's typed columns.

**Mid-tool chats:** a chat cut off mid-tool (the fixture's `plain` and `branched` chats) had its in-flight run left in `pi.live`, queueing new input forever. The promotion now clears the orphaned run, so the next message runs at once (`migration-cutover.test.ts`).

## Measured: the integrated Runner, Gate, Projector and Live

The integrated benchmark (`packages/v2-server/test/integrated-bench.test.ts`, removed from the repository and in the history at `c1d60bb`) drove the product itself at 5, 50, 500 and 1,000 active streaming runs against real PostgreSQL (non-superuser roles, durability on for the qualification run) and NATS, with a scripted streaming model, while one person's `/api/sessions` and `/api/snapshot/sidebar` are read throughout. CI runs 5 and 50 with short windows. Full details, machines and definitions: [../v2-operations.md](../v2-operations.md#integrated-qualification-real-gate-live-projector-and-runners). Everything shares one 4-vCPU machine, load generator included, and each profile ran once.

**Multi-process** (`ed372aa`: Gate, Live with the Projector, and several Runners each a Node process of its own):

| Active runs | Runners | Commits/s | Turn latency p50 / p95 (solo 2.8 s) | Foreground p95 under load (warm baseline about 10 ms) | Machine CPU |
|---:|---:|---:|---|---|---:|
| 5 | 2 | 36 | 2.7 / 2.7 s | 9 ms | 44% |
| 50 | 2 | 122 | 8.6 / 8.9 s | 15 ms | 69% |
| 500 | 9 | 145 | 34 / 44 s (only 327 of 500 admitted when the window opened) | 86 ms | 95% |
| 1,000 | 17 | 217 | none completed in the 30 s window (418 admitted) | 451 ms | 100% |

**Scale is not accepted.** The relative budget (p95 within 20% of the warm baseline) **failed from 50 active runs upward in both harnesses** (multi-process 15.3 ms against about 10 ms; one process 54 ms against 12 ms) and was met only at 5. In the more realistic multi-process harness **1,000 active runs also missed the absolute budget (p95 under 250 ms) at 451 ms**: the machine was at 100% CPU, **no turn finished inside the 30 s window** (all eventually landed), and **only 418 of 1,000 runs were admitted when the window opened**; the absolute budget was met up to 500 runs. A paused socket's roughly 3 MB buffer absorbed everything sent, so the slow-reader coalescing path was not triggered. At 50 runs the Projector's single drain loop, not the Runners, limits readable turns (about 1,000 commits behind at a plateau); at 500 and above the machine is out of CPU. Every turn eventually landed and the projection caught up (82 s after the load at 1,000). Not measured: real providers, tools in turns, a separate database host, PgBouncer, Kubernetes, long stored histories. The slow-reader coalescing path was not reached by the load (socket buffers absorbed it); it is covered by Live's own tests.

**In one process** (`1dcecd0`, the first run: Gate, Live, Runners and Projector in a single Node process; superseded as the method, results kept): 5 runs 1.3 s answer readable, 50 runs 4.5 s, 500 runs 55 s, 1,000 runs 89 s, about 95 to 109 commits/s from 50 runs up with the one process at 84 to 88% of a core; foreground p95 under load 19, 54, 78 and 78 ms, relative budget met only at 5 runs. The two methods agree on the shape: the integrated stack commits about 100 to 200 commits/s on this machine, far below the reference writer's 2,000 to 3,700, so the Runner's own per-commit work, not PostgreSQL's fsync, is what to profile; and neither holds 1,000 simultaneous streams here. The one-process result is the easier configuration and is never evidence of scale acceptance; the multi-process figures are the ones to quote.

Each profile ran once; the harnesses and their raw results are in the history at `c1d60bb`.

## What a "Verified" inventory row means

[v2-inventory-coverage.md](v2-inventory-coverage.md) has 162 entries: **138 Verified, 20 Partial, 0 Gap, 4 not behaviour.** Verified means an automated sandbox test exercises that entry's v2 behaviour; it is **not** full live production parity, and most of those rows reach third-party services only through stand-ins. No entry is a gap. The 20 Partials each carry their missing part in the matrix note.

## The web app on v2, and what it defers

The Gate serves the web app (`web/`, built into the image) and answers the routes it calls in the shapes the Cloudflare version had (`packages/v2-server/src/compat/`, tried before the Gate's own routes). The Cloudflare Worker that served the same app is no longer in this branch: it was removed after v2 reached parity, and the git tag `v1-final` is its last commit. `node scripts/v2-dev/web-routes-gap.mjs` lists the web app's routes v2 does not answer; what remains there is the script's false positives (template-literal paths, sockets, `/auth/*`, snapshots, and the routes Forge's and the Gate's own handlers answer without a route table), and the compute providers' create, edit and delete, which answer unsupported because v2 reads the sandbox manager from the environment.

The web app uses Live's cursor protocol and HTTP commands (`V2Link`); v1's `/api/ws?session=` chat socket is not served. What the web app shows is built on v2: queue editing and steering (`queue_change`), email, rooms (a seat per agent, agents waking each other, a seat's model), hosted apps and apps with a backend, the canvas and its tools, a chat's own model, environment snapshots for coding threads, the coding page's live stream (newline-delimited JSON), diagnostics with an event log, and the compute quotas. What is **not carried** is below; each answers honestly (empty, 404, 409, 501, `unsupported`, or a sentence in a tool's result) rather than with invented data:
- Widgets from connector tool results (Spotify's now playing; Pim's own widgets are loaded), and the live coding stream's partial text and running-command output (the stream follows the conversation a message at a time; `Accept: text/event-stream` is not offered).
- The utility model (names, summaries, suggestions, an improved prompt) reaches a ChatGPT-plan model with the plan's token (`compat/utility.ts`); an app's `pim.ask` does not, and neither's calls are metered.
- Live pushes of room changes (a room's members and mode ride in the chat's listing and sidebar row), and a room member held on the plan's usage limit is not shown as held.
- The majordomo's approval review is one model call, not v1's review conversation with recall and zoom; `write_skill`'s `from` and a file copied `from_url` (`install_skill` takes a GitHub folder or a folder of the person's files); image models of Google and Anthropic and a daily image limit.
- Harnesses pointed at the model gateway: v1 never wired them either (`modelGatewayEnv` had no caller), so the gateway stays a token-only API for clients. A pi coding thread runs on the person's own providers and ChatGPT plan, as their chats do (Forge's role reads them through the definer functions of migration 0701), and `PIM_CODING_DEFAULT_MODEL` is only what a thread that names no model starts on. A thread's environment is readied as in v1 (toolchains, dependencies, `.pim/env.json`, the setup script): where the sandbox manager keeps snapshots the sandbox is kept as the person's snapshot of the repository and their next thread starts from it, `POST /api/coding/threads/:id/environment/rebuild` sets it up again, and a host without snapshots builds in place. Not ported: the lock that makes a person's simultaneous threads wait for one build (each builds, and the manager keeps one snapshot per key), and the environment's notices at the start of the transcript (the log has the events).
- File computer triggers (v1 delivered none either: a `file` source is kept as a draft, and enabling one answers `source_not_wired`). The computer container does not ship Cua's binaries (`cua-spacesd`, `cua-env-driver`): its displays' desktop tools are served by Pim's own driver (`computer/desktop-driver.ts`), which does not stream a display, so there a person watches and takes over a chat's browser rather than its whole display.
- Storage and app limits are shown, not enforced. Diagnostics read a chat's turns from its transcript and the model-call ledger (which records failed calls and where a call's time went), and an event log of the last 200 things per person (`pim_app.diagnostic_events`: a model that failed over, a cooldown, a failed or slow request).

**Settings that matter for a deployment** (all in `deploy/compose/.env`, written by `init-env.sh` where they are secrets): `PIM_VAPID_*` (Web Push; never change them), `PIM_CODING_SIGNING_KEY` (shared by Gate and Forge), the OAuth clients of native connectors (`GOOGLE_GMAIL_*`, `GOOGLE_DRIVE_*`, `SPOTIFY_*`, `GITHUB_CLIENT_*`; a connector is offered only when its client is set, with the redirect `<PIM_PUBLIC_URL>/mcp/callback/apps`), `PIM_IMAGE_MODEL`, `PIM_MEMORY_MODEL` and `PIM_MEMORY_NAP*`, the Runner's guards (`PIM_MODEL_STALL_MS`, `PIM_TOOL_TIMEOUT_MS`, `PIM_RUN_STALL_MS`, `PIM_STOP_GRACE_MS`), per-space limits (`PIM_LIMIT_*`) and rate limits (`PIM_RATE_*`), and `PIM_HOSTOPS_ENROLL_TOKEN`.

**Not promoted by the migration**, kept in `pim_ops.legacy_rows` (nothing is deleted): push subscriptions (each browser subscribes again), built-in or non-chat-completions shared providers, a bot's own snapshot of its agent (a bot here follows its agent; its picture becomes the agent's when the agent has none), the Gitea connection (deployment-wide tokens: connect again once), standing approvals (an admin records them again; a person who had coding threads is given a coding grant), every computer's pairing and the computer host's, and the hostops credential and audit (computers connect again with a new token, and the admin pairs pim-host and issues the hostops credential again), the compute providers' settings and the sandbox pools' history and queue, pending approvals and tasks, the number of calls of days older than the per-call log (their tokens and cost are kept), per-day tool-call counts, diagnostics, audit of the UI, the "seen" and UI state of files and screens, and MCP tools' on/off (v1 never kept the tool list, so an owner switches tools on again once). Promoted and sealed: ChatGPT-plan sign-ins, MCP servers with their tokens, native connector tokens (renewable once the deployment's OAuth client is set), shared providers (`pim_app.instance_providers`, 0695), templates, bots and the default agent. A passkey works only on the hostname it was made for; on a new hostname a person signs in with a recovery code ("Lost your passkey?") and adds one.

## What is not proven or not built

- **Kubernetes** manifests were never applied; the Compose stack is the tested deployment.
- **External environments:** CloudNativePG, OpenBao, gVisor, WAL archiving to object storage, failover and restore on a live cluster; real Google/GitHub browser sign-in; the vendor CLIs' interactive logins (Claude Code, Codex, Mistral Vibe, Amp).
- **Reached only through stand-ins in tests:** the connectors' OAuth and MCP servers (Gmail, Drive, Spotify, a remote MCP server), the SMTP server email goes through (a real mail provider was not run), the browser push service, OpenAI's and ChatGPT's endpoints (chat, images, the plan's sign-in), a git host for push (a public GitHub clone through the broker was run), pim-host's `docker` (a test runs the real pim-host against a stand-in), and Cua's desktop (`cua-spacesd`, `cua-env-driver`), whose binaries the computer image does not ship (there the desktop tools run on Pim's own driver, which `computer/test/desktop-driver.test.ts` drives on a real display with a real app). No automated test boots the images: the Compose smoke test (`scripts/v2-compose/smoke.sh`, run after a push to main) does.
- **The agent host.** Not ported from v1, on purpose or still: widgets from connector tool results, the deployment-written extensions of `pim.config.ts` (a deployment adds tools through connectors; `docs/extensions.md`), `write_skill`'s `from` and a file copied `from_url`, and the approval review's conversation with recall and zoom (one model call decides). The Runner runs agents without injection: env and owner providers, per-chat agent resolution (migration 0604), prompt context and the tools of the `pim` extension (memory, skills, goals, schedules, triggers, notes, apps, `fetch_url`, approval-gated `http_request`, delegation, agents, `coding_*`; `test/agent-host.test.ts`). A model that fails before output, or while only thinking (rate limit, overload, 5xx, a refused credential, a stalled stream), is cooled for every Runner (`pim_runtime.provider_cooldowns`, 0666) and the turn goes to the next model of the chat's list (`provider-failover.ts`); once text or tool calls were shown the failure is final. A run held while the ChatGPT plan is out of usage goes on by itself when the limit resets: the Runner leaves a row in `pim_app.held_retries`, and the maintenance role asks the chat to try again then (`sweepHeldRetries`; a chat that is no longer held is left as it is). A chat's model is read before each message: its own (0670), its agent's, the person's Settings', then their fallbacks; the deployment's default only starts a chat and never replaces an imported chat's model. The owner's catalog is rebuilt on each message, so a changed provider is used at once. A stuck chat ends with an error (stoppable tools, a stream stall guard, the run watchdog), and the stop button works. An owner signed in with ChatGPT runs `openai` on the plan: the credential is sealed in `pim_app.chatgpt_credentials` and the Runner refreshes it under a row lock (migration 0610; `PIM_CHATGPT_ISSUER`, `PIM_CHATGPT_BASE_URL` and `PIM_PROVIDER_COOLDOWN_MS` are for proxies and tests). A v1 sign-in is promoted by the migration bridge. A provider or key changed by an owner reaches partitions opened afterwards. The computer tools (files, `shell`, browser, desktop; `computer-tools.ts`), the MCP and native connector tools and watches, `generate_image`, `install_skill`, the memory nap, the admin's majordomo tools and host operations, a guest's two tools, the group chats' tools (`remove_from_chat`, `chat_history`), the canvas tools, `app_deploy`, the skills a connector publishes and `send_to_user`'s email channel are ported; what has effects outside the conversation is approval-gated. The tools that write need `PIM_APP_DATABASE_URL`, a login in the gate role, so a Runner holds one more credential than its own role.
- **Forge's worker runs in the `forge` role** (`startForgeLoops`: worker, scheduler and stall supervision, woken by `pim_forge_work` notifications) with the git broker, Gitea, vault and gateway mounted on the Gate under row-level security (`test/forge-worker-role.test.ts`, `v2-forge/test/rls.test.ts`). Not exercised: vendor CLIs against real logins and a real sandbox manager.
- **Cross-process Relay:** a Gate and a Relay in separate containers reach each other over NATS (`natsRelayBus`, `v2-live/test/relay-nats.test.ts`); in `all-in-one` the bus is in memory.
- **The web app uses v2:** `V2Link` (`LiveClient`, HTTP-first `/api/snapshot/*`, `v2-view.ts`) is chosen by server capabilities; the client of the Cloudflare version's `/api/ws` protocol (`pim-client.ts`) stays in the app only as a fallback the v2 server never needs. Tested by the web app's unit tests (`pim-client-v2.test.tsx`, `v2-view.test.ts`) and `v2-server/test/live-e2e.test.ts`; run in a browser against the booted Compose stack (see above), not by an automated browser test. The editor tab, the service worker and the screens are not driven by an automated browser test.
- **Importer scope** is the promotion above; what it lists as not promoted stays in `pim_ops.legacy_rows`.
- **Ids.** The application chooses a chat's partition and public id; pi allocates numeric conversation ids, so `pim_app.conversations.conversation_id` is a provisional number for chats made after cutover (imported chats carry the real one). Forge accepts owner ids that are not `o_…`; Live skips them.
- **Coding grants** are one source now (admin routes on the Gate write the application's tables and Forge's); quotas are not mirrored, and Forge's tables carry row-level security for the Gate (0406).
- **Drain leaves a trace.** A Runner drained mid-answer leaves pi's aborted assistant message in the transcript; the next Runner's turn follows it.
- **Three ledgers of external operations** (`pim_app`, `pim_runtime` 0106, `pim_ops`): unreconciled.
