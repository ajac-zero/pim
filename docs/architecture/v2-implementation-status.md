# v2 implementation status

What `pim/v2-canonical` implements of the audit ([rearchitecture-foundations-audit.md](rearchitecture-foundations-audit.md), inventory in `inventory/`), where it is tested, and what is not proven. Written at the integration of all six workstreams; read the gaps before relying on a claim.

**What "tested" means here.** Each module's own tests run against a real PostgreSQL (and, where named, NATS, an S3-protocol server, real WebSockets, real processes). The cross-module claims are tested in `packages/v2-server/test/`. **Every one of the audit's 162 entries is mapped, one row each, in [v2-inventory-coverage.md](v2-inventory-coverage.md)** (generated by `scripts/v2-coverage/build.mjs`; a test fails if an entry is unmapped or the file is stale): 76 verified, 61 partial, 23 gap, 2 not behaviour. The statuses are judgments recorded in `scripts/v2-coverage/rules.mjs`.

## The processes

`@pim/v2-server` (`node --import tsx src/main.ts <role>`, image `deploy/Dockerfile.v2`) runs `migrate`, `gate`, `live`, `runner`, `forge`, `canvas`, `relay`, `maintenance` or `all-in-one` from `loadProcessConfig`. Each serves `/healthz`, `/readyz` and `POST /drain` on `PIM_HTTP_PORT` and Prometheus metrics on `PIM_METRICS_PORT`; with `PIM_INGRESS_SECRET` set it refuses requests that lack the proxy's header. Each process connects as its own database role (`pim_gate`, `pim_runtime`, `pim_live`, `pim_forge`, `pim_maintenance`), none a superuser or `BYPASSRLS`.

| Role | Runs |
|---|---|
| `gate` (also `canvas`, `relay`) | The application API and sockets (`@pim/v2-app`), the projections' snapshots at `/api/snapshot/**`, Forge's coding API at `/api/coding/**`; publishes revocations on Pulse; carries a decided approval to the runtime. |
| `live` | WebSocket at `/api/ws`, snapshots at `/snapshot/**`, the projector (runtime commits and Forge's feed, woken by `pg_notify` and polling). |
| `runner` | The runtime's `Runner` and the command relay (Gate's inbox to the runtime's), with the default agent host (`agent-host.ts`, `agent-tools.ts`): model providers, prompt context and the agent tools. Not ready until any restore has been reconciled (`pim_ops.ops_restore`). It also reads `PIM_APP_DATABASE_URL` (a login in the gate role, for what tools write), `PIM_FORGE_DATABASE_URL` (coding), `PIM_DEFAULT_MODEL`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `PIM_AI_GATEWAY_URL`, `PIM_AI_GATEWAY_KEY`, `PIM_AI_GATEWAY_MODELS` and the key ring (`PIM_KEK_*`); without the databases the tools that need them say so. |
| `forge` | Forge's pool and connectivity. Steps no threads yet (see gaps). Its HTTP surface on the Gate: threads, pools, harness logins (vault), and the model gateway where a provider key is set. |
| `maintenance` | Moves Forge's wakes into the chats that started threads (`coding_wake`) and Forge's spend into the cost ledger; delivers approval timeouts to the runtime; trims Forge's outbox. |

How the schemas are joined (migrations `0600`–`0602` in `packages/v2-server/migrations`, one ledger, one migrator):

- **Gate to runtime:** the Gate admits a command into `pim_app.command_inbox` (202 at once). The Runner's relay claims it through `pim_app.relay_claim` (a `SECURITY DEFINER` function), creates the chat's family partition and conversation under the application's ids, hands the command to the runtime's inbox, and marks it `runtime_committed` once pi has taken it.
- **Runtime to Live:** `runtimeOutboxSource` turns commits (receipts, outbox references, the live document) into projected events; partials are replaced by the final message.
- **Forge to Live and to the runtime:** Forge's outbox is numbered per owner without gaps (`0601`), projected as coding topics, and its wakes and costs delivered.
- **Live's identity:** two `SECURITY DEFINER` functions (`live_authenticate`, `live_valid`) give `pim_live` a credential's owner and validity without any grant on `pim_app`.

## Promotion of an imported snapshot

`@pim/v2-ops` lands a legacy export in `pim_ops`; `promote` (`node --import tsx src/main.ts promote`, or `scripts/v2-migrate/promote.mjs`) writes it into the live schemas, idempotently per tenant (`migration-bridge.ts`):

- `pim_app`: accounts and usernames, passkeys (rebound to the new relying party id), OIDC identities, recovery codes, API token hashes as legacy tokens, the chat directory with forks.
- `pim_runtime`: each tenant's pi history through the runtime's own importer, ids, `asOf` ancestry, document revisions and commit sequences kept; public chat ids equal the application's; a task whose effect was unknown at the cutover is orphaned, never replayed; missing built-in pi documents are created and `pi.agent` names the deployment's default model.
- `pim_projection`: a baseline of every imported chat and sidebar row, with the watermark just before the partition's next commit, so snapshots show history at once and new commits continue without a gap.
- `pim_forge`: coding threads and their events; a remote Amp thread keeps its handle and Forge adopts it without starting it again.

`packages/v2-server/test/migration-cutover.test.ts` rehearses it end to end: synthetic legacy export, import, audit, promote, then real gate and live processes (an imported passkey signs in, forked chats read over the snapshot API), a Runner answering a new message in an imported chat after the imported history, and Forge adopting the imported Amp thread (the fake cloud sees no second start).

**Promoted** per owner from `pim_ops.legacy_rows`, the sealed envelopes and the object copy: agents (and which chat answers as which), skills with every version and file, memories, goals and steps, triggers (a time trigger counts from the later of the cutover and the activation, so nothing the fence missed fires; a computer trigger waits paused for a grant), providers and connectors (re-sealed under the key ring), circles, chat links, profiles, apps with every version, notes (the Yjs document as the first update), object metadata and explicitly set settings only. A chat cut off mid-tool has its orphaned run cleared from its live document, so its next message runs at once. **Not promoted**: legacy schedules (they are triggers), deployment-level providers, templates and bots, and coding grants and standing approvals (an admin re-issues those through the Gate). The ops synthetic snapshot's pi records are not pi-faithful (no usage on assistant messages, no task state, string document scopes, stub `pi.agent` documents); the rehearsal adds what it needs, and the bridge rebuilds task and document records from the landing's typed columns.

**A finding:** a chat that was cut off mid-tool (the fixture's `plain` and `branched` chats) keeps its in-flight run in its `pi.live` document, and new input queues behind it: the runtime does not clear a run whose task the bridge orphaned. Someone must reconcile those chats; the rehearsal sends its new message to an idle imported fork instead.

## Measured: the integrated Runner, Gate, Projector and Live

`packages/v2-server/test/integrated-bench.test.ts` runs real Gate, Live and two Runner processes against real PostgreSQL (non-superuser roles) and NATS, with a streaming scripted model: N people each start one turn at once, and a fifth person reads the sidebar and session list throughout. On this machine (4 vCPUs, one shared with everything, Node 26, PostgreSQL 17, results in `packages/v2-server/bench-results/`):

| People streaming at once | Gate 202, p50 / p95 | Answer readable after send, p50 / p95 | Foreground read, p50 / p95 / max | Peak projection lag (commits) | Runtime commits |
|---|---|---|---|---|---|
| 5 | 66 / 67 ms | 1.40 / 1.43 s | 6 / 25 / 59 ms | 13 | 66 |
| 50 | 88 / 103 ms | 3.08 / 3.86 s | 14 / 35 / 81 ms | 156 | 721 |

An answer takes about 1.4 s to stream by itself; 50 at once stretch it to about 3 s, and the projector trails by up to 156 commits at the peak and catches up within the turn. This is the integrated product, so it supersedes the reference-writer benchmark's claim about the Runner; the 500 and 1,000 run profiles of `@pim/v2-ops` were not repeated with it.

## What is not proven or not built

- **No Docker daemon here.** `deploy/Dockerfile.v2` and the Compose stack were never built or started; the Kubernetes manifests were never applied. Production-dependency installation and `node --import tsx src/main.ts` were checked outside Docker.
- **External environments:** CloudNativePG, OpenBao, gVisor, WAL archiving to object storage, failover and restore on a live cluster; real Google/GitHub browser sign-in; the vendor CLIs' interactive logins (Claude Code, Codex, Mistral Vibe, Amp).
- **The agent host is partial.** The Runner runs agents without injection: env and owner providers, per-chat agent resolution (migration 0604), prompt context and the tools of the `pim` extension (memory, skills, goals, schedules, triggers, notes, apps, `fetch_url`, approval-gated `http_request`, delegation, agents, `coding_*`; `test/agent-host.test.ts`). Model fallback is by availability when a chat starts, not after a failed request. A provider or key changed by an owner reaches partitions opened afterwards. The connector (MCP), computer, desktop and browser tools, `generate_image` and the background naps are not ported. The tools that write need `PIM_APP_DATABASE_URL`, a login in the gate role, so a Runner holds one more credential than its own role.
- **Forge's worker is not wired.** The `forge` role configures no compute provider, git host or vendor CLI ports, so no thread runs by itself; the slice completes one by writing what a worker writes. On the Gate: threads, pools, harness logins and (with a provider key) the model gateway are mounted; the git broker and the Gitea connection are not (they need a git host and a Gitea configuration this process does not build).
- **No cross-process Relay.** The Relay holds a computer's socket in the process it connected to; `canvas` and `relay` containers run the Gate's code, so a Gate and a Relay in separate containers cannot reach each other's computers. A NATS bridge was not built or tested. `all-in-one`, or one Gate that all computer traffic reaches, works.
- **The web app is not switched to v2.** `@pim/shared/live-client` and `/api/snapshot/*` exist and are tested; the web app's chat and sidebar views still use the v1 `/api/ws`.
- **Importer scope** is the core above; the rest of a space is not promoted.
- **Ids.** The application chooses a chat's partition and public id; pi allocates numeric conversation ids, so `pim_app.conversations.conversation_id` is a provisional number for chats made after cutover (imported chats carry the real one). Forge accepts owner ids that are not `o_…`; Live skips them.
- **Coding grants** are one source now (admin routes on the Gate write the application's tables and Forge's); quotas are not mirrored, and Forge's tables still carry no row-level security (the Gate holds a grant on them).
- **Drain leaves a trace.** A Runner drained mid-answer leaves pi's aborted assistant message in the transcript; the next Runner's turn follows it.
- **Three ledgers of external operations** (`pim_app`, `pim_runtime` 0106, `pim_ops`): unreconciled.
