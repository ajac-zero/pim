# Agent-hosted coding threads (orbs)

A coding thread's agent runs somewhere. Until now there has been one kind of provider for that: a **workspace** — a sandbox machine Pim makes (the sandbox manager's Compose pool, or Cloudflare Containers) and execs into, where the harness runs as a local process. An **agent-hosted** thread is the second kind: there is no machine Pim can exec into at all. The agent runs in the vendor's own cloud — an Amp **Orb** — and Pim only drives it through a client that speaks to that cloud.

The two kinds sit side by side in a thread's record: `providerKind` says which one runs it, and an agent-hosted thread also keeps the orb it runs on, the agent's own thread id and the page where the person can watch it (`src/coding/orb/types.ts`). Nothing about workspaces changes: their providers, their registry and their tests are as they were, and old thread records read as the workspace threads they are.

## The interface

`OrbClient` (`src/coding/orb/types.ts`) is the whole of what Pim can do with an agent-hosted thread. It is written so that nothing in it depends on one vendor's API: the client is the only seam, and a later slice adds a real Amp client behind it.

- `start({project, prompt, mode, title, idempotencyKey})` starts a thread and returns its id and url. It is **idempotent on the idempotency key**: the same key again is the thread the first call started, so a retry — after a lost response, a restart, anything — never starts a second orb and never bills for one.
- `steer(threadId, message)` gives a running thread another message. It **queues**: the agent takes the message when it is ready, on a turn boundary. It never interrupts the run in progress.
- `stop(threadId)` ends a thread: it is **archived** on the agent's site, so it leaves the person's list there, and its run is cancelled. Stopping a stopped thread does nothing.
- `state(threadId)` says what the thread is doing — `working`, `idle`, `awaiting_approval`, `error`, or `unknown` when the client can't tell — and when its agent last did anything.
- `messages(threadId, {after})` reads the thread's transcript, oldest first, a page at a time: each call asks for what follows the message the caller ends at.
- `usage(threadId)` says what the thread has cost in dollars, or **null when the client can't say**. Null means unavailable, not free.
- `capabilities()` says which of `steer`, `stop` and `usage` the client can do; a call on one it can't throws `OrbUnsupportedError`.

Every method throws a subclass of `OrbError` — `OrbUnreachableError` (the agent's cloud can't be reached just now, nothing was changed), `OrbAuthError` (the person's login with the agent's cloud was refused: a token missing, wrong or expired), `OrbUnsupportedError` (the client's `capabilities` say it can't), `OrbLostError` (the thread no longer exists there) — never a bare string, so a caller tells failures apart by type. There is no workspace behind the interface: no files, no commands, no resource limits Pim can set, no egress Pim can allow or refuse.

The conformance suite in `src/coding/orb/conformance.ts` is what a client must pass, in the style of the workspace suite: idempotent start, steering that queues without interrupting, idempotent stop, state as it moves, usage that answers null when it can't say, capability flags honoured, a lost orb reported as a typed error, and transcript paging. `FakeOrbClient` (`src/coding/orb/fake.ts`), an in-memory client with a deterministic clock and scriptable failures, is the first to pass it; `test/coding-orb-fake.test.ts` runs the suite against it.

## The Amp CLI client

`AmpCliOrbClient` (`src/coding/orb/amp-cli.ts`) is the first real client: it drives Amp Orbs through the `amp` CLI, the same one the workspace harness runs (`docs/coding-amp.md`), with `-ox` — execute mode on an orb in Amp's own cloud. It is the whole of a client without the running of the CLI: the commands are built there and handed to an injected `CommandRunner`, which the real one — a later slice — supplies by execing the CLI inside a Pim sandbox with the person's `AMP_API_KEY` in the process's environment. The token is the runner's to supply, so it is never on a command line, never in a log of one, and taken out of anything the CLI printed before the client repeats it.

What the CLI does is the client's contract: a start's first stream-json line names the thread and its process stays attached until the turn's `result` — a stream result being the only end of a turn — so `start` keeps the thread id under its idempotency key (in an injected key-value store, so a retry after a restart is still the same thread) and returns before the turn ends, and `steer` returns once the CLI has taken the message, since `amp threads continue` queues behind the running turn and its own process only ends when that turn does. What the client knows of a thread is what the CLI printed while Pim watched it: `messages` is the transcript it captured, `state` is its processes and the stream's last word (working while a turn is attached, idle after a result, an error on a failed one — unknown when nothing is tracked, after a restart). `stop` runs `amp threads archive`, which cancels the run and takes the thread off the person's list on ampcode.com, and kills the processes the client holds for it. The CLI reports tokens, not dollars, so `usage` is refused and `capabilities` says so.

`test/coding-orb-amp-cli.test.ts` runs the conformance suite against it, with a `FakeCommandRunner` (`test/fake-command-runner.ts`) that scripts the CLI's output, exit codes and delays: no real `amp` and no network anywhere in the tests, so what the real CLI does with a real token is not verified there.

## What is honest about it

- **Costs are the agent's word.** The client reports what the agent's cloud says it spent; the thread can't measure the run itself, as it can in a workspace it owns. A client that reports no cost answers `null`, and a budget can't be held to that.
- **Tests are the agent's word too, or n/a.** A workspace thread runs the repository's own tests in its sandbox and reads their exit codes. An agent-hosted thread reports what its agent says it did; Pim has no process table, no files and no terminal of its own there. What Pim can still check is the diff: the thread's commits and the branch it pushes, as with any harness.
- **Steering queues; it does not interrupt.** A workspace thread can stop a CLI's process mid-turn. Here the run belongs to the agent's cloud: a steered message waits for the agent to take it, and there is no way to cut a turn short except `stop`, which ends the whole thread.
- **`stop` archives.** Archiving is what takes the thread off the person's list on the agent's site; it is best-effort there, as it is for the Amp CLI harness's own threads. Cancelling the run is the part Pim asks for; whether the agent's cloud finished writing anything down first is its word again.
- **The repository is outside Pim's sandbox policy.** An agent-hosted clone reaches the network as the vendor's cloud allows, not as a workspace's egress allowlist allows, and the agent's own credentials and settings live there. What a workspace thread keeps out of a repository (`docs/coding-amp.md`'s untrusted-repository table) is out of Pim's reach here.

## How a coding thread runs one

A thread whose record says `providerKind: "agent-hosted"` runs its turns through the client and nothing else: no workspace, no slot of the space's scheduler, no environment (src/coding/thread-do.ts). The thread's `advance` job is the whole of the loop, and it is driven from durable state as every other step of a thread is, so an eviction loses nothing:

- **The first turn starts the orb.** `client.start`, with an idempotency key of the thread's own id and the turn's operation, and the handle it answers — the agent's thread id and the page where the person watches it — is written to the thread's record at once, before anything else is awaited: a restart finds it there and never starts a second orb. Every later turn is a message steered to the same orb, which the agent takes when it is ready, on a turn boundary.
- **The turn is polled.** Every 30 seconds the job asks `client.state`: `idle` ends the turn as any turn's end does, `error` fails it with what the agent last said, and `unknown` — a client that can't tell, such as one that was itself restarted — ends nothing; ten unknown looks in a row fail the turn as `orb_state_unknown`. A cloud that can't be reached is waited out, and an orb that no longer exists fails the thread (`orb_lost`).
- **The agent's transcript is mirrored.** Each look pages `client.messages` from after the last message mirrored — its id is kept on the thread's record, so a restart repeats nothing — into the thread's own conversation, so the person reads it where they read any thread's.
- **Steering queues.** A message sent mid-turn goes to the agent at once and waits there for the turn's end; a client that can't be steered says so in the thread's log, and the message waits for the thread's next turn instead of being lost. Aborting or archiving the thread ends the agent's thread (`client.stop`, idempotent — a client that can't stop says so too), and the turn ends cancelled.
- **Costs stay the agent's word.** At each turn's end the thread records what the agent says it cost, and its status reports it as `cost` — null, with an honest note, when the agent's cloud reports nothing, as the Amp CLI client's does. It is never counted against the thread's budget, which Pim can't hold to the agent's word. Tests are the agent's word too, or n/a: Pim ran none and reports none, and only the diff — the thread's commits and its branch — is Pim's own to check.

A thread finds its client through an `OrbClientFactory` (src/coding/orb/types.ts), injected the way workspace providers are: the thread asks with its own, its space's and its provider's name, and the factory answers the client. No deployment registers one yet — the real client's `CommandRunner` is a later slice — so a thread that says it is agent-hosted fails with `agent-hosted provider not available` rather than crashing.

## What is not there yet

This slice wires the loop above into a coding thread, and the fake client (`FakeOrbClient`) is what its tests run against. The Amp CLI client still has no runner that runs the CLI for it (the real one execs `amp` inside a Pim sandbox; a later slice) and so no factory registers it on a deployment. There is no way to start a thread as agent-hosted from the API or the UI, and no pool placement or scheduler slot for orbs: a thread record *can* say `providerKind: "agent-hosted"` and its orb, and nothing yet makes one say so. Those come in later slices. There is no feature flag or opt-in to add: this is additive code, on by default, and a workspace thread runs exactly as it did.
