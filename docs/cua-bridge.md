# Cua computers through an operator's bridge

`src/cua.ts` connects a space to pim-computer on a Cua VM through a bridge the operator runs. A space uses it only when its operator chose it for that space (see "Choosing Cua for a space"), and then uses no other computer. Spaces without that choice keep paired computers and Sprites exactly as before. Nothing here turns on, takes over or resumes the control state (`docs/computer-control-state.md`), so an operator's computer receives agents' requests only in a space whose control state some other, operator-side step has already enabled and leased to the agent; no code in Pim does either. Its tests use a `fetch` they give it, answered in the same process; none reaches the network.

## What the space talks to

A space's computer is reached through a `ComputerLink` (`src/computer.ts`): one of pim-computer's JSON messages at a time, both ways, which `Computer` reads and writes as it does for a paired computer or a Sprite. `Sprites.connect` makes one over the Sprites exec API, with each message a line of `pim-computer --stdio`'s input or output; `Cua.connect` makes one over the bridge's WebSocket, with each message a text message. `Computer` keeps its tracing as it was: a call is settled by its reply, a DevTools message by its answer, and anything sent and not answered when the link ends is unknown and never sent again.

The model is one persistent VM per space, where pim-computer runs as one non-root desktop user that every agent of the space shares. Agents are not isolated from each other on it, and Pim makes no claim that they are. `/workspace` is where the space's files are kept, which file calls stay inside; it is not a sandbox. A command runs as the desktop user and reaches whatever that user can.

## The bridge's contract

Pim does not assume Cua's own services speak pim-computer's protocol. The operator runs something that does, in front of the VM, and gives Pim, for one space, a `CuaBridge`: the space's owner ID, the bridge's address, and its bearer token. The bridge must:

1. **Serve HTTPS** at an address with no credentials, query or fragment (no `?` or `#` at all), and take a WebSocket upgrade there (`GET`, `Upgrade: websocket`).
2. **Authenticate the request** by `Authorization: Bearer <token>`, comparing in constant time, and refuse anything else before upgrading. The token is printable ASCII without spaces, 32 to 4096 characters.
3. **Bind to one space.** Pim sends the space in `x-pim-space`. The bridge must refuse a space that isn't the one its VM belongs to, and name the space back in `x-pim-space` on its `101` response; Pim closes a connection that doesn't.
4. **Not redirect.** Pim follows no redirect, so its token never goes to another address; a `3xx` is a failure.
5. **Carry pim-computer's messages unchanged**, one JSON message per text message, both ways: first the `hello` pim-computer sends, then `call` and `reply`, `cdp` and `cdp_closed`. Binary messages and messages over 16 Mi characters (`MAX_MESSAGE_CHARS`) end the connection; text that isn't JSON is ignored. One way to do it is to start `pim-computer --stdio --root <folder>` as the desktop user for each connection and relay each message as a line.
6. **Hold nothing back for later.** The bridge must not queue messages across connections or replay them on a new one, or answer for pim-computer: a reply must be pim-computer's own. When Pim closes the connection, the bridge ends pim-computer's input, so it quits the browser (saving what's signed in there) and exits, as on a Sprite. If the connection drops, what was in flight may or may not have run; Pim treats it so.
7. **Take one connection at a time per space.** A new connection replaces the old one, which the bridge closes.

## The bridge's relay

`computer/cua-bridge.ts` is the part of a bridge that keeps this contract between Pim's WebSocket and one session of pim-computer. Nothing in Pim imports it, and it adds no route, Worker or setting: it is for an operator's bridge to embed. It is not a bridge an operator can install: what it relays to is the embedder's (see "What is not done").

- **`new Relay({ space, token, path, open, log, maxOpeningChars })`** serves one space (its owner ID), with one bearer token, at one path, such as `/pim`. These come from whoever embeds it, are checked when it is made (an owner ID; a token as Pim sends it; an absolute, canonical path with no query or fragment), and can't change after; the relay keeps only a SHA-256 digest of the token. `log` gets fixed event names and reasons (`bridge.refused` with its status, `bridge.opened`, `bridge.ended`), never what a request carried or what a session threw; by default they go to `console.error`.
- **`relay.check(request)`** answers `null` for Pim's request, or the response that refuses it, in this order: `404` for any other path, or any query or fragment at all; `405` for a method other than `GET`; `426` without `Upgrade: websocket`; `401` unless `Authorization` is exactly `Bearer <token>` (a header over 4,103 characters isn't read), compared as SHA-256 digests in time that doesn't depend on where they differ; `403` unless `x-pim-space` is exactly the relay's space. It reads nothing else, so a token in a query or a cookie is never read, and no response is a redirect or repeats what was sent. Nothing else happens before a request passes.
- **`relay.open(client, signal)`** takes the bridge's end of Pim's socket (`send`, `close`) for a request that passed, and asks the embedder's **`OpenSession`** for a session: it gets only `{ message, closed }` to report what pim-computer says and when its transport ends, and a signal that aborts if the connection is given up first; nothing of the request reaches it. A session is `{ send, close }`: one message to pim-computer, and ending its input. The `Channel` it returns says whether the session opened (`ready`), and settles that false as soon as the connection ends, without waiting for a session still opening; the embedder passes it what Pim's socket receives (`receive`) and when it closes or fails (`end`).
- **`serveWithWebSocketPair(relay, request)`** is the one runtime adapter here, for a Workers runtime (workerd): `check`, then a `WebSocketPair` and `open`, and `101` naming the space back in `x-pim-space` only once the session has opened; `502`, with no socket, when it didn't, or as soon as the connection is replaced or given up while it opens. The request's own signal is the one `open` watches. It is what the tests run.
- **`Lines`** splits a byte stream of pim-computer's `--stdio` output into messages, one per line, for an embedder whose session is such a stream. Each `push` takes at most `MAX_CHUNK_BYTES` (64 KiB, a pipe's read), so what one call decodes and returns is bounded; an embedder that reads more at once hands it over in parts. Both limits (`new Lines(maxChars, maxChunkBytes)`) must be positive whole numbers, and an empty part holds nothing. A larger part, bytes that aren't UTF-8, or a line longer than a message may be throw a fixed error, after which the reader refuses everything and the embedder must end the session. A line not ended when the output ends is dropped. The other way, each message is written followed by `\n`.

What it does with a connection:

- **It carries messages unchanged**, both ways, and makes up none: pim-computer's `hello` and replies come from the session. It doesn't parse them; text that isn't JSON is passed on for pim-computer or Pim to ignore. What pim-computer says while its session is opening (its `hello`) is held by the relay, up to `MAX_OPENING_CHARS` (1 Mi characters, each message counting one more than its length; `maxOpeningChars` changes it), and goes to the client socket in order once the session is open, which must hold it until `101` (a `WebSocketPair` does). More than that ends the connection; if the session doesn't open, what was held is dropped.
- **It ends the connection on what the protocol has no place for**: from Pim, a binary message (`1003`), one over `MAX_MESSAGE_CHARS` (`1009`), one with a line break (`1007`, since a session that is a stream of lines couldn't frame it), or anything before the session is open (`1008`); from the session, anything but text of at most that length on one line (`1011`). JSON from pim-computer has no line breaks.
- **It tries nothing again and keeps nothing.** A message a session's `send` throws on may or may not have reached pim-computer: it isn't sent again, and the connection ends. Nothing is queued across connections; a session's messages after its connection ended go nowhere.
- **One connection at a time, per `Relay`.** A newer connection that passes `check` ends the one before (`4409`, pim-computer's `REPLACED`) and closes its session before asking for its own. A request that failed `check` replaces nothing. Two `Relay`s know nothing of each other, so a bridge must make exactly one for its space, in one place.
- **Ending is once.** Whatever ends a connection first (Pim's socket closing or failing, the session's transport ending, a replacement, Pim giving up while it opens, a session that failed to open) closes the session once, if it has one, and the client socket once. The connection is answered (`502`) without waiting for a session still opening; if that session ever arrives, it is closed at once, once, unused, and no `101` is answered for it. Closing a session ends what the relay sends it, nothing more: it doesn't show that pim-computer has exited, quit its browser, or that nothing else runs on the VM. A new session may be asked for while the one before is still winding down; making that safe on the VM is the embedder's.

Pim's side keeps to its own part: it checks the space, address and token before it reaches the network; puts the token only in the `Authorization` header and never in errors, logs or the space's storage; logs only fixed event names and statuses, never what a failing `fetch` threw; makes one request per connection, aborts it after 30 seconds (`CONNECT_MS`) and closes any socket answered after that unused, and retries nothing, neither the connection nor a message; refuses a message it can't send whole, and anything after the connection ends, by throwing before it leaves; ends the link and tries to close its socket on a socket error, taking nothing from it after, even if the close throws; and calls `closed` once, however the connection ends. A closed socket, like a socket error, says nothing of what the computer did or stopped doing. A message the bridge took is a transport receipt, not a result.

## The bridge's Node host

`computer/cua-host/host.ts` serves a `Relay` over HTTPS and WebSockets on Node 22.18 or later, as `serveWithWebSocketPair` does in a Workers runtime. It is its own package (`pim-cua-host`, in the pnpm workspace), the only one that depends on `ws`; nothing in the Worker or the web app imports it. Importing it does nothing. It starts no process and opens no session: `OpenSession` stays the embedder's, given to the `Relay`.

- **`createHost({ relay, transport, limits, log })`** makes the host; `listen()` serves and answers the address and port; `close()` stops serving and ends every connection, open or opening, which closes its session.
- **`transport`** is `{ kind: "https", cert, key, host, port }`, with the operator's certificate chain and key (PEM), TLS 1.2 or later and HTTP/1.1 only; or `{ kind: "loopback-http", host, port }`, plain HTTP for a TLS terminator the operator runs on the same machine, taken only for a loopback IP literal (`127.0.0.0/8`, `::1`), never a name such as `localhost`, and checked again on the address actually bound. There is no other kind, so plain HTTP is never served on a public address by default or by mistake.
- **For each upgrade request, in order:** the request target must be a canonical path (`/a/../pim` is not `/pim`; an absolute-form target is refused), and `Upgrade`, `Authorization` and `x-pim-space` must each come at most once (`400`); then `relay.check`, given a `Request` holding only those three headers; then `ws` checks the handshake's key and version (`400`); only then `relay.open`. `101` is answered once the channel is ready, with `x-pim-space` naming the relay's space; otherwise `502`, or `504` when the session didn't open within `openingMs`. A request that isn't an upgrade as HTTP has it (no `Connection: upgrade`) is checked the same way and, if the relay would let it through, answered `426`. No answer is a redirect, and none repeats a header, the token, or the space asked for.
- **What Pim's socket does reaches the relay's channel:** text messages go to `receive` as text, binary as bytes (which the relay ends with `1003`); the socket's close, error, or end before `101` (`end`, or the request's signal while the session opens) end the channel once. Bytes sent before `101` end the connection unanswered, with no session asked for.
- **What it holds is bounded** (`limits`, defaults in `DEFAULT_LIMITS`): request line and headers to 16 KiB (`431`); a TLS handshake and headers to `headersMs` (10 s); `maxPendingUpgrades` (4) upgrades checked or opening at once, past which `503` without checking; `maxConnections` (16) sockets; `openingMs` (20 s, under Pim's 30) for a session to open; one message from Pim to 48 MiB (16 Mi characters at three bytes each), no compression; and `maxOutboundBytes` (64 MiB) held for Pim, before `101` and in the socket's buffer after. A message that would pass that limit makes the relay's `send` fail, so the connection ends (`client-send`) and its session closes: a session can't be slowed down, so nothing waits for a peer that doesn't read. Closing handshakes get `closeMs` (5 s).
- **Logs** are fixed: `host.listening`, `host.upgraded`, `host.refused` with a status and a reason (`target`, `headers`, `method`, `upgrade`, `handshake`, `busy`, `early-data`, `opening-timeout`, `session`, `http`, `tls`), and `host.failed`; the relay logs its own. Neither logs an address, a header, or what failed.

The relay's contract is unchanged by the host: one connection at a time (a newer one ends the older with `4409` and closes its session before asking for its own), nothing replayed, no `hello` or reply made up. A socket closing, or the network failing, ends a connection and closes its session as far as the relay is concerned; it says nothing of whether pim-computer, or anything else on the VM, has stopped.

To embed it, an operator's program makes the relay with its own `OpenSession` and serves it:

```ts
import { readFileSync } from "node:fs";
import { Relay } from "../cua-bridge.ts";
import { createHost } from "./host.ts";

const relay = new Relay({ space: "o_…", token: readFileSync("/etc/pim-bridge/token", "utf8").trim(), path: "/pim", open: openSession });
await createHost({ relay, transport: { kind: "https", cert: readFileSync("/etc/pim-bridge/cert.pem"), key: readFileSync("/etc/pim-bridge/key.pem"), host: "0.0.0.0", port: 8443 } }).listen();
```

Its checks (`pnpm typecheck` and `pnpm test` run them too):

```sh
pnpm install --frozen-lockfile
pnpm --filter pim-cua-host typecheck   # tsc against Node's types
pnpm --filter pim-cua-host test        # node --test over loopback sockets; needs openssl
```

The tests (`computer/cua-host/test/host.test.ts`) are real Node network tests, not workerd: a Node HTTPS server on 127.0.0.1 with a certificate `openssl` makes for the run (deleted after), and `ws`'s client or raw TLS sockets writing HTTP by hand. Sessions are made in memory by the test and run nothing. They show refusals (`401`, `403`, `404`, `405`, `400`, `426`, `431`, `503`) with no session asked for and nothing reflected; `101` with the space named back, the session's `hello`, and a call and its reply unchanged; replacement; a session still opening given up by Pim or by `openingMs`, and closed once, unused, when it comes late; `502` for one that fails; binary, line-broken and oversized messages ending the connection; a peer that doesn't read getting its connection and session ended while one that reads keeps it; and plain HTTP refused off loopback. The relay's own tests (`test/cua-bridge.test.ts`) still run in workerd. Neither reaches a Worker: how Pim's deployed `fetch` meets this host over the internet, and a real certificate, are untested.

## The bridge's credential boundary (design, not built)

The bridge's token and TLS key must be out of the desktop user's effective reach, not merely out of its environment. The design for review, which nothing here builds:

- **A bridge account** (say `pim-bridge`, no login, no sudo) owns the token and key files (`0600`, in a `0700` directory it owns) and runs the host. Its program and configuration are owned by root and not writable by either account. As another, unprivileged user, the desktop user can't read its files, its `/proc/<pid>/environ` or memory, or trace it (with Yama's `ptrace_scope` at 1 or more, and no shared group).
- **The desktop account** (one shared, non-root user that every agent of the space runs as) runs a fixed local session endpoint: for each connection on a Unix socket at a path the operator sets (say `/run/pim-session/session.sock`, in a directory the desktop user owns, the socket `0660` with a group whose only other member is `pim-bridge`), it starts `pim-computer --stdio --root <folder>` and carries its lines both ways, ending its input when the connection closes. The endpoint may check its peer's uid (`SO_PEERCRED`) is `pim-bridge`.
- **The host's `OpenSession`** connects to that socket, writes each message and `\n`, and reads lines back with `Lines`. Only pim-computer's messages cross it: the relay hands `OpenSession` nothing of the request, so the token and the space's header stop at `check`, and never reach the endpoint, pim-computer, or the desktop user.

What it doesn't change: every agent of the space shares the desktop account, with no isolation between them; anything running as the desktop user can use the endpoint as freely as the bridge does, which gives it nothing it didn't have; root on the VM, and whoever runs the VM, see everything. Building the endpoint, the accounts, the services and their confinement, and checking the boundary on a real VM, are later stages.

## Choosing Cua for a space

The choice is the operator's, and is kept in two places, neither of which anything in Pim writes:

- **The space's marker.** The space's own metadata (`pim_meta`), key `computer_provider` (`PROVIDER_KEY`), holds exactly `{"provider":"cua","space":"<owner>"}`, where `<owner>` is that space's owner ID. No route, tool or setting creates, changes or removes it; Pim only reads it, on every use. Anything else stored under that key (not JSON, another provider, another space's ID, any other field) is **unreadable**: the space then uses no computer at all, not the default. Pim never infers the marker from anything else, such as a Sprite's machine name or a bridge in the secret below.
- **The bridge, in a Worker secret.** `CUA_BRIDGES` (`wrangler secret put CUA_BRIDGES`, or the dashboard) holds every Cua space's bridge, by owner: `{"o_…":{"url":"https://bridge.example/…","token":"…"}}`, each entry with exactly `url` and `token`. Pim takes the entry for the space asking, and only that one, binds it to that space, and checks it further when it connects (HTTPS, no credentials, query or fragment; a well-formed token). The secret is never stored in the space, the marker never holds it, and neither its address nor its token appears in an answer, a status, a tool's text, an error or a log: a missing or unreadable entry is refused with one fixed message and logged as `cua.unconfigured`. A bridge in the secret chooses nothing: a space without the marker ignores it.

The operator writes the marker before the space first runs, or restarts the space after, since the space sets up its agents' tools when it starts (file, shell and browser tools while it has a computer; no `generate_image`, which saves to files, on an operator's computer). What reaches the computer doesn't wait for a restart: the marker and the secret are read again right before every send (see "Checked right before every send").

A space with the marker keeps it, whatever the secret holds: with no usable entry, every request that would reach the computer is refused before anything is sent, and nothing falls back to a paired computer, a Sprite, or another space's bridge.

## What reaches an operator's computer

- **Agents' requests, only as the control state admits them.** Every agent path that reaches the computer goes through `#controlled` (`src/pim.ts`): approved `shell`, `file_delete`, `browser_click` and `browser_type`, the file tools and the browser tools. On an operator's computer it refuses unless the space's control state is enabled and admits the request under the agent's current lease (see `docs/computer-control-state.md`): with no control state, a damaged or blocked one, the person in control, or an approval not filed under the current lease, nothing is sent. The approval gates are unchanged: an approved action is dispatched once, after its decision.
- **`Computer.call` refuses everything else.** On an operator's computer, a call outside an admitted request is refused before anything is woken or sent, unless it is one of the person's reads below. That covers Pim's other uses of the person's files, which aren't admitted requests: an agent's icon or skill read from files, an artifact made from a file, an app tool's `save_to`, and moving files a space kept before files moved to the computer (which an operator's computer never does). They fail with that refusal.
- **Waking.** A call that finds the computer asleep connects through the bridge (`Cua.connect`), once, and the space lets go of it after five idle minutes, as for a Sprite. A connection that fails, is refused or times out sends nothing, so an admitted request is settled `rejected`; a call sent and unanswered when the connection ends is `unknown`, blocks the control state, and is never sent again.
- **Checked right before every send.** Each link (to a Sprite or a bridge) remembers, in memory only, what it was made under: paired computers and Sprites, or the operator's bridge by its address and token as the secret named it then. Right before a call or a DevTools message is sent, after any wait (waking, a bridge's handshake), Pim checks the marker, any paired computer or Sprite on record beside it, and that the secret still names that same bridge for the space. A call that finds the link made under another choice or bridge lets it go and connects anew under the current one; one that finds it so after its own wait sends nothing and is refused. A DevTools message that fails any check is not sent, and the browser's connection ends, so puppeteer stops waiting on it. So a warm Sprite link, its browser, or a warm bridge link sends nothing once the marker is stored, unreadable or in conflict, or the secret's entry is gone, unreadable or another. Provider identity is not fixed for the space's lifetime; the check is application state, not a fence on the VM. `GET /computer` reports the transport, so a link that no longer holds can show `online` until the next send lets it go.
- **Nothing of a paired computer or a Sprite.** A paired computer's connection is never used in place of the operator's computer, and a paired computer can't connect (`/api/computer/connect` answers `409`); one connected from before is closed (`4409`) on its next message, and nothing it says is taken. While a paired computer's token, or a Sprite Pim started, is still on record beside the marker, every call is refused (`409`) and neither is touched: Pim doesn't forget the token or remove the Sprite to resolve it. The operator does.

## The person's direct routes

No person's input reaches an operator's computer. These are what the person's own routes do there:

| Route | On an operator's computer |
| --- | --- |
| `GET /computer` | `{ state, managed: false, pairedAt: null, computer, provider: "cua", startable: false }`: `computer` is what the operator's pim-computer said when it last connected, never a paired computer's; `provider` is `"unreadable"`, with `computer: null`, when the marker can't be read |
| `POST /computer` (pairing or starting), `DELETE /computer` | `409` before anything changes: Pim doesn't start, pair, replace or remove the operator's computer |
| `GET /files`, `GET /files/content` | **Allowed**, as the person's reads (`asPersonRead` in `src/computer.ts`), which may wake the computer through the bridge. A person's read may make only `stat`, `read`, `readdir` and `browser_status` calls, which change nothing there; a large file's later parts are read as part of the same read |
| `PUT /files/content`, `DELETE /files` | `409`, nothing written or deleted |
| `GET /browser` | `takeOver: false`. Reading the page, or `GET /browser/screenshot`, is **allowed** only while the browser's DevTools connection is already open from an agent's admitted request; puppeteer's own messages to read the page or take its picture are sent then. Otherwise it is refused (`409`) without starting or connecting the browser |
| `DELETE /browser` | `409`: closing a window is input, and nothing is sent |
| `GET /browser/live` | Refused before it watches: an `error`, then `4005`, whether or not the control state is enabled, damaged or missing; one open from before is ended on its next message |

These are application paths. Refusing them doesn't show that nothing else drives the VM or its browser: the bridge, the operator, and whatever runs as the desktop user there are outside Pim.

## Lifecycle is the operator's

Pim doesn't create, start, stop, replace or delete an operator's VM, and never calls Sprites for a space with the marker. Erasing such a space lets go of the bridge's connection and sends nothing to the VM, nor to any Sprite still on record; it logs `{"event":"cua.erased","owner":…,"sprite":…}` (the Sprite's name, or null) so the operator can clean up. **The operator must remove the VM, its bridge, the space's `CUA_BRIDGES` entry, and any such Sprite, when a space is erased or stops using Cua.** Nothing switches a space between providers.

## What is not done

- **The operator's tooling.** Writing the marker, enabling the control state and giving the agent a lease are outside this repository; only tests do them here. Human takeover stays unavailable.
- **The bridge itself** is not in this repository, only its relay (`computer/cua-bridge.ts`) and a Node host that serves it (`computer/cua-host/host.ts`, above). Missing are the session it opens (the local session endpoint and its `OpenSession`, pim-computer started as the desktop user, kept from the bridge's own token and control state, and its stopping and restarting), the accounts and confinement of "The bridge's credential boundary", and the host's packaging, installation, configuration, certificates and deployment. Nothing here has run against a real bridge or a real Cua VM; the host's tests serve only loopback clients in the same process, with in-memory sessions: Pim's tests answer `fetch` in the same process, with a `WebSocketPair` and pim-computer's own `Link`; the relay's tests (`test/cua-bridge.test.ts`) put the relay's Workers adapter behind that `fetch`, with sessions made in the test from `Link` over a test folder, whose commands run nothing, or from nothing at all. How a deployed Worker's `fetch` upgrades, times out and aborts against a real bridge is untested. That Workers expose the `101` response's `x-pim-space` header to `fetch` is assumed from the platform, not tested against it; if they don't, every connection is refused.
- **Versions.** A Sprite fetches pim-computer from its Pim each time it starts; the bridge's operator must keep its copy in step.
- **Control and takeover.** A Cua VM is a whole desktop. Nothing here shows that a person's input there is quiescent or exclusive, so human takeover stays unavailable, as in `docs/computer-control-state.md`. Local transport tests say nothing about what else drives the VM.

## Application qualification against the relay

`test/cua-relay-qualification.test.ts` joins Pim's real selection and admission (the Durable Object's marker and `CUA_BRIDGES` reading, `Cua`, `#controlled` and the control coordinator) to the relay, with an injected `fetch` answered by `serveWithWebSocketPair` and in-memory sessions. It shows, for the application only:

- A valid marker, a matching secret and an admissible lease (seeded by the test; nothing in Pim does it) send one command to exactly the matching owner's session, and none to another space's.
- With no control state, a damaged one, or the person in control, there is no connection at all. With a lease but another owner's address or another token, the relay is connected to and refuses (`403`, `401`): no session is opened and no command is sent.
- A session that gets a command and ends without answering leaves it `unknown` and the control state blocked; a later request connects, sends and falls back to nothing, and neither a paired computer nor a Sprite is recorded or reached.
- Neither token, nor the bridge's address, appears in the public routes, the control state, the space's storage or what was logged; no takeover is offered, and `inputQuiescence` stays `"unproven"`.

What it does not show: a real network upgrade, a VM, a host adapter or session launcher, or that anything stopped on a machine. Its sessions run no process. It can't restart the Durable Object: "reconstruction" is the control state read anew from what the space stored (the helper `cua.test.ts` also uses), so the restart of the whole object, and with it the relay's own state, is not exercised.
