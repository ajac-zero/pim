# The Cua stand-in lane

The Cua stand-in lane is one Vitest configuration, `vitest.cua-standin.config.ts`, that runs the Cua transport, bridge and relay, control state, runtime and viewer, and preview-fixture tests together, one file after another. Every computer, bridge, browser and model in it is a stand-in in the test's own runtime: pim-computer's `Link` over a folder in the runtime's temporary file system, a fetch or `WebSocketPair` that answers as a bridge, `fakeChrome`'s in-process DevTools peer, and pi-ai's faux model. It is for qualifying Cua's combined behavior without the tests' Chrome. It isn't the whole Worker suite (`vitest.config.ts`), which still runs every file, the ones that use Chrome included.

The six native-handler tests were in `test/computer.test.ts`, whose other tests use the tests' Chrome; they are in their own file, unchanged, so the lane can run them without it. The whole suite runs them as before.

## How it keeps out the tests' Chrome

- **No Browser Run binding.** The lane's Worker has no `browserRendering`, so there is no `BROWSER` binding. `testBrowser` (`test/helpers.ts`) throws when called without one, before it connects to anything, and the lane's setup file (`test/standin-lane.ts`) fails every file before its tests run if a binding ever appears.
- **Files checked before anything runs.** Loading the configuration reads each listed file, and refuses to run if one names `testBrowser`, `pairTestComputer`, `BROWSER`, `browserRendering`, `PIM_LIVE` or `test/live/`.
- **No live mode or remote bindings.** `PIM_LIVE` set at all stops the lane before it runs; `remoteBindings` is off, as in the whole suite.

## What the listed files reach

Checked by reading the files and what they import, not by running them:

- They import `test/helpers.ts`, `test/worker.ts`, `test/waits.ts`, `src/`, `preview/worker.ts` and `preview/cua-fixture.ts` (through `test/worker.ts`), `computer/pim-computer.ts`, `computer/cua-bridge.ts` and `computer/native-outcome.ts`. `computer/cua-bridge.ts` and `computer/native-outcome.ts` import nothing.
- None calls `testBrowser` or `pairTestComputer`, and `src/` names no `BROWSER` binding.
- pim-computer starts processes (`runCommand`) and its own Chrome (`localBrowser`) only from `main`, which runs as a program and not when tests import `Link`. A `Link` given no browser answers browser calls with `ENOSYS`; the tests' machines run commands through the stand-ins they're given.
- Requests outside the runtime: `test/cua.test.ts`, `test/cua-relay-qualification.test.ts` and `test/preview-cua-fixture.test.ts` replace `fetch` and fail a test that reaches anything but their stand-ins. The other files don't replace it; read as written, their requests go to the Worker itself (`exports.default.fetch`, test computers' sockets), and their `browser_open` URLs to `fakeChrome`. The lane doesn't block the network itself, so code that reached it unexpectedly would, as in the whole suite.
- Files are written through `node:fs` in workerd, whose `/tmp` is the runtime's own.

## Running it

It needs the Node and workerd infrastructure Vitest's Workers pool starts, the same as the whole suite, and is run only once authorized after review. The commands:

```sh
node_modules/.bin/vitest run --config vitest.cua-standin.config.ts   # the lane: 193 tests expected
node_modules/.bin/tsc --noEmit                                       # types of src/ and test/
```

The configuration files at the root (`vitest*.ts`) aren't in `tsconfig.json`'s `include`, so `tsc` doesn't check them.

### Runs so far

- **At `876b773`, once, by the reviewer, without `tsc`:** exit 1, 143 of 144 passed, 8 of 9 files, in 131 s; `test/waits.test.ts`'s nine passed. The one failure was `test/computer-control-runtime.test.ts`'s "fails closed when checking a native reply throws": the call settled with the computer's outcome, where the test expects the error a failed check gives (`[message, undefined]`, received `false`).

  The throwing check was not triggered, read from the source: `Computer.native` always sends `NATIVE_TOOL_OP`, so its reply always goes to `#nativeReply`, which settles a check that throws as the test expects; only a check that returned an outcome resolves the call. No other code calls the check between the test setting it and its reply: a space's own `Computer` is made without `nativeApps` and sends no native-app call. And the throwing implementation was never used at all: `vi.restoreAllMocks()` after each test restores only `vi.spyOn` spies, so it stayed queued, and the next test, "binds a native call to the admitted request and the space", whose replies must be outcomes, passed. So `src/computer.ts` called a `readNativeOutcome` other than the one the test set: the real one, or a copy of the mock wrapping it, which read the valid reply as it should.

  How that can happen, not shown by the run: a module evaluated in a file's run before that file's `vi.mock` is registered keeps its real imports. Vitest resets modules before each file, but every event a Durable Object gets runs through the plugin's wrapper, which imports the Worker (`test/worker.ts`, and with it `src/computer.ts`) through the same module runner, so a Durable Object of an earlier file that wakes in that window leaves the real check in place for the whole file. The lane's setup file imports only `cloudflare:test`, but loading it is more waiting in that window. Which object woke, if one did, isn't known.

  The test now clears the module registry before its mock is registered and before anything in the file is imported, and, before its other assertions, which are unchanged, checks that the throwing check read this reply (its last call was with the reply's result, and threw). A run where the mock again doesn't reach the space's code fails there, saying so. Not run since.

## Waits and what a test starts

`test/waits.ts` records, for setup and for each test, which waits are open and how long finished ones took. A failed test prints them on one line of JSON, as they stood when it ran out of time if it did; setup that never finishes prints its own from `afterAll`. Labels are the tests' words and requests' methods and paths, with IDs and token-like words replaced and the length bounded.

**Ownership.** Each setup (`setup` in `test/helpers.ts`, around a `beforeAll`), each test and each test's cleanup has its own scope, which owns the code it runs through the runtime's async context (`AsyncLocalStorage`). A test's scope is made by an `aroundEach` hook in `test/helpers.ts` before its `beforeEach` hooks and owns them, its body, its `afterEach` hooks, and every promise continuation and timer callback they lead to, whenever those run. `waits()` gives the scope that owns the code running now, and throws in code no scope owns. So a continuation of a test that ran out of time, resuming after the next test began, asks its own test's scope, which refuses it; it never gets the next test's.

**Starting.** Watching changes nothing. Where a test's work must not start after the test has run out of time, it goes through `waits().start`, which takes the work as a function and doesn't call it once the test's signal has aborted or its scope has closed; the function runs as that scope's own. Work already started is not stopped, only tracked. In `test/cua.test.ts` every request, step inside the space and model turn (the faux model's answers are set as the turn starts) starts that way, and the bridge's gates (`hold`, `handshake`) are the test's own (`waits().gate`).

**Settling.** After each test, its scope closes first, so nothing more starts in it and the tasks it waits for can't grow: a task that asks for more work while the test settles is refused. Then its gates are opened and every task it started must finish within four seconds. Then the cleanup the test registered with `waits().defer` and didn't dismiss runs, last registered first, whether or not the test ran out of time and whether or not its tasks finished, in a cleanup scope that admits only that cleanup's work; it and what it started must finish within four more seconds. The test fails naming every task or cleanup not seen to finish, and every cleanup that failed. The handshake race test registers undoing its change that way, and undoes it itself and dismisses the cleanup when the iteration ends normally.

That only says those tasks and that cleanup finished: a socket is counted closed when its close event is seen, and nothing here shows that the space, or anything else, is idle. A stale continuation that changes shared state without starting work through a scope, such as assigning a fixture variable, isn't held back; the race test clears only its own gate for that reason.

**What one run shows.** That workerd carries the async context into promise continuations and timer callbacks, and that Vitest runs a test's hooks and body inside its `aroundEach` hook's call, were taken from their documentation and source. The one run above is evidence for both, not proof: `test/waits.test.ts` checks the first, and passed; `test/cua.test.ts`, whose every request and turn goes through `waits()`, passed, where code run unowned would have failed at `waits()` rather than start anything. `src/` already relies on the same `AsyncLocalStorage` in workerd.

## What it doesn't settle

The lane leaves out the files that use the tests' Chrome, and every other file of the Worker suite, so a clean lane says nothing of them. The intermittent timeouts seen in whole-suite runs (`test/cua.test.ts`'s handshake race and approval wait, and `test/background.test.ts`'s shared setup) are not diagnosed; the waits above are there to name where such a stall is when it happens again.
