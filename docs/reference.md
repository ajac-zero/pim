# How Pim works

The details behind the [README](../README.md): what Pim is made of, how to deploy and run it, its API, and how each part behaves.

**Vocabulary:** Pim is the platform; a space is one person's own part of it, with their agents, conversations, memories and files; an agent is what you create and chat with; a template is an agent shared through the gallery; an app is what an agent builds that people use, with every version kept (Pim Apps); a connector is a service an agent works with, such as Gmail.

This repository is the agent, its API, and its web app ([`web/`](../web)): chat, approvals, notifications and settings, signed in with a passkey, or with Google, GitHub or your own single sign-on when you set those up. One Worker serves all of it, for everyone, at one address. Mobile apps and messaging bridges can use the same API with an API token, and Claude, ChatGPT and other MCP clients can talk with your majordomo at `/mcp` (see [Talking with Pim from other apps](#talking-with-pim-from-other-apps)).

## Chats

A chat with no activity for 72 hours, and nothing unread or running, folds into Inactive, closed by default between the dated chats and Archived. A chat with no activity for two weeks moves to Archived, folded at the bottom of the chat list, so the list holds what's current. Until then, chats sit under dividers for today, yesterday, last week and the last 14 days. It is not deleted: search finds it, it opens as before, and sending it a message brings it back. A chat with an unread reply, or one still working, stays in the list. Archive in a chat's options menu moves it there at once, whatever its age; sending it a message brings it back.

When the model fails and a few automatic retries don't help, such as when a plan's usage runs out with no other model to go to (see [ChatGPT plan](#chatgpt-plan)), the chat doesn't give up: it holds the run where it stopped, however long that takes, and shows the problem with **Try again**. That asks the model again with whichever model the agent has then, so switching models or waiting for a limit to reset both work, and the answer carries on from the same place. Stop ends the held run instead. An agent can also have **fallback models** (Agents → the agent → Models): when its model fails for good, the run moves on to the next one in the list and carries on from the same place, and only when every model has failed is it held. Each new message starts on the agent's own model again, so a quota that has reset is used again. A task handed to an agent has no one watching it, so without a fallback it isn't held: it fails, and its requester is told.

A chat can't be held up for good. Stop always works: it tells every call of the run to stop, including one that never returns and a wait for your decision, and answers within a few seconds even if one is slow to end. What was queued for the agent by Pim, such as a coding thread's turn ending or a task's answer, isn't withdrawn with your own queued messages: the agent reads it in its next run. A run that makes no progress at all for thirty minutes (no output, no new step, no commit) is stopped the same way, with a note to the agent; a wait for your decision, or for a retry, is not a lack of progress. When the space restarts, a tool call whose approval was decided just before is woken at once, and an approved action that was running then is not run again, but its result says it may have partly run.

**Copy conversation as Markdown** in the chat's options box (the button at the right of its header) copies the conversation as Markdown, with separate headings for the user, the named agent and system notices. It becomes available when the chat finishes loading and the agent finishes replying. Message formatting stays intact; attached images are marked with a placeholder, and private reasoning and tool activity are left out.

**Fork from here**, under any of an agent's messages, opens a new chat with the same agent that has the conversation through that message, and leaves the chat it came from as it was. **Edit**, under one of your messages, changes what you said: the changed message, with its images, goes in a new fork of the chat up to just before it, which opens. The chat it came from stays in the list as it was. A fork is titled like its chat with a number, as "Trip (fork #2)", until you say something in it; then the utility model names it again from the conversation, by its latest messages. A fork starts afresh with the chat's tasks, schedules, public link and cost: they stay with the chat they belong to. A group chat and a chat with someone else's agent can't be forked. The images sent in a chat are kept while a fork of it is.

**Public link**, below it in the box, makes a public link to the chat: a copy of the conversation as it is then, which anyone with the link can read at `/shared/<owner>/<link>`, without an account. The copy is what you read in the chat: your messages and what the agent sent you, with the widgets that went with them as they were. The images you attached, Pim's own notices, private reasoning and tool activity are left out, and so is everything said after it was made. **Update to include new messages** copies the chat again under the same link. **Turn off link**, deleting the chat, or deleting the account makes the link answer `404`; a browser that read it in the last minute may still show its copy. The page asks search engines not to index it, and shows the copy as untrusted text: no images load, no HTML runs, and links go only to web and mail addresses. A chat with someone else's agent (a visit) can't have a link.

## How it works

```
 Browser, bot, app                        Cloudflare
┌─────────────────────┐   HTTPS / WS   ┌──────────────────────────────────────────────┐
│ web app, or REST +  │───────────────▶│ Worker (src/index.ts, src/gateway.ts)        │
│ WebSocket at /api;  │                │  ├ /*       the web app (web/, static files) │
│ MCP clients at /mcp │                │  ├ /auth/*  joining, passkeys, Google/GitHub │
└─────────────────────┘                │  ├ /mcp, /oauth/*  the majordomo over MCP,   │
                                       │  │          and its OAuth (OAUTH_KV)         │
                                       │  └ /api/*   whoever the session or token     │
                                       │   │         names                            │
                                       │   ▼                                          │
                                       │ Durable Object "Pim" (src/pim.ts), one per   │
                                       │ person, named by their owner ID              │
                                       │  ├ PiHarness ── pi-durable runs, tasks, inbox│
                                       │  ├ Extensions: optmem, goals, schedule,      │
                                       │  │   messaging, approvals, web               │
                                       │  ├ Scheduler (alarms) ── background wake-ups │
                                       │  └ SQLite: pi's tables + pim_* tables        │
                                       │        │                                     │
                                       │        ▼                                     │
                                       │ Workers AI / AI Gateway (env.AI)             │
                                       │                                              │
                                       │ "Auth", one per person: sign-ins, tokens     │
                                       │ "Directory": accounts, the admin, invites    │
                                       │ "Gallery": profiles, published templates     │
                                       └──────────────────────────────────────────────┘
```
- **[pi-durable](https://github.com/earendil-works/pi/tree/main/packages/durable)** runs the agent. Every model turn and tool call is a durable task committed to the Durable Object's SQLite before anything is shown. If the object is evicted mid-run, the `agents` SDK's `PiHarness` alarm wakes it, and pi resumes where it stopped.
- **One space per person.** The Worker reads whose request it is from the browser's session or the API token, and sends it to that person's Durable Object, which holds their memory, connectors and agents in its SQLite database. A URL never chooses whose space answers. See [docs/instance.md](instance.md).
- **The app opens from the device.** Its service worker (`web/public/sw.js`) keeps the page and the files it starts with, so the app opens without waiting on the network, and fetches the page again in the background. A newer page is kept only once every file it starts with is, and a page opened from the older app moves to the new one by reloading within its first ten seconds; after that the next visit gets it. The lists the app's frame shows, such as chats, agents and approvals, are kept in the browser's IndexedDB by build (`web/src/lib/saved-queries.ts`), so the app draws them at once and refreshes them as it opens; signing out forgets them. The built files are named by their content and cached for good (`web/public/_headers`), and `/api/themes.css` answers "not modified" until a deploy changes it.
- **A model that can do the job.** Pim decides what to say and when, and says it with a tool call, so it needs a capable model. The default is GLM-5.3 on Workers AI (`@cf/zai-org/glm-5.3`), billed to your Cloudflare account, with no vendor keys. Any AI Gateway catalog model works too, such as `anthropic/claude-opus-4.8` (set `PIM_MODEL`), or OpenAI's through your ChatGPT plan, or any model on a server that speaks OpenAI's chat completions, which you or the admin add in Settings (see [Model providers](#model-providers)). Each agent has its own model, chosen from the model's logo beside the send button in its chats. An agent that hasn't one follows the default model, which is the deployment's unless the person chose another in Settings → Model.
- **Your ChatGPT plan**, optionally. Sign in with ChatGPT (Plus or Pro) and Pim runs on OpenAI's models, such as GPT-6.1 Sol, using the plan's included usage. See [ChatGPT plan](#chatgpt-plan).

## Deploy

Pim's Durable Objects run on the Workers free plan, but the default model, GLM-5.3 on Workers AI, needs the Workers Paid plan or prepaid AI Gateway credits. For a free first look, set `PIM_MODEL` to `@cf/zai-org/glm-4.7-flash`, which runs on Workers AI's daily free allocation but is not good enough for real use; or connect a ChatGPT plan in Settings.

Images people send in chats and skills' files are kept in one R2 bucket, and apps' files in another (people's own files are on [their computers](#your-computer)); deploying creates both. R2 has to be turned on for the account first: in the dashboard, open Storage & databases, then R2, and add the R2 subscription. Its free tier covers 10 GB, but Cloudflare asks for a payment method.

[![Deploy to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https://github.com/ajac-zero/pim)

The button copies this repository to your GitHub account and deploys it to your Cloudflare account. It asks for nothing. Then open the Worker's `workers.dev` URL, which the deploy shows: Pim asks for its address, `PIM_PUBLIC_URL`, before anything else. Pim answers only there, and passkeys belong to it, so choose the one you'll keep: the `workers.dev` URL, or a custom domain you attach to the Worker first. Add it in the dashboard (Workers & Pages → `pim` → Settings → Variables and Secrets), open it, give your name (your username is made from it, such as `grace-hopper`, and Change picks another), save your recovery codes and create your passkey: your face, fingerprint, or PIN. You're the admin of this Pim. That's the whole setup.

- **The first account** can be made that way for 15 minutes after a deploy, and it is the admin's. Until you make it, whoever opens the URL first could, so open it right after deploying. Missed the 15 minutes? The sign-in screen has the Worker write a one-time setup link to its logs, which only someone signed in to your Cloudflare account can read. In the dashboard, open Workers & Pages, then `pim`, then Observability, and open the link in the log that starts with "Pim setup link". It works once, for an hour.
- **Inviting people.** Settings → Members → Invite someone makes a link that lets one person join. With `PIM_REGISTRATION` set to `open`, anyone who finds the address can; `closed` lets nobody in. A [bot's public link](#public-bots) lets anyone join as a guest whatever this says, within `PIM_MAX_ACCOUNTS` and `PIM_REGISTRATIONS_PER_ADDRESS`.
- **More passkeys** (your phone, another browser) come from Settings.
- **Google, GitHub or single sign-on** (optional). Passkeys always work, and need no setup. To let people also sign in with Google, GitHub, or any OpenID Connect provider (Microsoft, GitLab, Authentik, Keycloak, Pocket ID...), make an OAuth app there and add its client ID and secret as the Worker's secrets: in the dashboard (Workers & Pages → `pim` → Settings → Variables and Secrets) or with `wrangler secret put`. They work once saved, with no redeploy. Google takes `PIM_GOOGLE_CLIENT_ID` and `PIM_GOOGLE_CLIENT_SECRET`; GitHub `PIM_GITHUB_CLIENT_ID` and `PIM_GITHUB_CLIENT_SECRET`; single sign-on `PIM_OIDC_ISSUER`, `PIM_OIDC_CLIENT_ID`, `PIM_OIDC_CLIENT_SECRET`, and optionally `PIM_OIDC_NAME` for its button. The app's callback URL is `https://<your Pim>/auth/oauth/<google|github|oidc>/callback`; Settings → Members shows it, and which providers are on. People then link that account in Settings, or use it instead of a passkey when they join. It never makes an account by itself: someone who never joined, or never linked that account, isn't let in. An account at a provider signs in to one person on the Pim, matched by the provider's user ID, not by email.
- **Lost every passkey?** Each person got ten recovery codes when they joined; one, with their username, adds a new passkey. The admin can make anyone a setup link in Settings, and gets one for themselves from the logs, as above.

Sessions last 30 days, and removing a passkey, or unlinking an account, signs out the browsers it signed in. API tokens for other clients are made in Settings (`POST /auth/tokens` from a signed-in browser) and revoked there. Passkeys belong to the hostname the app is served from, so moving Pim to another domain means creating new ones.

Or from a checkout:

pnpm wrangler login
pnpm run deploy        # builds web/ first

Pim comes with 38 connectors ([`popular-apps.ts`](../src/extensions/popular-apps.ts), [`spotify.ts`](../src/extensions/spotify.ts), [`gmail.ts`](../src/extensions/gmail.ts), [`google-drive.ts`](../src/extensions/google-drive.ts)): Airtable, Amp, Atlassian (Jira and Confluence), Attio, Cal.com, Calendly, ClickUp, Cloudflare, Context7, Exa, Firecrawl, Fireflies, GitHub, Gmail, Google Drive, Granola, Hex, Hugging Face, Intercom, Jotform, Klaviyo, Linear, Make, Mercury, Miro, monday.com, Neon, Netlify, Notion, PayPal, PostHog, Sentry, Spotify, Stripe, Supabase, Todoist, Webflow and Wix. All but four work as they are. Four need secrets of your own, set with `wrangler secret put`; until they are, nobody is offered the connector, and its actions say which are missing (by name, never value):

- **GitHub**: `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET`, from an OAuth app at [github.com/settings/developers](https://github.com/settings/developers) whose callback URL is `https://<your Pim>/mcp/callback`. GitHub's MCP server doesn't let apps register themselves, so Pim signs everyone in with this one.
- **Spotify**: `SPOTIFY_CLIENT_ID` and `SPOTIFY_CLIENT_SECRET`, from an app at [developer.spotify.com](https://developer.spotify.com/dashboard) whose redirect URI is `https://<your Pim>/mcp/callback/apps`.
- **Gmail** (search and read mail; never sends, drafts, labels or deletes, and never downloads attachments): `GOOGLE_GMAIL_CLIENT_ID`, `GOOGLE_GMAIL_CLIENT_SECRET` and `APP_CREDENTIALS_KEY`, as below.
- **Google Drive** (reads only the files each person picks for Pim; never writes, shares or deletes): `GOOGLE_DRIVE_CLIENT_ID`, `GOOGLE_DRIVE_CLIENT_SECRET`, `GOOGLE_DRIVE_API_KEY`, `GOOGLE_DRIVE_APP_ID` and `APP_CREDENTIALS_KEY`, as below.

`APP_CREDENTIALS_KEY`, 32 random bytes in base64 (`openssl rand -base64 32 | wrangler secret put APP_CREDENTIALS_KEY`), encrypts people's sign-ins to connectors Pim implements, such as Spotify, in their spaces. It is optional for those, but Google's connectors aren't offered without it. Keep it: changing or removing it means people connect those connectors again.

Google's connectors (see [Google connectors](extensions.md#google-connectors)) each need an OAuth client of their own, in a Google Cloud **project** of their own: Google keeps a person's grant per project, every client in a project shares it, and revoking it (which disconnecting does) revokes the tokens of every client in that project. Separate clients in one project are not enough. So use one project for Gmail, another for Drive, and neither for Pim's own Google sign-in (`PIM_GOOGLE_*`). Pim checks: a sign-in whose grant holds more than the connector asks for (because its project serves something else too) is refused, and left unrevoked so the other grant survives. In the [Google Cloud console](https://console.cloud.google.com/), for each connector:

1. Make a project for it.
2. Enable the API the connector uses: the Gmail API; or the Google Drive API and the Google Picker API.
3. Set up the OAuth consent screen (Google Auth Platform → Branding, Audience, Data access): the app's name, support email, your Pim's domain, and the app's scope: `gmail.readonly` for Gmail, `drive.file` for Drive. Who may sign in, and for how long, is Google's to decide by the app's user type, publishing status and verification, and its rules change; check [Google's overview](https://developers.google.com/identity/protocols/oauth2/production-readiness/overview) for your case. As Google describes them now: an **Internal** app (a Google Workspace organization's own) is open to that organization's users and isn't verified. An **External** app in **Testing** is open only to the test users you list (at most 100), and their sign-ins expire after 7 days, after which they connect again. A **published** External app that asks for a sensitive or restricted scope, unverified, shows people an unverified-app warning and is capped at 100 users; `gmail.readonly` is restricted, so verifying Gmail involves a security assessment, while `drive.file` is not a sensitive scope. Pim doesn't change any of this.
4. Make an OAuth client (Clients → Create client) of type Web application, with the authorized redirect URI `https://<your Pim>/mcp/callback/apps`.
5. Set its ID and secret as the Worker's secrets: `GOOGLE_GMAIL_CLIENT_ID` and `GOOGLE_GMAIL_CLIENT_SECRET`, or `GOOGLE_DRIVE_CLIENT_ID` and `GOOGLE_DRIVE_CLIENT_SECRET`. Until they and `APP_CREDENTIALS_KEY` are set, nobody is offered the connector.
6. For Drive, the Picker: make an API key in the Drive project (APIs & Services → Credentials), restricted to the Google Picker API and to the website `https://<your Pim>/*`, and set it as `GOOGLE_DRIVE_API_KEY`; set the project's **number** (not its ID, from the project's dashboard) as `GOOGLE_DRIVE_APP_ID`, so Google grants Pim the files people pick. The key is shown to people's browsers, as Google intends, so restrict it. The OAuth client needs no JavaScript origins: the picker gets its token from Pim.

People pick Drive files on Pim's page `https://<your Pim>/app-pages/google/drive` (Drive's tools give its link). It is served under a strict content security policy that lets Google's Picker load, and gets from Pim, only for the browser signed in as the person, the connection's current access token (an hour at most, `drive.file` only), never its refresh token or client secret: the Picker can't run without one. While it lives, that token could read and change the files the person picked for Pim, from that page; the page keeps it in memory only, and Pim never logs it. Pim then checks each pick with Google and keeps only those Google confirms, with their resource keys, encrypted with the credential; the tools read only those, and Google checks each read. Removing a file there only stops Pim reading it.

Disconnecting a Google connector revokes its grant at Google; so does erasing an account. If Google can't be reached then, the person can remove Pim at [myaccount.google.com/connections](https://myaccount.google.com/connections). A grant revoked at Google, or expired, shows the connector as failed in Connectors, to be connected again.

### GitHub for coding threads

A coding thread's workspace never holds a GitHub credential. Its git `origin` is Pim's git broker, `https://<your Pim>/api/coding/git/<owner>/<name>.git`, which it signs in to with a broker token: signed by Pim, bound to one coding session and one repository, and good for an hour unless the session asks for less (12 hours at most). The broker only clones and fetches, through GitHub's smart HTTP protocol. Pushing is Pim's to do, when the person approves it in the app or the agent runs `coding_push` or `coding_merge`: the workspace hands Pim a git bundle of the branch, and Pim sends it to GitHub. Pim pushes to the repository's default branch, `main` or `master`, only to merge a coding thread into it (`coding_merge`, as a fast-forward of the branch), pushes every other branch only if it starts with `pim/`, never rewrites a branch (one that exists only moves forward), and pushes at most 64 MiB at once. See [`src/coding/git-broker/`](../src/coding/git-broker/broker.ts).

Public repositories need nothing more. For private ones, and for pushing, make a GitHub App (Settings → Developer settings → GitHub Apps) with the repository permission **Contents: Read and write** and nothing else, install it on the repositories coding threads may use, and set its ID and a private key of it as Worker secrets: `PIM_GITHUB_APP_ID` and `PIM_GITHUB_APP_PRIVATE_KEY` (the `.pem` file as GitHub gives it). Set `PIM_GITHUB_APP_INSTALLATION_ID` too to use one installation for every repository, rather than the one GitHub finds for each. Until the ID and key are set, the GitHub App is not configured: public repositories still clone, and pushes fail with "GitHub App not configured". Pim gets a token from the App for each repository on its own, with only `contents: read` to fetch, or `contents: write` to push, and keeps it until 5 minutes before it expires.

Coding threads can also work on repositories of one Gitea instance, whose `https` origin (such as `https://gitea.example.com`) is `PIM_GITEA_BASE_URL`, with no default. Pim connects to it as one Gitea account of the deployment's own, through an OAuth2 application (a confidential client) made in that account's Gitea settings, with the redirect URI `https://<your Pim>/api/coding/gitea/callback`. Set its client ID and secret as the Worker secrets `PIM_GITEA_CLIENT_ID` and `PIM_GITEA_CLIENT_SECRET`, then the admin signs in at `/api/coding/gitea/authorize`; `GET /api/coding/gitea/status` says whether Gitea is configured and connected, as which login, and whether it needs a new sign-in (`needsReconnect`, after Gitea refused a token refresh), and `DELETE /api/coding/gitea/connection` disconnects it. The tokens are stored sealed in the Directory, Gitea's rotated refresh tokens included. Until it is configured and connected, a coding thread on a Gitea repository fails with "Gitea not connected", and GitHub is unaffected. Gitea repositories are cloned, fetched and pushed through the same broker, with the account's access token as the git password; a push moves an existing branch only forward, as on GitHub, and the `pim/` prefix and protected branches apply the same.

Two variables, in the dashboard, set the rules: `PIM_GIT_BRANCH_PREFIX`, another prefix than `pim/` for the branches Pim pushes, or `none` for any; and `PIM_GIT_REPOS`, the repositories coding threads may use, such as `acme/*, me/notes`, every one on github.com when unset. A list Pim can't read allows none.

Coding threads work only with repositories on GitHub, and every workspace clones through the broker: a thread refuses any other repository when it starts.

### Model gateway for coding threads

A coding CLI that runs in a thread's workspace, such as Claude Code or Codex, never holds the space's model key either. Pim gives it a gateway token instead (`pimgw_<…>`), with Pim as its provider: `ANTHROPIC_BASE_URL=https://<your Pim>/api/coding/gateway/anthropic` and `ANTHROPIC_API_KEY`, or `OPENAI_BASE_URL=https://<your Pim>/api/coding/gateway/openai/v1` with `OPENAI_API_KEY` and `CODEX_API_KEY`; the workspace's egress then needs only Pim's host. The token is signed by Pim with a key derived from its own (no variable to set), bound to the thread, its space and the provider families it may call, and good for the thread's time limit and 15 minutes more (a week, for a thread with none). Aborting or archiving the thread revokes every token it has.

The gateway forwards only `POST /v1/messages` (with `?beta=true`) and `/v1/messages/count_tokens` to Anthropic, and `POST /v1/responses` and `/v1/chat/completions` to OpenAI, with the space's built-in Anthropic or OpenAI API provider's key (the one the thread runs on, else the person's own, else the admin's). Requests are at most 16 MiB, and each thread may make 120 a minute and have 4 under way; an answer may take 10 minutes to start, go 5 minutes without a byte, and take 30 in all, and a stream that stops ends with the API's own `error` event. Answers come back as the provider sends them, streams included, without the provider's cookies or account headers; an error that repeats the key has it taken out, and a refused key is the gateway's own `502`. Refusals are in the API's own error shape, with an `x-pim-gateway-error` header: `402` once the thread's budget is spent, `429` at a cap.

Each answer's usage, read from the stream as it passes or from the JSON answer, is charged to the thread at pi-ai's catalog prices, as the thread's own model calls are: one `model_call` in its log, and its spend, in one transaction. A model the catalog doesn't know is charged at the family's dearest price, and an answer cut short before it reported usage at a token for every 4 bytes of request and answer. Requests already under way may together spend past the budget. See [`src/coding/model-gateway.ts`](../src/coding/model-gateway.ts).

### Workspaces for coding threads

A coding thread runs its commands in a workspace on a backend the deployment sets up, read from its environment whenever a thread asks, so turning one on needs no flag. The sandbox manager is used when `PIM_CODING_MANAGER_URL` (a variable) and `PIM_CODING_MANAGER_TOKEN` (a secret) are both set; Cloudflare Sandbox, when the Worker has a `Sandbox` binding, which it doesn't today (see [coding-cloudflare-sandbox.md](coding-cloudflare-sandbox.md)). Without a backend, a thread fails with `no_backend` and says what to set; once one is set, continuing the thread uses it. With the sandbox manager, a thread checks the manager's `/health` before it asks its space's scheduler for a slot, and every 30 seconds while it waits in the queue: under 15% of the disk free holds the space's queue, and the manager's own limit caps the space's slots. A workspace refused for low disk holds the queue too, and the thread tries again each heartbeat. See [`src/coding/workspace/registry.ts`](../src/coding/workspace/registry.ts).

### Email

Pim can email each person, when they ask for it or for something worth keeping, such as a report. It's off until you set it up with [Cloudflare Email Service](https://developers.cloudflare.com/email-service/): onboard a domain for Email Sending, then add to `wrangler.jsonc`

```jsonc
"send_email": [{ "name": "EMAIL" }],
```

and set `PIM_EMAIL_FROM` in the dashboard to an address on that domain, such as `pim@example.com`. Each person then adds their address in Settings and confirms it with a code Pim emails there; Pim only ever emails that one address, at most 50 times a day.

### Your computer

Agents run commands and keep files on a machine of each person's own, or the one Pim keeps for them where it has a computer host (see [Computers Pim keeps](#computers-pim-keeps)), which runs [`computer/pim-computer.ts`](../computer/pim-computer.ts): a single file for Node.js 22.18 or later, which the Pim serves at `/pim-computer.ts`. It connects out to the space over a WebSocket, so the machine needs no open port and can sit behind NAT. Settings → Computer makes its token and shows the command that installs it, on Linux or macOS, or the Docker container to run instead:

```sh
curl -fsSL https://pim.example.com/install.sh | sh -s -- computer pimc_…
```

The Pim serves `/install.sh` with its own address in it. It gets Node.js where the machine has none new enough (Node's official build, checked against a checksum the script holds), downloads `pim-computer` into `~/.pim-computer`, and runs `pim-computer install`, which keeps it running as the user's own service: a systemd user service on Linux, which it lets linger so it runs from boot where `loginctl` allows (and says how otherwise), or a launchd agent on macOS. Where there's no systemd for the user, it runs in the background until the machine restarts. Each time the service starts, it gets the Pim's newest `pim-computer` first. A `pim-computer` command, in `~/.local/bin`, manages it: `status`, `logs`, `update` (a restart, with the newest copy) and `uninstall`, which leaves the files. Options after the token, such as `--root` or `--chrome`, are the service's from then on; running the command again sets it up again, and restarts it only if something changed. Or run it in the foreground yourself:

```sh
PIM_URL=https://pim.example.com PIM_COMPUTER_TOKEN=pimc_… node pim-computer.ts
```

It keeps the files in `~/pim` (`PIM_COMPUTER_ROOT` or `--root` sets another folder), and reconnects by itself after a drop. The Docker container Settings shows installs Chromium the first time it starts.

The computer's Chrome is the agents' browser: `pim-computer` finds Google Chrome or Chromium where it's usually installed (`PIM_CHROME` or `--chrome` names another), starts it headless when an agent first needs it (`--headful` shows its window instead), and lets the space drive it over the DevTools protocol through its connection. It starts it with `--disable-blink-features=AutomationControlled`, since Chrome started with DevTools on otherwise tells pages it's automated (`navigator.webdriver`), and Google's sign-in, which "Continue with Google" on other sites goes through, turns such a browser away. Its profile, in `~/.pim-computer/browser`, keeps what you signed in to between runs, including sign-ins that last only for the session. It quits after half an hour with nobody using it. Settings → Computer says when a computer has no browser. A space has one computer: a new token replaces the old one and disconnects it, and removing the computer in Settings forgets its token.

Commands run as the user who started `pim-computer`, with the files folder as their working directory, for up to two minutes unless the agent asks for up to ten; what comes back is the exit code and up to 64 KB of each of its outputs. `shell` is a gated action, so each command asks first unless Settings → Tool permissions sets it to On. File calls never reach outside the folder, through `..` or a link. Anything the user can do, an approved command can, so give it a machine, VM or container meant for it. `pim-computer` also keeps the backends of apps running (calls `app_start`, `app_stop`, `app_status`, `app_logs` and `app_http`, which relays one HTTP request to a backend on the computer's loopback; see [Apps with a backend](apps.md#apps-with-a-backend)); they belong to its process, not to the connection, so they keep running when the space disconnects, and stop when it exits. Files on the computer don't count toward the space's storage. A space that kept files in Pim before this moves them to its computer the first time one connects, renaming any whose name is taken there to `name (from Pim).ext`.

### Computers Pim keeps

Pim can keep a computer for everyone, so nobody needs to bring one: an Ubuntu 24.04 desktop (with Xfce) for each space, which runs all the time and is never removed while its person is here. They run on a machine of the operator's, the **computer host**, where [Cua](https://github.com/trycua/cua)'s `cua` command makes each computer from Cua's own Ubuntu image, which Cua builds as both a VM and a container, for x86-64 and ARM:

- **VMs**, from `ghcr.io/trycua/linux:24.04-disk` with QEMU, where the host can run them: Linux with KVM, or a Mac with Apple silicon (with Apple's Hypervisor.framework). A cloud VM needs nested virtualization for KVM (on Azure, a size whose page says it's supported); a bare-metal machine, such as a mini PC with virtualization turned on in its firmware, has it.
- **Containers**, from `ghcr.io/trycua/linux:24.04` on Docker, where it can't (Linux without KVM). Containers share the host's kernel, so they're lighter and need no KVM, but they can't run Docker inside, and an agent that escaped one would be on the host, with everyone's computers. `pim-host install` picks VMs or containers this way unless `--kind vm` or `--kind container` says which, and keeps what it picked; Settings → Deployment → Computers shows which. Each computer's whole disk persists, so what agents and the person install there, such as Tailscale, or Docker in a VM, stays.

The admin pairs the host in Settings → Deployment → Computers, which makes its token, shown once with the command that installs [`computer/pim-host.ts`](../computer/pim-host.ts) from the Pim, run on the host as the user who'll keep the computers:

```sh
curl -fsSL https://pim.example.com/install.sh | sh -s -- host pimh_…
```

The script gets Node.js where the host has none new enough, as for a person's own computer, and `pim-host install` checks the rest before it starts anything, saying what to do about what's missing: on Linux, that the host has KVM and the user can use it; Cua's command, which it installs where it isn't there; Cua's runtime for the kind of computer, which `cua runtime setup` sets up where it can (it uses `sudo`, without asking for a password; otherwise the host's admin runs it); and that the Pim knows the token. Then it runs `pim-host` as a systemd user service, lingering so it runs from boot (or it says how), or on a Mac as a launchd agent of the signed-in user (turn on automatic login, so it starts again after the Mac restarts). Each time it starts, it gets the Pim's newest `pim-host`. The `pim-host` command manages it: `status` says whether it runs, whether the Pim knows its token, and which computers it keeps; `logs`, `update` and `uninstall`, which leaves the computers as they are. Options after the token (`--cpu`, `--memory`, `--image`, `--kind`; `pim-host --help` lists them) are the service's from then on.

`pim-host` needs no open port: every five seconds it asks `/api/computer-host/sync` for work with its token, and reports what it did with the work it took before. Each space's computer is asked for the first time the app looks at it (`GET /api/computer`): the host makes the computer, named `pim-` and the space's owner, with 4 vCPUs and 8 GB of memory unless set otherwise, and sets `pim-computer` up in it with the same install script, as a user service of its desktop session, with a token of its own, so it connects to its space like any other computer. The host starts any of its computers that stopped, as after the host restarted, and starts `pim-computer` again in any where it has gone. In each computer it sets up, it adds 4 GB of swap, so a computer short of memory slows down rather than stopping, and has systemd kill only a program that runs out of memory: by default it stops `cua-spacesd`'s whole service, which `pim-computer` and everything the agents started run in. A computer it couldn't make says why in Settings → Computer and in the Computer dialog, with **Try again**, which makes it anew where making it failed partway (Cua lists it, but it has no VM or container); one that is offline has **Set up again** there too, which starts it if it stopped, makes it anew where Cua has nothing behind it, and gives `pim-computer` in it a new token; one it took and never reported is given again after 20 minutes. Deleting an account removes its computer, with everything on it. Unpairing the host stops it getting work, and leaves the computers it keeps running. Settings → Deployment → Computers shows whether the host is connected, which image it uses, and how many computers it keeps and runs.

There, the agents' Chrome is the desktop's Chromium, with its windows on the desktop, and it stays open. Chromium uses `pim-computer`'s profile and flags however it's opened, so the person and the agents share one browser: what either signs in to, the other is signed in to. A computer set up before a flag was added gets it the next time `pim-host` starts, and its Chromium uses it once it's opened again.

**The Computer dialog.** The rail has a Computer icon at its bottom, with the other dialogs, where the computer is one Pim keeps or one that streams its desktop; ⌘⇧D (Ctrl+Shift+D away from a Mac) opens or closes it from anywhere, and the command palette lists it. It opens over the page, as large as the window allows in the desktop's own shape, and shows the desktop live, and the person uses it with their mouse and keyboard, while the agents work there too: to sign in to sites, get past a check that they're human, or take over from an agent at any time. Pasting sends what the person copied as typed text; copying or cutting there (Ctrl or Cmd with C or X) brings the computer's clipboard text back to the person's own device a moment later, which the browser may refuse where it asks first for clipboard access. While the desktop has the keyboard, every key goes to the computer, Escape and the app's own shortcuts too, except ⌘⇧D, which closes the dialog; keys still held then are let go on the computer. The stream is Cua's: `cua-spacesd`, in the computer, encodes the display as H.264 (its media plane, wire protocol rcdp v2), which `pim-computer` relays to its space and the space to the app, at `/api/computer/screen`, where WebCodecs decodes it onto a canvas. Only the person's own signed-in browser opens it, since it takes input as if at the computer: not an API token. The app acknowledges each frame it decodes (`frame_ack`), so `cua-spacesd` keeps no more than about two seconds of frames on their way, leaves frames out and lowers its bitrate for a slow connection or device, and the picture stays current rather than falling behind; a stream that has sent nothing for three seconds is asked for a keyframe, since after leaving frames out it waits for one, and one that goes quiet after its last frame came more than a second late (measured against the quickest frame, so the two clocks needn't agree) is asked after half a second, since that is how it fell behind. Closing the dialog keeps the stream open for five minutes, so opening it again shows the desktop at once; signing out closes it. When the computer's connection closes, or another takes its place, the space closes the app's stream too (`4000`), and the app connects again once the computer is back. Beside the full-screen button, the dialog's header shows the round trip from the browser to the computer every two seconds, the path the person's input and the video take, and on hover or focus its two parts: between the browser and the space, and between the space and the computer. The app times it with a `pim_ping` on the stream's socket, which the space answers itself after pinging the computer, rather than passing it on to `cua-spacesd`. A computer of one's own streams too where it runs `cua-spacesd` and `pim-computer` can read its token (`/run/cua-env/env-token` in Cua's VMs, `/run/cua/env-token` in its containers, or `PIM_SPACESD_TOKEN_FILE`).

A Pim that started Sprites for people before (Fly.io computers, which it no longer starts) forgets each one the next time its space starts, and the person has no computer until the host makes one or they connect their own. Pim doesn't delete the Sprites or move their files: delete them at [sprites.dev](https://sprites.dev) once nobody needs what's on them.

Cua's CLI is MIT-licensed. `cua-spacesd`, which is in Cua's images, and Cua's own media-plane code are under the Functional Source License (FSL-1.1-MIT), which allows using them but not offering a product that competes with Cua's, and becomes MIT two years after each release. Pim doesn't ship them, or Cua Driver: it talks to `cua-spacesd` in the computer (and through it to Cua Driver, over MCP), and its desktop client is its own, written to the protocol Cua documents (`libs/cua/proto/MEDIA.md`). `pim-host` runs `cua` with its telemetry off (`CUA_TELEMETRY=0`) unless set otherwise. Other images with `cua-spacesd` work with `--image`, such as [Omarchy](https://omarchy.org)'s (`ghcr.io/trycua/omarchy:edge`, Arch Linux with Hyprland, an x86-64 VM only), which Pim hasn't been tried with.

### Host operations

The admin's majordomo can run a few fixed operations on the machine this Pim runs on, through a small daemon there, `hostopsd`: `stats`; `deploy` (`{ ref? }`, a git ref, `origin/main` unless given); `rollback` (`{ commit }`, 7 to 40 hex digits); `restart` and `logs` (`{ service }`, one of `sandbox-manager`, `egress-proxy`, `docker-socket-proxy` and `hostopsd`, and for `logs`, `lines` from 1 to 500, 100 unless given); and `set_slot_limit` (`{ maxConcurrent }`, 1 to 16). Anything else, or any other argument, is refused. Only the majordomo of the admin's space may ask, whatever tool or route the request comes through ([`src/hostops.ts`](../src/hostops.ts)): the admin's other agents, other people's agents, MCP clients, API tokens, and the admin signed in to the app are all refused. The admin, signed in to the app, reads the audit log, the daemon's status and each operation, and issues or revokes the daemon's credential, in Settings → Deployment → Host operations.

The majordomo asks through the `hostops` extension's tools ([`src/extensions/hostops.ts`](../src/extensions/hostops.ts)): `hostops_stats`, `hostops_deploy`, `hostops_rollback`, `hostops_restart`, `hostops_logs` and `hostops_set_slot_limit` each queue their operation and wait up to 100 seconds for it to end; a deploy or rollback still running then answers with its id, which `hostops_op` follows (it waits up to 100 seconds more each time). `hostops_status` says when the daemon was last seen, its version and commit, and its queue. The tools and a prompt section about them are offered only to the admin's majordomo; that only keeps them out of other agents' prompts, since the `HostOps` Durable Object checks every caller, so another agent that reached them is refused, and audited, as any other. They aren't actions that ask first: the allowlist, the audit log and the daemon rolling back a deploy that fails are what keep them safe, so a schedule can run them at night. The exception is `hostops_exec`, a risky action (`explicitApproval`) that runs one shell command as the daemon's unprivileged user: every call asks you, showing the command, and the `HostOps` Durable Object queues it only under an approval Pim records as yours for exactly that command, once; its audit rows keep the command, approver, exit code, duration and redacted output (see [host-ops.md](host-ops.md#running-a-command)). See [host-ops.md](host-ops.md) for setting the daemon up.

The daemon needs no open port: it long-polls `/api/hostops/agent/poll` with its credential for the oldest queued operation, runs it, and reports how it went to `/api/hostops/agent/result`. An operation nobody takes within 10 minutes expires; one the daemon took and didn't report by its deadline (15 minutes for a deploy, 2 for the others) fails as timed out. Only one deploy or rollback is queued or running at a time. The queue and an audit log of every request, refused or not, and of every change of an operation's state, are in one Durable Object, `HostOps`; the log keeps the newest 10,000 rows, with bearer credentials and long token-like strings taken out.

### Diagnostics

The admin's majordomo can debug this Pim without the web app, through the `meta-diagnostics` extension's two read-only tools ([`src/extensions/meta-diagnostics.ts`](../src/extensions/meta-diagnostics.ts), reading through [`src/diagnostics.ts`](../src/diagnostics.ts)). `pim_diagnostics` takes `since` (an ISO 8601 time, or how long back, such as `6h` or `2d`; a day unless given), `kind` and `limit` (20 unless given, 100 at most), and reports, from data the space already keeps: `runs` (chats whose run is held after a model error, and failed tasks), `triggers` (triggers whose source isn't healthy, and their failed runs and deliveries, which covers scheduled tasks), `model_calls` (errors, calls with no price, slow and costly calls), `coding` (threads that failed or wait for input), `connectors` (any that isn't ready, with its error), `approvals` (those still waiting) and `events`. `pim_health` reports the Worker version, the Durable Object's status and next alarm, how many agents, chats, triggers, schedules and connectors the space holds, and how the deployment is set, with its addresses, keys and email sender left out.

The events are a ring buffer of the last 200 warnings that were only logged before (`slow_request`, `slow_refresh`, `run_stalled`, `task_failed`, `model_error`, `failover`, `provider_cooldown`, `watch_lost` and `triggers_on_failed`), kept in the space's own table `pim_diagnostic_events`. Whatever the tools say is cut short and has bearer credentials, token-like strings, `password=`-style values, addresses (only their paths stay) and email addresses taken out. Like the host operation tools, they are offered only to the admin's majordomo, and each call checks that again.

### Who spends

Every model call a space makes is one row in `pim_model_calls` once it settles, errored and aborted calls included with whatever usage they reported: when, which agent and chat, why it ran (`run_kind`), the model, tokens by billing tier (input, output, cache read, cache writes of 5 minutes and of 1 hour; a provider that reports no split has all its cache writes in 5 minutes), how it ended, how long it took, the size of the prompt and of the tool schemas sent, and its cost in dollars. Calls are recorded after they end, apart from the call, and a failure to record is logged and never reaches it ([`src/model-calls.ts`](../src/model-calls.ts), wired in [`src/usage.ts`](../src/usage.ts)).

A call finds its tags from the provider session id pi sends with it, which names its conversation:

| `run_kind` | Which calls | Tagged |
| --- | --- | --- |
| `interactive` | A chat's runs, including those a person's message, an approval or a coding thread's wake started | agent, chat |
| `scheduled` | A chat a trigger whose source is a time (a scheduled task) is running in | agent, chat, trigger id |
| `trigger` | The same for any other source | agent, chat, trigger id |
| `delegated` | A task's conversation | agent, the chat the work began in, the task id as `parent_run_id` |
| `background` | Calls with no conversation (naming a chat, the utility model, memory compression) and compaction summaries | nothing else |
| `coding_thread` | Not recorded yet | |

A call whose conversation can't be found has no tags, and a null `run_kind`. A call's `turn_index` is the number of assistant turns already in what it sent.

**TODO: coding threads.** A coding thread's model calls don't reach the space's Worker: its `ThreadDO` records them in its own log and spend (`coding_*` tables, `recordModelCall` in [`src/coding/thread-store.ts`](../src/coding/thread-store.ts)), and nothing reports them to the space. Rows with `run_kind = 'coding_thread'` and `coding_thread_id` need that report added; the columns and the top coding threads in the costs report are ready for them.

Prices are in [`config/model-prices.json`](../config/model-prices.json), in dollars per million tokens by model id (an id with a gateway prefix such as `anthropic/` matches the model without it). A call is priced when it is recorded, and keeps the table's `version`; a model with no price has a null cost and counts as unpriced, and calls on the person's own plans and providers have a null cost and are marked `plan`. Prices the catalog flags as estimated are `estimated` there, as are the 1-hour cache write prices, which the catalog doesn't have and which are twice the input price. To change a price, edit the file and bump `version`.

The triggers' wake, an alarm, rolls the calls up each hour into `pim_usage_daily` (a day recomputed from the calls and replaced, so doing it twice changes nothing), and drops calls older than 90 days and rollups older than 400. `GET /usage/costs?days=30` reads the rollup and the calls since it.

### Traces

Pim sends [OpenTelemetry](https://opentelemetry.io/) traces of what the agents do to any backend that takes OTLP over HTTP as JSON: Langfuse, Arize Phoenix, Honeycomb, Grafana, Jaeger, or an OpenTelemetry Collector. They follow the [semantic conventions for generative AI](https://github.com/open-telemetry/semantic-conventions-genai): each run of a conversation is an `invoke_agent` span, each model request in it a `chat` span with the model, finish reason and tokens, and each tool call an `execute_tool` span. Work a tool call starts in another conversation is that call's child, so one trace holds everything a message led to: the tasks it handed out, and the majordomo's review of an approval request, with its decision.

Set the endpoint as a variable in the dashboard, like the settings above, and its key as a secret, with the standard OpenTelemetry variables:

| Variable | Meaning |
| --- | --- |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | The backend's OTLP base URL; traces go to `/v1/traces` under it. Or set `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` to the full URL. Empty sends no traces |
| `OTEL_EXPORTER_OTLP_HEADERS` | A secret (`wrangler secret put`): headers as `key=value,key=value`, such as `Authorization=Basic ...` |
| `OTEL_SERVICE_NAME` | The traces' service name; `pim` when unset |
| `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` | `true` adds prompts, messages, and tool arguments and results. They are people's private conversations: set it only for a backend that may hold them |

Each span's `gen_ai.conversation.id` is its conversation's id; for a chat, the one in `/chat/<id>`. Spans go out every few seconds and whenever a person's agents go idle; any not yet sent are lost if their space is evicted.

For local development, run `pnpm dev`: the Worker and the built web app at `http://localhost:8787` (use `localhost`: passkeys don't work on an IP address). Its first 15 minutes count as just deployed, so the first account you make is the admin, and setup links show up in the terminal. For the web app with hot reload, make an API token in Settings and run `PIM_API_TOKEN=... pnpm dev:web` (port 3000), which signs in with it. The `AI` binding is remote, so `wrangler dev` needs a Cloudflare login, and model calls bill that account. `pnpm preview` runs the same Pim with no Cloudflare login and a stand-in model, at the same address.

## API

The API lives under `/api`: `GET /api/sessions`, and so on; the table leaves out the prefix. It is the signed-in person's own space. The web app calls it with its session cookie. Other clients send `Authorization: Bearer <token>`, with a token made in Settings (API tokens), which names its owner (`pim_<owner>_…`). WebSockets from clients that can't set headers pass `?token=<token>` instead. Only the three paths connected connectors call stay at the root, without the prefix, and name whose agent they are for: `/mcp/callback/:owner`, `/mcp/events/:owner/:key`, and `/mcp/client/:owner`, Pim's client metadata document for services whose sign-in takes one instead of registering clients (Amp's). MCP clients talk with your majordomo at `/mcp`, also at the root, with an OAuth access token or an API token (see [Talking with Pim from other apps](#talking-with-pim-from-other-apps)). Each has a random id (a UUID) of its own, which is also its address in the connector (`/chat/<id>`); `GET /` names the root session, where API clients talk by default. ### WebSocket

Connect to `wss://<host>/api/ws?session=<id>` (add `&token=...` without a passkey session); without `session`, the socket follows the root session. Each socket follows one session at a time; `follow` moves it to another, starting again with that session's snapshot, and `snapshot` returns another session's snapshot without following it. Message types are in [`src/protocol.ts`](../src/protocol.ts).

- Server → client:
  - `hello`: the session and tools.
  - `events`: pi's [agent events](https://github.com/earendil-works/pi/tree/main/packages/durable#agent-events-experimental). The first batch starts with a `snapshot` that replaces client state.
  - `progress`: what the session's agent is doing, in a few words from the utility model, for the tool calls `calls` (see [Utility model](#utility-model)).
  - `notification` and `approval`: sent to every socket.
  - `result` and `error`: replies to commands that carried an `id`.
- Client → server: `submit`, `abort`, `reset`, `resync`, `follow`, `snapshot`.

A socket whose session's events stop coming (its watch couldn't be set up, couldn't be restored as the space started again, or ended) closes with `4010`: connect again to get a fresh snapshot.

To fold events into a chat view, see the reducer in Cloudflare's [pi harness example](https://github.com/cloudflare/agents/tree/main/examples/next/harnesses/pi/src/view.ts).

## Memory

Long-term memory follows Victor Taelin's [OptMem](https://github.com/VictorTaelin/OptMem), reimplemented as a pi-durable extension in [`src/extensions/optmem`](../src/extensions/optmem).

- **The log is the truth.** The agent records one-line memories (up to 280 bytes) with `note` as it learns things. Memories are numbered in order and never edited.
- **Each memory is in one scope.** A scope is a log of its own, with its own places 0, 1, 2, …, and its own tree; see [Scopes](#scopes) for who reads which.
- **Summaries form a binary tree.** In each scope, block `#0-1` summarizes its memories 0 and 1, `#0-3` summarizes `#0-1` and `#2-3`, and so on; the model sees them as `#private/0-3`. A background pi task compresses each block as soon as it is complete, smallest first: blocks up to 16 memories from the raw lines, larger ones from their two halves. The tree is a cache; any summary can be dropped and rebuilt.
- **The view has a fixed size.** Every conversation's prompt holds about `PIM_MEMORY_LINES` lines of the scopes its agent reads, shared out equally, a scope never getting more than it holds: in each, the newest memories verbatim, older ones as summaries that get coarser with age. The model gets back detail with `recall` (a regular expression over the scopes it reads) and `zoom` (a block's two halves).
- **Forgetting is real.** `forget` blanks the memory, keeping its number, and drops every summary built over it; they are rebuilt without it. A summary that was being written when a memory was forgotten is discarded.
- **Moving is forgetting in one scope and noting in another.** `move_memory` (or `PUT /memory/log/:id`) appends the memory to the other scope, with a new number and the date it was first noted, and empties its old place as forgetting does.

### Scopes

Your majordomo knows everything you tell it; your other agents know only what concerns them.

| Scope | Who reads it | Whose notes go there |
| --- | --- | --- |
| `private` | your majordomo | your majordomo's |
| `everyone` | every agent, and the circles you tick | any agent's that chooses it |
| `agent-<id>` | that agent, the copies of it you made from the same template, and your majordomo | theirs |
| a named scope, such as Work | the agents and circles you tick, and your majordomo | theirs, when they choose it |
| a deleted agent's or named scope's | your majordomo | nobody's |

- **Notes start narrow.** `note` keeps a memory in its agent's own scope unless the agent names another scope it reads. The majordomo is told to keep in `everyone` only what every agent should know, such as your name and language, and to pass the rest along in the tasks it hands out.
- **A task reads its own agent's memory.** An agent working on a task another handed it reads its own scopes, not those of the agent that asked: what it learns about you from the asker is what the task says.
- **The majordomo can make and share scopes.** For a part of your life only some agents should know, such as your health, it names a scope with `create_memory_scope` and keeps those memories there; only it reads a new scope. `share_memory_scope` lets another agent read a named scope, or stop reading it, and asks you first, as Settings → Tool permissions sets. Other agents aren't offered either tool, and only you choose what circles read.
- **Choosing.** Settings → Memory lists your memories with their scopes: move one by choosing another scope, or forget it, and make, rename and delete named scopes. An agent's page ticks the named scopes it reads; a circle's, in Sharing, ticks `everyone` and the named scopes it reads.
- **From before scopes.** Memories noted before there were scopes are all in `private`, with their summaries, so only the majordomo reads them until you or it move some. Circles that could read memory read `everyone`. Copies of a template made before scopes each have a scope of their own.

Where pim differs from OptMem:

- The view is a prompt section rather than a `wake` command, so the model always has it.
- Compression runs in a durable background task instead of interrupting the conversation.
- OptMem never deletes; pim lets you forget.

### Memory and the prompt cache

pi never edits what it already sent, so the provider's prompt cache keeps hitting. A changed system-prompt section is appended to the transcript as a whole new copy, and old copies stay until a compaction writes a fresh baseline. The memory is built to change that prompt as little as possible:

- **A conversation keeps the view it was first shown.** Most requests add nothing to the prompt.
- **Notes a conversation takes itself** are already in its transcript, so they trigger nothing.
- **Memories from elsewhere** (the API, other sessions) are listed in a small `memory_since` section after the view. When the list changes, only the list is re-sent.
- **The view is re-rendered only when:**
  - a memory is forgotten or moved, so the old view stops showing it;
  - the agent reads other scopes;
  - more than an eighth of the view (at least 4 memories) piles up in `memory_since`;
  - a full view's worth of memories has arrived since it was shown.
- **Compaction** writes every section again anyway, and the old view goes with the compacted entries, so the conversation gets a fresh view at no extra cost.

The same rule applies to every section: one that appears later than sections after it makes pi remove and re-send all of them. That is why `active_goals` says "No active goals." instead of disappearing.

Forgetting removes a memory from the log, the tree, and future views. It does not erase the conversation where it came up: that stays in the session's transcript until you reset the session.

## ChatGPT plan

Pim supports OpenAI's [ChatGPT plan usage for open-source apps](https://developers.openai.com/siwc/token-sharing-open-source): sign in with ChatGPT, and requests to OpenAI models count against your Plus or Pro plan's included usage instead of an API bill. ChatGPT's settings show Pim's usage and let you cap it.

OpenAI only redirects a sign-in to a loopback address (`http://127.0.0.1:1455/...`), which can't reach a Worker. So the sign-in has a paste step:

1. `POST /chatgpt/login` returns a URL. Open it, sign in, and approve Pim.
2. The browser lands on a `http://127.0.0.1:1455/auth/callback?code=...` page that doesn't load. Copy that whole address.
3. `POST /chatgpt/callback` with `{ url }`. Pim exchanges the code (with PKCE), checks the ID token against OpenAI's keys, and stores the tokens in its database.
4. `PUT /model` with one of `GET /model`'s choices, such as `{ "provider": "openai", "id": "gpt-6.1-sol" }`.

Pim registers with OpenAI as one agent host (a `urn:uuid:` ID it keeps) and refreshes the token itself, one refresh at a time, since OpenAI rotates refresh tokens. Memory compression stays on `PIM_MEMORY_MODEL`, or `PIM_MODEL`, so background work doesn't spend the plan. pi-ai sends these requests the way the flow requires: `store: false`, streaming, and no `temperature` or `max_output_tokens`.

When the plan's usage limit is reached, the request that found it goes to the deployment's default model (`PIM_MODEL`) at once, and the chat carries on there without an error. The plan then cools down: until the reset OpenAI gives, in its `retry-after` or rate-limit headers, its error's fields, or its words ("try again in 42 min", "try again at 5:32 PM", read as UTC), or else for 5 minutes, then 15, then an hour, 3 hours and at most 6 for each limit in a row. Meanwhile every request for the plan goes to the default model without asking the plan first, side jobs go to the utility model, and once the cooldown ends the plan is asked again; its first answer forgets the cooldown. A deployment whose default model is the plan's provider, or can't run, has nowhere else to go: the chat is held on the limit as before. Cooldowns are kept in the space's database ([`src/provider-cooldowns.ts`](../src/provider-cooldowns.ts)).

## ChatGPT images

OpenAI's plan sharing doesn't include image generation, so the plan above can't draw. ChatGPT's Codex backend can, for anyone signed in with Codex's own client, and Pim uses it the way Codex does: `generate_image` posts to `chatgpt.com/backend-api/codex/images/generations`, and the image counts against the plan's Codex usage. ChatGPT's firewall answers requests from Cloudflare Workers with a 403 page, so the request is made from your computer: Pim writes it to a file in `/workspace/.pim/`, runs a few lines of Node.js there with `node` (which `pim-computer` already needs) to send it, and reads the answer back, so the computer must be online and have `node` on its PATH. This is a second sign-in, apart from the plan's, and an internal OpenAI API with no promises: it can change or stop working. OpenAI picks the model (`gpt-image-2`), the quality and the pixel size; the shape (square, landscape or portrait) is asked for in the prompt. It needs a Plus or Pro plan, not Free.

The sign-in has the same paste step, with Codex's redirect, `http://localhost:1455/auth/callback`:

1. `POST /chatgpt/images/login` returns a URL. Open it and sign in.
2. Copy the address of the page the browser lands on, which doesn't load.
3. `POST /chatgpt/images/callback` with `{ url }`.

While connected, the plan makes every image, and each counts as a model request on `openai`. Disconnecting returns to `PIM_IMAGE_MODEL`. Pim refreshes the token itself, one refresh at a time, since OpenAI rotates refresh tokens.

## Model providers

Besides Workers AI and the ChatGPT plan, Pim has built-in connections for Anthropic, OpenAI API, Google Gemini, OpenRouter, DeepSeek, Mistral AI, Groq and xAI. In Settings → Model → Providers → Add provider, choose the service, enter its API key and choose up to 50 models from Pim's searchable catalog. No endpoint address is needed. These connections use the models' native APIs and capabilities from pi-ai. They bill the provider's API account, not a chat subscription; OpenAI API is separate from the ChatGPT-plan connection. The catalog is bundled with Pim, not a live account listing: your account must have access to the models, and the key is checked when you use one.

Pim also runs on any server that speaks OpenAI's `/chat/completions`: a model on your own machine, such as llama.cpp's `llama-server`, LM Studio, Ollama or vLLM, or another provider's compatible API. Choose Custom endpoint and give it a name, its address (the part before `/chat/completions`, such as `http://localhost:1234/v1`), and its API key if it needs one. A custom endpoint can instead speak Anthropic's Messages API, such as a proxy that serves Claude models: choose it under API (`api: "anthropic-messages"`), and give the address before `/v1/messages`, such as `https://proxy.example.com`; its models are then read from `<address>/v1/models`. Existing custom endpoints keep working unchanged, on chat completions. Both kinds of connection offer models for chats. A custom endpoint's models are offered as the utility model only when you say it supports structured outputs (the switch in its settings, `structuredOutput`): that its models follow a JSON schema given as `response_format`; check your server's documentation. Of the built-in services, Anthropic, OpenAI, Google Gemini, Mistral and xAI are offered; DeepSeek, Groq and OpenRouter are not, as they only promise valid JSON, or only for some models.

- **Yours, or everyone's.** A provider you add is yours alone: only your agents use it, and its tokens count as yours, not against the deployment's daily token limit. The admin can add one for everyone instead (Everyone on this Pim can use it), so people who join can use it without bringing their own; its tokens count against the limits like Workers AI's. Only the admin changes or removes those. Removing a provider moves chats on its models back to the default model.
- **Models.** A built-in connection offers only the models you choose; saving it again updates their definitions from Pim's bundled catalog. Adding a custom endpoint reads its models from `<address>/models`, and saving it again reads them again, such as after loading another model in LM Studio. A server that lists more than 50 needs the ones to offer named, and a server that can't list its models can be given them by name. What a custom endpoint's model can do comes from the server's list where it says (OpenRouter's context length and input types, vLLM's `max_model_len`, llama.cpp's served context `n_ctx`), else from pi-ai's catalog when it knows the model by that id, else a 128,000-token context and text only. You can set a custom endpoint's real context window, and its price per million tokens, for each model when you edit it; they stay when its models are read again, and without a price a model counts as free. A chat that outgrows a model's real context is compacted and tried again (see Compaction continues a chat).
- **Keys.** Pim keeps a provider's key in your space, or for the admin's in the gallery, sends it only to that provider, and never shows it again: Settings shows only that there is one. A server without a key, as local ones usually are, is sent a placeholder.

A Pim on Cloudflare can only reach providers on the public internet; one running on your own machine reaches `localhost` too. Pim says everything with tool calls, so a model needs dependable tool calling and a large context: llama.cpp needs `--jinja` and a `-c` well above the 8k tokens of memory every prompt carries, and LM Studio a context length well above its default. Image generation stays on Workers AI.

Workers AI is optional. A deployment without the `AI` binding (delete `ai` from `wrangler.jsonc`) has no platform model: the first model of the first provider, the admin's and then the person's own, is the default until someone chooses another, and until a provider is added, chats answer that no model is set up. Without it, `PIM_MODELS`, `PIM_IMAGE_MODEL` and `PIM_UTILITY_MODEL` do nothing, chat naming and similar side jobs use a provider's model that answers in a JSON schema when someone picks one, long-term memory is not compressed, and `generate_image` is not offered.

## Utility model

Small jobs around a conversation go to one utility model rather than the chat's model: a fast, cheap one by default (`PIM_UTILITY_MODEL`), or a model on your ChatGPT plan, a built-in service that answers in a JSON schema, or a custom endpoint you said supports structured outputs (Settings → Model → Utility model). A chosen model whose provider stops qualifying, such as an endpoint with the switch turned off, is skipped for the default until it does again. Its requests count against the daily model limits, but not as runs. Today it:

- **Names chats.** A chat is called by the start of its first message at once, then by the few words the utility model picks. A rename in the meantime stays. Chat ⋯ → Regenerate names it again from the conversation so far.
- **Improves prompts.** The ✨ button in the message box rewrites the draft in place so the agent can act on it.
- **Suggests what to say.** Below the message box in New chat, chips offer short commands to send the agent; ⌘-click (Ctrl-click) one to put it in the message box to edit first. A new agent offers Pim's starters. Once you've chatted with it, the utility model writes them from its latest chats and what Pim remembers, and they fade in when ready. They are written again only when opening New chat finds that something changed, so an agent you don't talk to costs nothing.
- **Summarizes chats.** The options button in a chat's header opens a box at the top right, which also holds a row of buttons: the chat's agents, copying, the public link and the cost; it is closed whenever a chat opens. Expand the Summary dropdown inside it for what the chat covered and the next steps; Nothing is written while the dropdown is closed, so you can view the browser without starting a summary, and a summary is kept until more is said.
- **Says what an agent is doing.** While an agent works, the chat lists its steps above the dots, a few words each behind a mark for the kind of step (a connector's tools get the connector's icon), and adds one as it goes. A model that summarizes its own reasoning under headings, as OpenAI's do, says it itself: each heading is a step. Each tool call is a step too, named by the utility model, from the person's request, the results the agent just got, its notes, and the call with its arguments, which makes it the one job that sees the agent's tool calls ([`src/progress.ts`](../src/progress.ts)). It writes one line at a time, at most one every five seconds, for the latest step, and only while someone has the chat open; a step it didn't describe, or any step without a utility model, shows the tool's name. Once the agent sends its message, the list folds into a "Worked for 42s" line that opens to it again. The utility model's lines aren't stored: after a reload the list shows the tools' names in their place.

Each job is a task in [`src/utility.ts`](../src/utility.ts): instructions, a cap on the answer for models that don't reason, and how to clean the answer. A job whose answer has a shape, such as the suggestions, is a structured task: the model answers in JSON that follows a schema, which its provider enforces with its own structured-output feature (`Pim.utilityStructured`; `withJsonSchema` puts the schema in the request in the form each API takes). That is why only models that support one are offered as the utility model. `Pim.utility(task, input)` runs one on the utility model, and `conversationText` gives it a chat as what each side said, without tool calls or the agent's private notes. A new feature adds a task there and a route that calls it.

## Connectors

Connectors connect through remote [MCP](https://modelcontextprotocol.io) servers: the vendor's own (many connectors publish one), or one you deploy as another Worker. The `agents` SDK's MCP client handles the connection, OAuth sign-in (with dynamic client registration), token storage in the agent's database, and reconnecting after a wake.

- **The directory.** People connect only the connectors this Pim offers: those its extensions bring (`apps` in [an extension](extensions.md#connectors): MCP servers such as the bundled GitHub, Linear and Notion, or connectors the extension implements for services without one, like the bundled Spotify connector), and those the admin adds in Connectors → Create new connector, or by asking their majordomo, named `custom/<app>`. Nobody connects an arbitrary server. `GET /app-directory` lists them.
- **One sign-in for all your agents.** Agents and templates list connectors by name (`test.ledger/notes`, `custom/acme-crm`), never by URL. You connect a connector once, and every agent of yours that lists it uses that connection. Agents and templates from before the directory listed `{ name, url }`: each is read as the directory's connector at that URL, and left out while the directory has none.
- **Each agent lists its connectors.** Each of your agents lists its own (ask in chat, type @ and the connector's name in a chat with it, or Add connector on its page in Agents, which offers the connectors you connected). The @ offers every connector in the directory, the agent's own first: one it works with is mentioned in your message, and any other asks whether to add it to the agent, then adds it, connects it if it isn't yet (opening its sign-in), and mentions it. A chat gets the tools, instructions, and prompt entry of the connectors its agent lists, and of no other, even when you connected more. An agent at work on a task works with its own connectors.
- **Connecting.** Connect from Connectors in the sidebar's rail (also opened by Connect more connectors under an agent's Add connector), a connector an agent's page lists but isn't connected yet, `POST /mcp` with the connector's `ref`, or ask Pim: its `connect_connector` tool connects one of the connectors the chat's agent lists, without asking, since the agent already chose it. It can't connect anything else. If the connector needs sign-in, the response (or Pim) gives you a link; the connector sends you back to `/mcp/callback/<you>`.
- **Seeing them.** Connectors, a dialog from the sidebar's rail, lists every connector this Pim offers, whether you connected it, which of your agents work with it, and a sign-in link while it waits for one. Disconnect a connector there. A connector no agent lists does nothing until one does. A connector you connected that the Pim no longer offers stays until you disconnect it.
- **Finding a connector.** Say "use my Linear" and Pim's `find_connector` tool looks it up in the directory by name, then by description, for its `ref`.
- **Managing connectors in chat.** With `manage_connectors` enabled, Pim requests additions and removals for its own agent, by `ref`; your majordomo can also name another of your agents. You approve the connector names in chat; approval adds and connects new connectors, and Pim resumes your task with their tools. A connector the directory doesn't have is refused before you're asked. Each change requires your explicit decision, even under the `auto` approval policy: no timeout or Always approve. Settings → Tool permissions offers **Off / Ask** for this capability, separately from `update_agent`, which cannot change connectors. Removing a connector here does not disconnect the shared connection, change its tool permissions, or affect other agents. If sign-in is needed, Pim returns its link; it never needs your credentials in chat. If connection fails, the connector stays on the agent's list so `connect_connector` can retry, and the result explains the failure.
- **The admin's majordomo adds connectors.** Tell your majordomo about an MCP server this Pim doesn't offer yet, with its https URL, and, if you're the admin, its `add_custom_connector` asks to add it to the directory for everyone, as Connectors → Create new connector does. Approving it adds the connector, puts it on the majordomo's own connectors and connects it, with a sign-in link if it needs one; it can then make an agent that works with it, or you add it to one. Each request needs your explicit decision from the signed-in web app: not an API token, the majordomo's review, a timeout or Always approve. Settings → Tool permissions offers **Off / Ask**. Only the admin's majordomo is offered the tool, and the space asks the directory whether its owner is the admin before it runs. A server already in the directory is that connector; nothing is added twice.
- **Tools.** Each MCP tool becomes a pi tool named `<app>_<tool>`. pi picks up added and removed tools from the next request, without a restart. The connector's instructions go in the `connectors` prompt section.
- **Each agent's switches.** An agent's page (in Agents) lists the connectors it works with, and once one is connected, a switch for each of its tools. A tool that is on runs in that agent's chats and tasks without asking you; one that is off isn't offered to it, and a call made with a tool list from before you switched it off is refused. Nothing an agent does with its connectors files an approval. A tool starts on, unless the connector marks it `destructiveHint: true` (native connectors: `destructive: true`) or the connector's approval policy is `all`: those start off, and run freely only once you switch them on. Choices you made in Settings for every agent before the switches carry over: On stays on, Ask and Off are off. The hints come from the connector itself, so only connect connectors you trust.
- **Tied to the tool you switched on.** A switch you turned on is held to the tool's definition at the time: description, input schema and annotations. If the connector changes any of them, the tool is off for that agent, and its page says so, until you switch it on again. Deleting an agent forgets its switches.
- **Apps and circles.** An app may call a connector's tool that runs without asking under the connector's approval policy (`writes`, the default: those that declare `readOnlyHint`; `none`: every routine tool), once you allow its version. People in your circles use your connectors' tools only as each circle's permissions say (see [Sharing](#sharing)).
- **Prompt cache.** The connectors' tools come last in pi's tool list, so a newly connected connector's tools are appended to what the provider has cached instead of re-sending every tool.

### Skills from connectors

Connectors that implement the [MCP Skills extension](https://modelcontextprotocol.io/extensions/skills/overview) (`io.modelcontextprotocol/skills`) ship instructions for using them as [Agent Skills](https://agentskills.io). pim reads a connector's `skills/list` when it connects and again when the listing's TTL runs out, and lists each skill's name and description under the connector in the prompt. The model loads one with `read_skill`, and supporting files with `read_skill_file`.

- Every file is checked against the SHA-256 digest and size the connector published; a mismatch re-reads the listing once, so a connector that updated a skill is picked up, and content that still doesn't match is refused.
- Skill content is labeled with the connector it came from, as the extension requires: it is the connector's text, not the user's.
- pim runs no code from skills. Anything a skill tells the model to do goes through the connector's tools and their approvals.

### Events from connectors

Connectors that implement the draft [MCP Events](https://github.com/modelcontextprotocol/experimental-ext-triggers-events) extension can tell Pim when something happens: a price changed, a message arrived. pim supports webhook delivery, the same slice ChatGPT implements.

- **Watching.** Ask Pim ("tell me when the JFK–Lisbon price drops below $500"); `watch_connector_event` makes a [trigger](triggers.md) on the connector's event, enabled, delivering to the chat it was asked in, and subscribes at once, with no approval: it only works for an event listed by a connected connector the agent works with, and says so when the connector refuses the subscription. Settings → Tool permissions can switch it Off (it is On otherwise, and an Ask chosen before it stopped asking counts as On). What the agent does when an event arrives still goes through the usual approvals. The trigger's subscription calls `events/subscribe` with a callback URL (`/mcp/events/<owner>/<key>`) and a fresh signing secret, and renews it before the connector's grant runs out (see [Keeping the subscription](triggers.md#keeping-the-subscription)). `list_watches` lists the agent's triggers on connectors' events and where each subscription stands; they are on the Triggers screen too.
- **Receiving.** Each delivery must carry a valid Standard Webhooks signature from the last five minutes and pass the ingress adapter's checks ([Connector events](triggers.md#connector-events-the-ingress-adapter)). The event becomes a `[Connector event]` message to the chat that created the watch, with the instruction and the event data marked as untrusted; the data is kept only until its run has it, a day at most. The event id is taken once, so a delivery the connector retries starts one run, not two.
- **Ending.** `stop_watch` (by its id) or deleting the trigger unsubscribes. A watch the connector terminates, or refuses to renew, shows it in its trigger's health and in `list_watches`. Deleting its chat, or removing its connector, stops it.
- **Draft.** The extension is not ratified. Today's MCP SDKs drop its `events` capability from the handshake, so pim also asks a connector for `events/list` when it declares nothing.

MCP servers expose tools, prompts and resources; pim uses their tools, instructions and skills. They cannot add hooks or change how pim runs, which is also what keeps them safe to connect.

### Tool permissions

Settings → Tool permissions lists Pim's own tools that act on the world (`http_request`, `watch_connector_event`, `update_agent`, `shell`, `file_delete`, `browser_click`, `browser_type`, `browser_upload`, `desktop_act`, and the actions extensions' abilities bring). Each is **Off** (the model isn't offered it), **Ask** (each call files an approval; for `browser_click` and `browser_type`, only a call that sends a form that doesn't say `method="get"`) or **On** (it runs without asking). A tool you haven't set asks, except `watch_connector_event` and `update_agent`, which run without asking and are only Off or On. **Always approve** on a request sets its tool to On. A connector's tools aren't here: each agent has its own switches for them (see [Connectors](#connectors)).

- **Assignment is consent for an ability's actions.** The actions of the installed extensions' abilities run in its chats without asking, unless you chose Ask or Off.
- **Connector management always asks.** `manage_connectors` offers only Off / Ask. Each request waits for your explicit decision, even under the auto policy; turning it off also blocks pending changes.
- **Removing a connector** forgets its tools' permissions and switches. Connector tools chosen with Always approve before permissions existed are on for every agent that works with the connector, the first time Pim sees them.

## Your agents

The notifications panel is for things you haven't opened, not an activity history. Each row shows the agent's icon, a title and a short time. In-app alerts and device push notifications also carry the agent's uploaded image, symbol or emoji; notices without an agent use Pim's icon. Device alerts use the default icon style and colors, and whether their icon appears depends on the browser and operating system. Safari, including iPhone and iPad Home Screen apps, ignores per-notification icons and shows the app's icon instead. A notification is marked read when you open its linked chat from the row. It stays in place until you leave the panel and disappears when you return. Opening the panel or scrolling through it does not mark notifications read; Mark all as read clears the list at once, including notifications without a linked chat. Reading a notification does not delete its chat or change the API's notification history.

Push notifications follow your device's browser permission, with no separate in-app switch. When permission is already granted, opening or returning to Pim automatically registers the device with your space, even if it has never subscribed, and repairs missing registrations or outdated subscription keys. If permission hasn't been decided, Settings → General offers Allow notifications to open the browser's permission prompt; Pim never prompts automatically. To turn notifications off or unblock them, use your device or browser settings. On an iPhone or iPad, add Pim to the Home Screen first. Settings reports whether the device is registered, not whether the system will display an alert. A device alert shows the opening sentences of its message, with Pim's mark as its small status-bar icon; the full text is in the app. By default (Settings → General → Alerts, "Only what needs me") a device is alerted only when an agent mentions you, when an approval waits for you, and when an agent answers a message you sent after you left the chat; the answer waits until the chat has finished working, so progress doesn't buzz. Choosing "Every message" also alerts on each message an agent sends you while you aren't looking, such as a scheduled task's reply. Replies from one chat share an alert that counts them; mentions and approvals each have their own. Scheduled tasks send an in-app notification linking to their chat when they start, but no device alert of their own.

The chats panel is one list across all your agents and your conversations with shared spaces, most recently active first, under dividers for today, yesterday, last week and the last 14 days. Each chat has its agent's icon in front of it (a shared space shows its owner's initial). It has a quiet, left-aligned New chat button below search. New chat, there, in the mobile bar, in the command palette and with ⌘⇧O (Ctrl+Shift+O), opens over whatever page is open, so you don't lose your place: a message box with whom the chat is with beside its attach buttons, the agent of the chat that's open or your majordomo anywhere else, which you can change. Sending the first message makes the chat and opens it; Escape or × closes it and keeps what you typed. Opening Pim goes to the chat you used last; a space with no chats opens New chat over an empty page. A dot on the left marks an unread response, or a working chat (working takes priority); it gently pulses unless reduced motion is preferred. Opening its conversation in a visible tab clears it once the transcript has loaded and the turn finishes. Read state belongs to your space, so it follows you between devices, independently of notification read state. Existing conversations start read when reply tracking is introduced; new replies become unread.

Your agents are assistants, each with its own instructions: a marathon coach, a trip planner, a code reviewer. Each has a name and a role. The role is what it is for, such as Marathon coach, and each of your agents has its own: two agents can't share one (`409`), and agents and templates refer to each other by it. The name is what you call it, such as Ada, and each of your agents has its own too (`409`), whatever its case. Left out, a role is the name, and your majordomo's is always Majordomo, whatever you call it. Each works as Pim's own assistant, with the tools the deployment's [extensions](extensions.md) bring; your name and instructions go on top. One is your [majordomo](#your-majordomo): it talks in chats started without choosing an agent. Agents, at the bottom of the sidebar's rail or with ⌘⇧E (Ctrl+Shift+E), opens over whatever is open and lists them down its side, the majordomo first, so changing an agent never leaves the chat. Pinned chats show as tabs above the transcript, so you can switch between them with the sidebar collapsed; each tab shows when its chat is working or waiting for your approval. ⋯ → Pin to tabs, or dragging a chat onto the conversation, pins it. Any other chat opens in place, replacing the unpinned chat shown before it, without a tab of its own, so quickly starting chats never piles up tabs. Unpinning a tab keeps the chat. The pins are kept in the browser, and each chat keeps its unsent text and scroll position while the page is open. Agents opens on the open chat's agent (the majordomo elsewhere); click another for its page beside the list: chatting with it, publishing, deletion, its connectors and their tools, and its details, which save together. Connectors you add there save at once, from those you connected. Creating or editing an agent sets how it looks: one of the built-in icons or any emoji, in a color, or an uploaded image. Use + beside the Agents title to create another; once made, its page opens, to add its connectors. Links open it too: `?dialog=agents&agent=<id>`, or `agent=new` to make one. A chat started with another (New chat from one of its chats, choosing it in New chat, or Chat on its page) talks with that one. A chat's agent adds its name and instructions to the model's own habits; everything else is shared by all agents in your space: connected connectors, approvals, schedules. Memory is in [scopes](#scopes): each agent reads its own, everyone's, and the named scopes ticked on its page; your majordomo reads them all. Edit an agent and its chats follow from their next request; delete it and they go on with the majordomo. An agent lists the connectors it works with, by name: its chats get only those connectors' tools, and whoever uses it connects them with their own accounts.

**Edit in chat.** Ask an agent to change its name, role, instructions, description, contacts or look, such as “Use the picture you just made as your icon.” `update_agent` makes the change at once, without asking; Settings → Tool permissions switches it off for every agent. An icon can be an emoji and a color, or an image: a PNG, JPEG, WebP or GIF of at most 256 KB from your files, such as one `generate_image` made, or from a URL on the web. A request to change an agent filed before `update_agent` stopped asking still waits for you, and its image is set only if it is still the one you were shown. Other agents change only themselves; your majordomo changes any of your agents, so you can ask it to rename one, change its role, or find or make a picture for one and use it as that agent's icon.

**An agent for everyone who joins.** The admin can choose one of their agents for new members (its page in Agents → Give everyone who joins a copy). Each person who joins after that gets a copy besides their majordomo: its name, role, description, instructions and suggested connectors, and copies of its contacts, theirs to change. Copies don't follow later edits to the admin's agent, and people who joined before don't get one.

An agent can be **published** to the others on your Pim: Discover lists published agents, and anyone on it can read one in full and **make it their own**, which copies its name, description, instructions, suggested connectors and look (its icon or emoji, color, or uploaded image) into their own agents, with copies of the agents it comes with (see [Contacts](#contacts)). The agent the admin chooses for everyone who joins is copied the same way. Nothing else of the author's goes with it: no memory, chats or credentials. The copy is theirs to change; publishing again updates what others see, not their copies. Unpublishing, deleting the agent, or deleting the account takes it out of Discover. Each person has a profile (a name and a line about them), shown on their page and next to what they publish. Apps are published the same way, from Share on the app's page: a copy of its latest version, which anyone on your Pim can open from Discover and use with their own data, model and tools, or make their own (see [docs/apps.md](apps.md#publishing)). Until someone else has an account on your Pim, there is nobody to publish for, so the app hides Discover and the Publish button.

A published agent's instructions are someone else's words running with your tools, so read them before you take one: your copy still asks before acting wherever your tool permissions say it should.

### Your majordomo

Your majordomo is the agent you come to first, for almost anything, and the one that knows you best. There is one, always the same: the title can't move to another agent, and it can't be deleted. It is edited like any agent.

- **Setting it up in chat.** There's no form to fill in. The first time you sign in, your majordomo opens your first chat itself: it introduces itself, greets you by the name you gave when you joined (or the one the Google, GitHub or single sign-on account you joined with says, or asks, when neither does), and asks what you'd like to call it. Give it any name, or leave it to it. It takes the name with `update_agent`, with an emoji and color that suit it, as any agent changes itself, and notes your name for every agent. Its page (in Agents) changes its name and look, how it talks (warm, formal, playful or brief, or in your own words), and how much it takes care of without asking you (keep me in the loop, use your judgment, or take it off my hands). After its name, it gets to know you: it asks one question at a time and takes one topic at a time, so that happens over a few conversations rather than all at once. It remembers your name, for every agent, and what you tell it, in its own private [scope](#scopes). Accounts from before majordomos keep the agent they talked with as theirs.
- **It hands work down.** It doesn't do the work itself. It hands tasks to your other agents with `delegate` (see [Tasks](#tasks)), making one first with `create_agent` when none fits. It doesn't wait for them: it tells you what it handed out and is free for whatever you say next, and when their answers arrive it tells you what came of them. It hands tasks to any of your other agents; any other agent, to its [contacts](#contacts).
- **It is your face to your agents.** Under the `majordomo` approval policy, another agent's request for your approval goes to it first: in a chat you have with that agent, or from an agent at work on a task. In a conversation of its own, with your memory, it approves what it's sure you'd want, denies what's clearly against it, and asks you about the rest: anything that spends money, sends something in your name, shares private information or deletes things, and whatever it's unsure of. The request's entry in the box shows it deciding, then who decided and why, or what it asks you; you can always decide first. A request it asks you about notifies you and waits for you however long. One it hasn't decided in five minutes comes to you too. Its own requests, in its chats with you, and requests that need your own decision (`manage_connectors`, `add_custom_connector`) or come from people in your circles, come straight to you.
- **It suggests connectors.** When something you talk about would go better with one of this Pim's connectors, it suggests that one connector, and connects it if you want it. One you turn down it remembers, and doesn't suggest again unless you bring it up. If you're the admin, it can also add a connector this Pim doesn't offer yet, from its MCP server's URL (see [Connectors](#connectors)).
- **It runs this Pim's host, for the admin.** The admin's majordomo, and no other agent, can deploy, roll back, restart services and read their logs on the machine this Pim runs on (see [Host operations](#host-operations)).

### Skills

A skill is how you want work that comes up again done, written down for your agents: how to plan your training week, what goes in the weekly report. It has a name such as `weekly-plan`, a description, and instructions in Markdown, as in [Agent Skills](https://agentskills.io).

- **Your agents write them.** When you ask an agent to remember how to do something, or it has worked out with you a task you'll ask for again, it saves it with `write_skill`. The request shows the whole skill, and nothing is saved until it is approved under your approval policy, since a skill steers every later run that loads it. Settings → Tool permissions sets `write_skill` to Off, Ask or On, for every agent.
- **Installing published ones.** Ask an agent to use a skill from a GitHub repository, such as `https://github.com/owner/repo/tree/main/skills/name`, or from a folder in your files with a `SKILL.md`, and it installs it with `write_skill`'s `from` (or `install_skill`, which does the same), through the same request and approval. `from` comes alone: a request with `from` and any of `name`, `description`, `instructions` or `files` is refused, as is one with none of them. The name and description come from the SKILL.md's frontmatter, its instructions are saved as written there, and every other file beside it is copied exactly, hidden ones left out; the request shows the instructions and each file's source, size and SHA-256, and each copy is checked against its SHA-256 when you approve it. From GitHub it reads the folder at the commit its branch is at then, and the skill records that commit as its source; only `github.com` addresses of a repository's folder are read (no `.` or `..` parts, credentials or ports), through GitHub's API, which must name the commit by its full hash, and `raw.githubusercontent.com`, at that hash; a redirect is followed only within GitHub's API, and never from a raw file. From your files only folders under `/workspace` are read, and a link in the folder that leads outside it refuses the install. GitHub's API limits requests from one address, which Pim shares with others; when it refuses, the agent can clone the repository to your computer and install from that folder. An installed skill is labeled with its source when an agent loads it, as written there and not by you. Installing it again with its version updates it.
- **Whose skills an agent writes.** An agent writes and installs skills for itself. Your majordomo can also give `agent`, the id of another of your agents (as `update_agent` and `manage_connectors` take it), to write or install one for that agent; any other agent that gives another's id is refused. The request names both, such as "Ada installs the skill deck for Researcher from …". A write changes only a skill that is on the list of the agent it is for and on no other agent's: a skill two agents use is changed by neither (take it off the others on its page first), and an agent can't rewrite, or reuse the name of, one of your skills that isn't on its own list, whatever version it gives. Who wrote a version is a label, not who controls the skill. An agent working on a task from before tasks were chats writes no skills; one in a chat a task started writes them as in any chat.
- **A switch for each agent.** Each agent's page in Agents has Skills → Write and install skills, on by default, as agents always could. Off, that agent's chats aren't offered `write_skill` or `install_skill`, and no agent, your majordomo included, writes skills for it. It doesn't skip approval: `write_skill`'s Off, Ask or On still applies, and turning it Off stops every agent. Only you flip it, on the page or with `PUT /permissions`; no agent's tool changes it. Whether `write_skill` and the switches allow a write, who asked and whom it is for, and whose skills it touches are checked when the agent asks and again when the request is approved; a request whose agent was deleted or switched off meanwhile, or whose skill changed, saves nothing. The last check, the new version and the skill's place on the agent's list are one transaction: a change made before it ends means nothing is saved, and one made after it, such as taking the skill off the agent, is kept.
- **Each agent lists the skills it uses**, as it lists connectors. A skill an agent writes goes on the list of the agent it is for; `PUT /agents/:id` with `skills` gives one to another agent. Its chats list each skill's name and description, and the agent loads one with `read_skill` before the work it describes.
- **Supporting files.** A skill can carry up to 50 files beside its instructions, by paths such as `references/paces.md`, `scripts/convert.py` or `templates/report.docx`. The agent writes text files out, or copies any file from your files with `from_file`: the request names the copy's SHA-256, and when you approve it the file is read again and copied only if it hasn't changed. The agent reads a file with `read_skill_file`, or with `save_to` copies it back to your files as it is, to run a script with `shell` on [your computer](#your-computer) or fill in a template; agents are told about scripts only when you have one. A rewrite that gives no files keeps the ones the skill had. The files live with each version, not in your files folder, so only an approved `write_skill` changes them.
- **Where they are kept.** As with apps, a skill's name, description, instructions and versions are in your space's database, and its files' bytes in R2, each stored once under its SHA-256 however many versions and skills have it: a rewrite that keeps a file, or a restore, stores nothing again, and deleting a skill frees the files nothing else has. One version's files take up to 10 MB, and all skills' files up to 100 MB; they count toward the space's storage, and a version there is no room for is refused before it is written.
- **Versions.** Every write adds a version, and the latest 20 are kept. A rewrite names the version it read; one approved after the skill changed is refused, so two rewrites never overwrite each other unseen.
- **Seeing them.** Skills, in the sidebar's rail, lists them. A skill's page shows what it says at any version kept, who wrote each, and the agents that use it: click an agent to give it the skill or take it away. Restore an older version (it becomes the newest) or delete the skill there.
- **Not yet:** sharing skills through Discover, and serving them to other apps over MCP.

### Tasks

Agents hand each other work as tasks, with `delegate`: your majordomo to your other agents, and any agent to its contacts. Each task starts a chat of its own with the agent doing it, which opens with the task as a message from the agent that handed it out. It is your chat like any other: you can read along, talk with the agent there, stop it or delete it. Tasks follow [A2A](https://a2a-protocol.org/)'s task model, inside your space.

- **Finished chats are archived.** Once an agent has what it needs from a finished task, it archives that task's chat with `archive_task_chats`, so your chat list holds what is still current. An agent can also archive the chat it is in once its own work is finished; a chat still at work is archived the moment it stops, so its last reply does not list it again. Otherwise only chats of tasks it handed out, and only once they are done; the chat moves to Archived, and a follow-up that continues the task, or anything said in it, lists it again.
- **Nobody waits, unless it must.** `delegate` returns at once with each task's id, and the agent that handed them out goes on, or ends its turn, so you can keep talking with it. Tasks handed out together work at the same time, each in its own chat.
- **Waiting for answers.** An agent that can't reply without the answers, such as when you asked something only its contact knows, sets `wait`: its call is suspended, holding no memory and keeping nothing running, until every task is done, including one waiting for your approval, however long that takes; then the space wakes it, and it returns their answers in place of the update. Meanwhile what you say in the chat waits its turn. If you stop the chat, the answers come in an update once the tasks are done.
- **States.** A task is `working`, then `completed` with its agent's answer, `failed`, or `canceled`. While its agent waits for your approval it is `auth-required`.
- **Answers come back once.** The agent doing a task answers with `send_to_user`, as in any chat: what it sends while working on the task is its answer. When none of the tasks handed out together is working, their answers come to the agent that asked, in one message starting with "[Task update]", which the chat shows as a notice. A task waiting for your approval doesn't hold up the others: the update says it waits, and its answer comes in an update of its own. An agent that hands out tasks of its own while working on one answers its task once those have come back. What you say in a task's chat yourself is between you and its agent.
- **Compaction continues a chat** <a id="compaction-continues-a-chat"></a>in a new one, as Amp does with threads. When a chat nears its model's limit, it is left whole, and a fork of it is compacted into a chat of its own that carries it on: the sidebar lists it in the chat's place, marked as continued and with the chats the old one started under it, while the old chat is archived, and it opens with a line linking back and with the summary as its first message, followed by the latest messages kept as they were. A chat is continued once; after that its own compactions wait, and only a run that already overflowed its model's context is compacted in place, so that it can go on. Chats from tasks, group chats and visits are compacted in place as before, except that a chat a task started is carried on too. Work addressed to a chat that has been carried on goes to the new chat: a follow-up that continues a task starts in the new chat of the task's agent, and answers to tasks a chat handed out are given to the chat that carries it on, once the old chat is at rest, with none of its tasks at work and no call of it waiting for answers. A schedule or a connector's event for a chat that has been carried on goes to the new chat too, in a chat a task started too, whose tasks are recorded on the new chat from then on, while the old chat still shows who started it.
- **The sidebar shows where work went**, as Amp shows threads started by other threads: a task's chat sits under the chat it was started from, behind a ↳, with a small icon of the agent that started it on its agent's icon. The chat it was started from counts how many of its tasks are done, such as 2/3, and hides or shows them. A task's chat opens with a line saying who started it and from which chat, which it links back to. Chats tasks started don't count toward a limit on chats. While its task is working, a chat doesn't send push notifications, and a model error fails the task instead of holding the run for you to try again: the agent that asked hears it.
- **The chat that asked shows the work** where the agent handed it out, in a compact line like the notice its answers come in: whom it went to and how many of its tasks are done, marked while any is working or waiting for you. It opens to each task with its current state; tasks it hands out in turn show in their own chats. The line stays where work began, while the completion notice stays where the answer arrived, even when the conversation continued in between. Links jump between the task and its completion notice, and each task opens its chat. Stopping a task's chat fails the task; deleting it cancels the task: the tasks it handed out are canceled, its pending approval requests are denied, and the agent that asked hears it was canceled. Deleting the chat that asked cancels its tasks; their chats stay.
- **Approvals.** A task's tools ask before acting, in its chat, as in any chat; the agent waits for the decision, which its call returns.
- **Following up.** To carry on with a task that is done, an agent hands out another that `continues` it, in the same chat, where the earlier work is.
- **Tasks from before.** Tasks handed out before tasks were chats ran in conversations of their own that aren't chats, where the agent talked only with the one that asked and answered in plain text. They open read-only from their cards (`/chat/<id>?task=<task>`), with what they were asked and what their agent did, and one not done can be canceled there. A follow-up to one goes on in its conversation.

### Group chats

Every chat is a group chat, with one agent, its host, until another of your agents joins: you add it from the chat's "In this chat" menu, or someone mentions it by name, as `@Coach`, in a message you type or one the chat's agent sends. The message box offers the agents in the chat as you type `@`. That agent joins the chat and talks there itself, where you talk with it too. The chat's own agent is its host. Bring an agent in when you should talk with it; hand it a [task](#tasks) when it can work in a chat of its own and report back. See [`src/rooms.ts`](../src/rooms.ts).

- **Each agent is itself.** An agent in a group chat has a conversation of its own there, as a chat with it is, with its own instructions, connectors, skills, tool permissions and memory scopes; it isn't one of your chats in the sidebar.
- **Agents join knowing nothing of what came before.** The message that brought an agent in is the first thing it hears, so it should say what the agent needs. When it needs more, the agent reads what was said before it joined with `chat_history`, as a person scrolls back.
- **Taking an agent out.** The host takes an agent out once it has done what it was there for, with `remove_from_chat`, and you do from the menu of the chat's agents (`DELETE /sessions/:s/room/members/:agent`). It stops, the tasks it handed out are canceled and its approval requests denied, it hears nothing more said in the chat, and everyone left hears it left. Mentioned again, it joins afresh. Only the host and you take agents out, and the host stays.
- **Everyone hears everything.** What you say goes to every agent in the chat, and what an agent sends goes to the others, as a message starting "[From Coach]"; the chat shows it as Coach's, under its name and icon, and says when an agent joins or leaves. Each agent's memory is its own, but what it says in the chat, the others hear.
- **Who answers.** An agent answers when it is mentioned, by you or by another agent, and the host answers what you say without mentioning anyone. The rest each agent only hears, without taking a turn, and knows when it next speaks. There is an experimental `open` mode, off by default and with no switch in the app (`PUT /sessions/:s/room` with `open`): everything said wakes every other agent in the chat, and each answers only when it has something to add; one that is mentioned has to answer.
- **Agents can mention you.** In any chat, an agent gets your attention by mentioning you in a message it sends, as `@username` or by a name of yours: the one you gave when you joined, or that the account you joined with says (`yourName` in `GET /majordomo`), or your profile's display name. You get a notification of its own kind, `mention` in the API's notifications, shown with an @ badge in the notifications panel and pushed to your devices unless that chat is on screen. It is read when you read the chat. In the chat the mention is a chip, and while a message that mentions you is below what's on screen and you haven't had it in view, an @ button beside the one that scrolls to the bottom goes to it.
- **Agents can talk among themselves.** Agents mention each other, so one turn can set off another. Each turn counts how far it is from your last message, and nothing stops a chain yet: we're watching whether agents go round in circles in practice.
- **Who an agent brings in.** You bring in any of your agents. In a message it sends, your majordomo brings in any of them too, and any other agent its contacts.
- **What they share.** The agents in a group chat share its browser window, and their approval requests and the tasks they hand out show in the chat, labeled with the agent that asked. The chat shows who is at work, and Stop stops all of them. Deleting the chat stops them and cancels their tasks.

### Contacts

An agent lists its contacts, as it lists its connectors: others of your agents it hands [tasks](#tasks) to. You still talk to one agent. It hands its contacts tasks, they work at the same time, and it combines their answers when they arrive. A coding agent, for example, can be a planner with a coder for a contact, which it hands several parts of a change at once. Your majordomo has no list: it hands tasks to all of your agents.

- **Every agent is yours to see.** A contact is one of your agents like any other, in Agents with its own page, chats, connectors, skills and tool permissions. Its page lists its contacts, each of which can be taken off; Add contacts opens Network, at the top of Agents, with that agent chosen. Network draws all your agents as one map, your majordomo in the middle, and brings out the chosen agent's lines: drag a line from one agent to another, or use + on an agent, to make it a contact, and click a line or use × to take one away. Or ask an agent in chat: `update_agent` adds and removes contacts by role or name, without asking.
- **Contacts answer the agent that asked.** What a contact sends in the chat its task started goes back to the agent that handed it out, which tells you what came of it. You can read along there, and talk with the contact yourself.
- **Work doesn't go round in circles.** No agent is handed a task by one working, directly or not, on a task it handed out, and a chain of tasks ends three deep: an agent that far from your chat hands out none.
- **Copies.** Publishing an agent publishes its contacts with it, and theirs, by role; the template's page lists each in full. Making it your own, or joining a Pim whose admin gives everyone that agent, gives you a copy of each, as contacts of the copies that had them. A copy keeps the name it came with, which you can change at any time. One whose role one of your agents already has gets a role of its own, such as "Physio (Marathon coach)", and one whose name is taken gets a name of its own the same way, such as "Physio (Marathon coach)". Each comes with its look, uploaded icon included.
- **Teams before.** Agents once had teams: members with instructions of their own that worked with their agent's connectors. Each became an agent of its own, with its agent's connectors, skills and connector tool permissions, and one of its contacts; its tasks are the new agent's. A member's list of tools has no counterpart, and was dropped.

## Talking with Pim from other apps

Claude, ChatGPT and other MCP clients can talk with your [majordomo](#your-majordomo). Add `https://<your Pim>/mcp` to one as a custom connector (Settings → Account → MCP clients shows the address). It works like Amp's Puck over MCP: the server has one tool, `pim`, which sends a message to your majordomo and returns its reply.

- **Connecting signs you in.** The client registers itself with Pim ([dynamic client registration](https://datatracker.ietf.org/doc/html/rfc7591)) and opens Pim's `/authorize` page, where you sign in if you aren't already and see who is asking and where access goes. Allow sends it back with a code it exchanges for tokens. Pim is the OAuth authorization server for its own MCP server, as the [MCP authorization spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) asks, with [`@cloudflare/workers-oauth-provider`](https://github.com/cloudflare/workers-oauth-provider): discovery at `/.well-known/oauth-protected-resource/mcp` and `/.well-known/oauth-authorization-server`, registration at `/oauth/register`, and tokens at `/oauth/token`, with PKCE. Clients, grants and hashed tokens are kept in the `OAUTH_KV` namespace, which deploying creates (see [`src/mcp-auth.ts`](../src/mcp-auth.ts)).
- **Access lasts while it's used.** An access token lasts an hour, and the client refreshes it. A connection ends after 30 days without use, or when you disconnect it in Settings → Account → MCP clients.
- **API tokens work too**, for clients without OAuth: send one from Settings → API tokens as `Authorization: Bearer <token>`.
- **A new chat per call, unless the client continues one.** Every reply names its conversation, a chat with your majordomo that you can also continue in Pim; a call that passes it back as `conversation` continues that chat, and one without it starts a new one. Only your majordomo's chats can be continued this way.
- **It hands work down as in the app.** Your majordomo hands bigger work to your other agents as [tasks](#tasks), and the reply waits for their answers too: it has everything the majordomo said, about the tasks as well. Work waiting for your approval comes back to its chat later, so asking again in the same conversation ("did Concierge book it?") tells you how things went.
- **A reply waits up to 45 seconds.** A turn still going after that answers "still working", or what the majordomo said so far and that it is still waiting on some of the work; ask again in the same conversation in a little while, and that message is answered once the turn before it ends.
- **Everything else works as in the app:** approvals, usage limits and tool permissions.

A connection opens only `/mcp`; an API token opens your whole API, so give it only to clients you trust.

## Coding threads

A coding thread is a coding agent that works on one GitHub repository, on a branch of its own (`pim/<task>-<id>`), in a workspace the deployment's backend makes for it (see [Workspaces for coding threads](#workspaces-for-coding-threads)). It belongs to the space that started it, and nobody else reaches it. People start and follow threads in the web app, at `/coding/<id>`, or through the API ([docs/coding-api.md](coding-api.md)); every agent can with its `coding_*` tools, from the `coding` extension in `pim.config.ts`.

- **Starting returns at once.** A thread waits in its space's queue while the space's workspace slots (3 unless the backend says fewer) are taken, and says its place and what it waits for; it starts on its own once it has one. Its task, and each message after, is one turn.
- **Its model** is the one you give, by one of your [model providers](#model-providers), or else your space's default model, as agents without a model of their own use it. A ChatGPT plan model can't run coding threads: on one, the thread runs on the deployment's default instead. It spends at most its budget ($3 unless given) and stops there until continued with a bigger one.
- **Its coding agent** is Pi, Pim's own, unless you choose Claude Code or Codex: Anthropic's `claude` or OpenAI's `codex` CLI, unmodified, run in the thread's workspace with your own Claude or ChatGPT subscription, which you connect once in the coding page ([docs/coding-claude-code.md](coding-claude-code.md), [docs/coding-codex.md](coding-codex.md)). Mistral Vibe and Amp connect with an API key of yours instead, saved once in the same place; Pim keeps it encrypted and never shows it again. Mistral's `vibe` CLI runs the same way ([docs/coding-vibe.md](coding-vibe.md)), billed to your Mistral account, and so does Amp's `amp` CLI, with your Amp access token ([docs/coding-amp.md](coding-amp.md)). Codex and Amp report tokens, not dollars, so on them the budget is a ceiling of 1,000,000 tokens a dollar.
- **The agent that started it hears of it.** When each of its turns ends, completed, failed or cancelled, the chat the agent started it from gets a message saying how it went, what it spent and what the coding agent last said, as a scheduled task wakes a chat, once for each turn. A deleted chat isn't woken. A thread you started yourself only logs it.
- **Cancelling** a thread that waits for its turn takes it out of the queue; **aborting** stops the turn under way; **archiving** ends it and deletes its workspace, keeping what it said, its diffs and its test runs.
- **Pushing from the app asks you every time; an agent's `coding_push` and `coding_merge` don't.** Push in the app readies a push of the thread's latest checkpoint while its workspace runs, and files an approval naming the branch, commit and size; Pim pushes once you approve (see [GitHub for coding threads](#github-for-coding-threads)). The agent's `coding_push` and `coding_merge` run at once, with no approval, so the safety is in the mechanics: only `pim/` branches or a merge, never a force push, a conflict stops before anything is pushed, and the result carries the latest test runs. `coding_merge` ships the checkpoint to the default branch: the thread's commits are fast-forwarded or rebased onto the latest default branch in its workspace (a conflict stops it before anything is pushed, and the agent steers the thread to resolve it), the default branch only ever moves forward, and the thread's own branch is updated too. Without the GitHub App set up, it says so before asking anything.
- **Its environment is prepared once and kept.** Before a thread's first turn, the toolchains and dependencies the repository's files pin (`go.mod`, `package.json`, `.nvmrc`, `pyproject.toml`, `uv.lock`, `rust-toolchain.toml`, `mise.toml`, a dev container's features and more) are installed in its workspace with mise, a failed step recorded rather than failing the thread, and the coding agent is told the commands the repository checks itself with, found in its mise tasks, Makefile, `package.json` and GitHub or Gitea workflows; see [coding-environment.md](coding-environment.md), which says what isn't covered. A repository with a setup script, `.pim/setup.sh` in it or the one you set for it (`PUT /api/coding/repos/:owner/:name/settings`), has it run after that, before the thread's first turn, with bash in the checkout, as the workspace's user, under its egress allowlist and limits, for at most 15 minutes, and with no secret of Pim's (git still goes through the broker). The workspace is then kept as your snapshot of that environment (on the sandbox manager; Cloudflare Sandbox keeps none yet), keyed by you, the repository, the provisioning steps with the versions they install, the script, its lockfiles (`pnpm-lock.yaml`, `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `bun.lock`, `Cargo.lock`, `uv.lock`, `poetry.lock`, `go.sum`, `requirements*.txt` and mise's configuration, at the root and one directory down) and the workspace image. Your next thread with the same key starts from the snapshot, fetches and checks out its own branch over it, and runs nothing; two threads that need it at once build it once, the other waiting for it. A snapshot is kept only when every provisioning step worked and restoring it (reckoned at 8 MB a second) would be quicker than the setup was, so starting from one is never slower than setting up again. Otherwise it is deleted with your older snapshots of the repository, and for 30 days each of your threads with that key runs the setup itself and takes none, which is quick because package managers' downloads are kept in a cache of yours for the repository that outlives workspaces. A setup that fails, or a snapshot that can't be restored, never stops a thread: it goes on as it would without one, and its `environment` says what happened. Nobody else's thread ever finds your snapshots. A rebuild (`POST /api/coding/threads/:id/environment/rebuild`) deletes the snapshot and provisions and runs the script again in the thread's workspace between turns. See [`src/coding/environment-cache.ts`](../src/coding/environment-cache.ts).

## Sharing

You can let others on your Pim message your agent from their own space. Sharing → Circles: make a circle (Family, Close friends, Acquaintances), add people by their username, and choose what the circle can use: each connected connector's tools (Off, Ask or On, as in [Tool permissions](#tool-permissions)) and the [memory scopes](#scopes) it may read: everyone's and those you named. Everything starts off. Until someone else has an account on your Pim, the app hides Sharing.

- **Their conversation runs in their space.** Someone you share with finds your space under Shared with you. Their conversation with it (a visit) is a chat in their own space, on their own model and usage: whoever sends the messages pays for them. It sees a brief your space sends before each of their turns: what their circle may use, the memory scopes it may read, and your time zone. Nothing of their own space (its tools, memory or connectors) is in that conversation, and nothing of yours is in their other chats.
- **The boundary is in your space, at every call.** Each tool in a visit is a call into your space (`guestCall`), which checks again that they're in a circle, that the circle is on, and that the tool is allowed for it now. A tool turned off, a connector that changed a tool since you allowed it, or a person you removed is refused, whatever their space was told before.
- **Ask means you decide.** A call to a tool set to Ask files an approval that names who asked and through which circle, and notifies you. Their conversation goes on; your decision arrives in it later as a message. Unanswered, it is denied after a day: a guest's request is never approved by a timeout. **Always approve for Family** sets the tool to On for that circle.
- **Limits.** Up to 20 circles and 200 people in them. Each guest can make 200 calls into your space a day, so your connectors' own limits stay yours. Sharing → Recent activity lists what guests used, asked for, or were refused.
- **Taking it back.** Remove someone, or turn a circle off, and their next turn is refused. Deleting a circle forgets its permissions.
- **Apps too.** Share an app with circles from its page, and their people find its latest version under Apps → Shared with you, running in their own space with their own model and data; what it keeps for everyone (`pim.shared`) stays in yours. See [docs/apps.md](apps.md#sharing).

### Public bots

The admin can share an agent as a bot with anyone, like a chat app with one assistant: Share as a bot, on the agent's page, makes a public link, `/b/<id>`, to post anywhere. Only the admin can, since the deployment pays for what guests send.

- **The link shows the bot** (its name, description, look and author, never its instructions) and lets anyone join as a guest: their name, recovery codes and a passkey, or a Google, GitHub or single sign-on account when the admin set those up. It works whatever `PIM_REGISTRATION` says, within `PIM_MAX_ACCOUNTS` and `PIM_REGISTRATIONS_PER_ADDRESS`. Someone who joined before signs in again there.
- **A guest's account is a space of their own** that holds a copy of the bot, with the agents it hands tasks to, and none of the agent the admin gives everyone. Their app is the bot alone: their chats with it, a new chat, how many of today's messages are left, signing out and deleting the account. Every chat they start is with the bot. The Worker lets a guest reach only what chatting needs (chats, approvals, apps, files, notifications, settings and the tools the bot shares); never agents, models, memory, a computer, sharing, publishing, Discover, MCP clients or the admin's API. Nobody finds a guest to add to a circle, and guests don't count as someone to share with.
- **Its tools.** The bot's connectors are the admin's, not the guests': a guest's copy connects none, and asks nobody to sign in. Instead, Share as a bot lists what the agent can use in the admin's space, by connector and tool: the tools of its connected connectors, and `generate_image` while the admin's space makes images (it needs their computer). The admin sets each tool Off, Ask or On (a connector's switch turns all of its tools on or off); nothing is on until they do. A tool set to Ask runs only once the admin approves each call: the guest's call files a request in the admin's space and waits, suspended, for the answer. The request waits at the top of the admin's Notifications, as "guest (bot) asks", needs their own decision every time (no "always approve"), and is denied if they don't answer within a day. Approved, the call runs and the guest's chat goes on with its result; denied, with the admin's note if they left one. A guest who stops the chat meanwhile leaves nothing to approve: the request is then denied without running. A guest's copy gets a stand-in for each tool switched on, which the admin's space runs, as the admin: with their connector connections, such as their Firecrawl sign-in, and their image model, the ChatGPT plan's included when it's signed in for images. The admin's space checks each call against what the bot shares at that moment, so switching a tool off stops it at once. An image a guest asks for is saved on the admin's computer, under `/workspace/bots/<bot>/<guest>/`, and the guest sees it only in their chat, which reads it from there: never another guest's, nor any other file, and not while the computer is offline. The computer's own tools (files, shell, the browser and the desktop) are never offered: they would open the admin's machine to anyone.
- **Messages and tool calls a day.** Each guest may send the bot as many messages a UTC day as its link allows (50 unless the admin says otherwise), counted as the space's runs, and make as many calls to the tools it shares as it allows (20 unless the admin says otherwise; 0 for none). A call past that is refused in the guest's space, before it reaches the admin's, and the bot is told the calls are used up until midnight UTC. The deployment's other `PIM_LIMIT_*` limits apply too.
- **Its model.** The admin picks the model guests use from what this Pim offers everyone: the deployment's default, the Workers AI models `PIM_MODELS` allows, and the providers the admin added for everyone. Never the admin's ChatGPT plan or own providers, which are theirs alone. A model that later goes away, such as a provider the admin removed, leaves guests on the default.
- **Updating it.** Update, beside the link, shares the agent as it is now: its name, description, instructions, connectors and look, with the daily messages, tool calls, model and tools chosen there, as each tool is now. Each guest's copy follows on their next request, keeping their chats. The agents that came with it stay as they came.
- **Turning it off.** Turn off link, deleting the agent, or deleting the admin's account makes the link answer `404` and lets nobody else join. Guests keep their accounts and can read their chats, and their bot answers nothing more.

## Develop

```sh
pnpm test        # Vitest in workerd, with pi-ai's faux model, then the web app's tests; no Cloudflare account needed
pnpm test:live   # live checks against real MCP servers (Hugging Face's); needs the network
pnpm typecheck   # also generates the web app's route tree, so it works on a fresh checkout
pnpm types       # regenerate worker-configuration.d.ts after editing wrangler.jsonc
pnpm lint        # Biome, for the web app
pnpm check       # typecheck, lint and test, as CI does
pnpm preview     # a Pim with a stand-in model and a passkey-free sign-in, at http://localhost:8787, with no Cloudflare login (see docs/instance.md)
```

The web app is in [`web/`](../web), with its own README. Sign-in, with passkeys and other providers, is in [`src/auth/`](../src/auth).

To add tools every agent gets, apps, or widgets, write an extension and list it in `pim.config.ts` (see [docs/extensions.md](extensions.md)). To add a tool, write a pi extension in `src/extensions/` and install it in `Pim`'s harness factory. A tool with effects outside the conversation should be a `GatedAction` (see `src/extensions/approvals.ts`) so it runs only after approval.
