# Pim v2 operations

How Pim v2 is deployed, observed, migrated from the Cloudflare deployment, backed up and load-qualified. The code is in `packages/v2-ops/`, the manifests in `deploy/`, the command-line tools in `scripts/v2-*/`.
What was run, what was only read, and what is not yet proven is in [Verification status](#verification-status); read that before relying on a claim here.

## Layout

| Path | What it is |
|---|---|
| `packages/v2-ops/src/fence-worker/` | The inert maintenance and export Worker for the cutover (a separate entrypoint, never a product flag). |
| `packages/v2-ops/src/migration/` | Snapshot format, exporter, conversation-family split, quiescence plan, importer, checksum auditor, report. |
| `packages/v2-ops/src/backup/` | Physical base backup, point-in-time restore, post-restore safety pass. |
| `packages/v2-ops/src/observability/` | Redaction, Prometheus metrics, OpenTelemetry spans, event-loop and PostgreSQL pool signals. |
| `packages/v2-ops/sql/` | Migrations `0500`-`0599`: cutover record, external-operation ledger, due work, remote threads, import landing tables, role grants, restore fence. |
| `deploy/compose/`, `deploy/k8s/`, `deploy/observability/` | Compose stack, Kustomize manifests, Grafana dashboard, Prometheus rules, runbooks. |
| `scripts/v2-migrate/`, `scripts/v2-backup/` | Entry points for the tools above. |

The package imports `@pim/v2-contracts` and nothing else from Pim, and nothing from the Worker (the Cloudflare version, removed from this branch; the git tag `v1-final` is its last commit). It is aligned with `origin/pim/v2-canonical` (`0ba6fd3`):

- **Migrations:** `src/pg/migrate.ts` runs canonical's `0001_foundation.sql` first, then this package's band (0500-0599), into canonical's ledger `public.pim_schema_migrations (number, name, checksum)`. Every directory is checked against its band with `validateMigrationFiles`; `scripts`/CLI `sql-migrate --dir runtime=...` adds other workstreams' directories. A file edited after it was applied is refused.
- **Schema:** operations has no schema in the contracts, so it creates `pim_ops` (0500). Its tables are the cutover record, the external-operation ledger, due work, remote threads, the restore fence and the **import landing tables** (identity, authentication, secrets, pi history, chats, objects, verbatim legacy rows). Landing tables use `owner_id`, the column canonical's row-level security policies compare with `public.pim_current_owner_id()`; they have no policies yet. When the application and runtime workstreams land their own tables in `pim_app` and `pim_runtime`, the importer's targets move there; the audit's checks stay the same.
- **Roles:** 0502 grants `pim_ops` to `pim_gate`, `pim_runtime`, `pim_live`, `pim_forge` and `pim_maintenance` as 0001 defines them (the Gate and Runner open secrets; Live and Forge never read `secret_envelopes`; only maintenance writes the cutover record and the restore fence).
- **Ids:** an owner id is `o_<chars>` (`OwnerId`): a legacy id that already has that shape is kept, any other is prefixed `o_` (recorded in `pim_ops.owner_map`, audited). A partition id is a UUID (`PartitionId`): a version-5 UUID of the owner and the family's label, so a re-import gives the same ids. Conversation 1 stays `ROOT_CONVERSATION_ID` in the owner's home partition.
- **Environment:** `PIM_ROLE`, `PIM_PUBLIC_URL`, `PIM_DATABASE_URL`, `PIM_APP_DATABASE_URL` and `PIM_FORGE_DATABASE_URL` (Runner only: its agent tools read the application and coding schemas through the gate and forge logins), `PIM_NATS_URL`, `PIM_S3_ENDPOINT`, `PIM_S3_BUCKET`, `PIM_S3_REGION`, `PIM_RUNNER_HOLDER_ID`, `PIM_POOL_<NAME>_MAX`, exactly as `loadProcessConfig` reads them; tests run every Compose service's and every Kubernetes Deployment's environment through it. Additions this package makes, which `loadProcessConfig` ignores: `PIM_S3_ACCESS_KEY`/`PIM_S3_SECRET_KEY`, `PIM_INGRESS_SECRET`, `PIM_KEK_*`, `PIM_METRICS_PORT`, `PIM_DRAIN_WINDOW_SECONDS`, `OTEL_*`.

## The role contract

One Pim image runs one role per container, chosen by `PIM_ROLE`: `gate`, `live`, `runner`, `forge`, `canvas`, `relay`, `maintenance` (`PIM_ROLE` of `@pim/v2-contracts`; the migrator is the one-shot SQL runner, not a role). Both deployments assume the same contract; the roles themselves belong to the other workstreams.

- `GET /healthz` (process is up) and `GET /readyz` (can serve) on `PIM_HTTP_PORT`; Prometheus metrics on `PIM_METRICS_PORT` (9464) at `/metrics`.
- Configuration is the environment listed above (`loadProcessConfig`), plus `PIM_CONTENT_ORIGIN`, `PIM_APPS_ORIGIN` and `PIM_LOGO` (the logo at the top of the app's sidebar: an https or `data:` image address).
- Envelope keys: `PIM_KEK_CURRENT` names the key that wraps new data keys; keys come from `PIM_KEK_<id>` (Compose) or files named `<id>` in `PIM_KEK_DIR` (Kubernetes).
- The Runner, on `SIGTERM` or `POST /drain`, stops claiming work and hands its partition leases back within `PIM_DRAIN_WINDOW_SECONDS` (90).
- A Runner must refuse to claim work while the newest row of `pim_ops.ops_restore` is not `reconciled`, and must never execute a `pim_ops.external_operations` row whose status is `needs_reconciliation`, nor a `pim_ops.pi_tasks` row with a `hold`.

## Installing and updating

Pim publishes its images, so an instance updates the way a self-hosted app does: it pulls them, and nothing is built from a git checkout. The Compose files and scripts still come from the checkout (`git pull` brings those); the image is what `pim.sh update` changes.

| Image | Built from | Used by |
| --- | --- | --- |
| `ghcr.io/ajac-zero/pim` | `deploy/Dockerfile.v2` | every role of the stack |
| `ghcr.io/ajac-zero/pim-computer` | `deploy/Dockerfile.computer` | the `local-computer` profile |

Both are `linux/amd64` and `linux/arm64`, carry `org.opencontainers.image.version` and `.revision`, and are published by `.github/workflows/publish.yml`. **Channels and tags:** `stable` is the newest release; a tag `vX.Y.Z` on a commit of `main` publishes `X.Y.Z`, `X.Y` and `stable`. each push to `main` is built as `sha-<first 12 characters of the commit>` while CI runs, and `edge` is moved to that same image (same digest and labels) once CI and the Compose smoke test on the commit have passed, so `edge` is the newest push to `main` that passed both. Nothing is published for `pim/*` branches or pull requests.

**First install from the published image.** `init-env.sh` writes `PIM_IMAGE=ghcr.io/ajac-zero/pim:stable` and `PIM_CHANNEL=stable` by default:

```sh
deploy/compose/init-env.sh https://pim.example.com
deploy/compose/pim.sh up -d --wait          # pulls the image; migrations run first
```

**Switching a stack built from source to the published image** (its `.env` has `PIM_IMAGE=pim:v2` or similar): `deploy/compose/pim.sh update stable` backs the stack up, pulls the image, and switches `PIM_IMAGE` to it, keeping the old reference in `PIM_IMAGE_PREVIOUS`; if it fails, the source-built image is put back. Add `PIM_CHANNEL=stable` (or `edge`) to `.env` so later updates need no argument. To keep building from source, leave `PIM_IMAGE` on your own tag and build it as before (`docker build -f deploy/Dockerfile.v2 -t pim:v2 .`); the development overlay and CI's `compose` job do.

**Updating.**

```sh
deploy/compose/pim.sh update --check        # reports whether a newer image exists for the channel; changes nothing
deploy/compose/pim.sh update                # the channel in .env (PIM_CHANNEL, default stable)
deploy/compose/pim.sh update 1.4.2          # a channel (stable, edge), a version (1.4.2, 1.4) or sha-<12 characters>
```

`update` pulls the image; takes a backup with `scripts/v2-backup/compose-backup.sh` into `PIM_BACKUP_DIR` (default `deploy/compose/backups/`; after a new one is taken, ones older than `PIM_BACKUP_KEEP_DAYS`, 14 by default, are removed, the newest always kept; 0 keeps them all) before anything changes, so the stack must be running; writes the image to `PIM_IMAGE` pinned by digest (`ghcr.io/ajac-zero/pim:stable@sha256:…`); and runs `pim.sh up -d --wait`, which runs migrations first. If that or the health wait fails it puts the previous image back, brings the stack up again and exits non-zero. Its last line of output is one JSON object, and the exit status is non-zero for `rolled_back` and `failed` (nothing changed: the pull or backup failed):

```json
{"event":"pim.update","from":"ghcr.io/ajac-zero/pim:stable@sha256:aaa…","to":"ghcr.io/ajac-zero/pim:stable@sha256:bbb…","result":"updated"}
```

`result` is `updated`, `unchanged` (the channel still points at the running image) or `rolled_back`. `update --check` prints `{"event":"pim.update.check","channel":…,"current":…,"latest":…,"available":true|false}`. With `PIM_COMPUTER_URL` set, the same update also pulls `pim-computer` and sets `PIM_COMPUTER_IMAGE`; `PIM_REPOSITORY` (default `ghcr.io/ajac-zero/pim`) names the repository to pull from, for a mirror.

**Rollback, and the additive-migration rule.** Migrations cannot be undone: the old image runs against the schema the new one migrated. So **every migration must be additive and compatible with the previous release**: add tables, columns (nullable or with a default) and indexes; never drop or rename a column or table, change a type, or tighten a constraint the previous image writes against in the same release. Do that destructive step in a later release, after no supported image reads the old shape (expand, then contract). A rollback by `update` is therefore safe only for releases that follow the rule; one that cannot (a release that must break it says so in its notes) is rolled back by restoring the backup `update` took: `scripts/v2-backup/compose-restore.sh <backup dir>` after putting `PIM_IMAGE_PREVIOUS` back in `PIM_IMAGE`. To go back by hand to an earlier image, `pim.sh update <version>` works the same way.

**Nightly updates (optional).** `deploy/compose/systemd/pim-update.timer` runs `pim.sh update` at about 03:30 each night. Before it, the service fast-forwards the checkout (`git pull --ff-only`), because `pim.sh` and hostopsd run from the checkout rather than the image, and afterwards it restarts hostopsd if it is installed; keep the checkout on a branch that tracks origin, such as `main`. Edit `User`, `WorkingDirectory`, `ExecStartPre` and `ExecStart` in `pim-update.service` to the account that owns the checkout (it must be in the `docker` group) and the checkout's path, then:

```sh
sudo cp deploy/compose/systemd/pim-update.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now pim-update.timer
systemctl list-timers pim-update; journalctl -u pim-update   # the last line of a run is the JSON result
```

Follow `stable` for this; `edge` is every push to `main`.

**Making the packages public (once).** The first push of an image to GHCR creates the package **private**, linked to the repository. A package owner has to open github.com → the organisation or user → Packages → `pim` (and `pim-computer`) → Package settings → Change visibility → Public, once, or instances cannot pull without `docker login ghcr.io`. The workflow needs no secret beyond the `GITHUB_TOKEN` it is given (`packages: write`). Publishing starts with the first push to `main` that contains `publish.yml`.

## Compose (homelab)

A trial on one machine, over plain HTTP on `127.0.0.1:8088` (a browser treats `localhost` as secure, so passkeys work):

```sh
deploy/compose/init-env.sh http://localhost:8088 --image pim:v2-local   # writes deploy/compose/.env with random secrets and keys
docker build -f deploy/Dockerfile.v2 -t pim:v2-local .
deploy/compose/pim.sh up -d --wait          # caddy, postgres 17, pgbouncer, nats, seaweedfs, migrator, gate, live, runner, forge, maintenance
curl -s -X POST -H 'origin: http://localhost:8088' http://localhost:8088/auth/setup-link
deploy/compose/pim.sh logs gate | grep -o 'http[^ "]*#claim=[^ "]*'   # open it, make the admin's passkey, save the recovery codes
```

For a real hostname, run `init-env.sh https://pim.example.com` instead: `pim.sh` then uses `compose.yaml` alone and Caddy gets a certificate. `pim.sh` is `docker compose` with this directory's files (`compose.local.yaml` when the URL is `http://`, `compose.dev.yaml`, which mounts this checkout's sources, when `PIM_DEV=1`). A model: either connect one in Settings → Model (the ChatGPT plan sign-in, or a provider with an API key), or set `PIM_AI_GATEWAY_URL`, `PIM_AI_GATEWAY_KEY`, `PIM_AI_GATEWAY_MODELS` and `PIM_DEFAULT_MODEL` in `.env` for an OpenAI-compatible endpoint. Scale Runners with `pim.sh up -d --scale runner=3`; optional profiles are `canvas`, `local-computer`, `coding` and `observability`.

**Notifications and Web Push.** The bell lists what the maintenance role announces from committed rows: an approval waiting, and an agent's reply that mentions the person (`@username` or the name they gave). Settings → General → Alerts decides which replies also reach devices: "Only what needs me" sends mentions, approvals and an answer to something the person said, once, if they have not read it by then; "Every message" sends every reply. Device alerts are Web Push: `init-env.sh` writes a VAPID key pair as `PIM_VAPID_PUBLIC_KEY` and `PIM_VAPID_PRIVATE_KEY` (base64url) into `.env`, and `PIM_VAPID_SUBJECT` (default `PIM_PUBLIC_URL`) says who the push service may contact. **Keep the pair with the backups and never change it**: a browser's subscription is bound to the public key, so a new pair silently stops every device until each opens the app and subscribes again. The keys live in the environment, not the database (so nothing is sealed there); with them empty `/api/push/key` answers "unavailable" and the bell still works. Messages are queued in `pim_app.push_queue` and sent with retries by maintenance, so a restart loses none; endpoints must be https on a public address (`PIM_PUSH_ALLOW_PRIVATE=1` relaxes that for a stand-in service in development). Browsers show a push only on https or `localhost`. Email is not built: Settings shows it as unavailable.

`scripts/v2-compose/smoke.sh` builds the image and boots the stack from nothing with a stand-in model (`scripts/v2-compose/fake-model.mjs`), then claims the first account, chats with the majordomo, parks and approves a tool call, round-trips an object, backs up, writes, restores and chats again; CI's `compose` job runs it on every push.

Connectors (Gmail, Google Drive, Spotify, OAuth-protected MCP servers, watches) need only the OAuth clients named in `env.example`, and `PIM_PUBLIC_URL` as the address the services call back; see [architecture/v2-connectors.md](architecture/v2-connectors.md), and `scripts/v2-compose/fake-connectors.mjs` to try them with no real provider.

No Kubernetes, Temporal, Cloudflare or AWS service is involved. The core stack runs with every optional profile off. PostgreSQL runs with `fsync`, `full_page_writes` and `synchronous_commit` on, and nothing in the stack turns them off (a test fails if anything does). `postgres/init/00-roles.sh` creates the five NOLOGIN roles of `0001_foundation.sql` and one login per process kind (`pim_gate_login`, `pim_runtime_login`, `pim_live_login`, `pim_forge_login`, `pim_maintenance_login`), each a member of exactly its role, with the connection limit and the statement timeout that kind has in `DEFAULT_POOL_BUDGETS` (set on the role, since PgBouncer does not pass `statement_timeout` through), plus `pim_migrator`, the only role that creates objects (no login is superuser or `BYPASSRLS`); applications connect through PgBouncer in transaction mode, while the migrator and maintenance connect directly (advisory locks and long statements do not belong in transaction pooling). The proxy sets `X-Pim-Client-IP` and `X-Pim-Ingress-Secret` on every request.

The Gate serves the web app (`web/dist`, built into the image) and answers the web app's routes, in the shapes the Cloudflare version had, through `packages/v2-server/src/compat/`, which are tried before the Gate's own routes. What the web app asks for and v2 does not have yet answers as empty or 501, never with invented data: see the deferred list in `docs/architecture/v2-implementation-status.md`.

### Deployment settings

A deployment is set with variables in `deploy/compose/.env` (`env_file` gives every one of them to every role; each is listed, with what it does, in `deploy/compose/env.example`). Settings → Deployment (the admin's) shows what Pim read, with a problem beside any variable it could not read; a variable that cannot be read counts as its default, except caps and limits, which count as 0 so that a typo never lifts them. An empty variable is unset.

- **Joining.** `PIM_REGISTRATION` is `invite` (the default), `open` or `closed`; `PIM_MAX_ACCOUNTS` caps the accounts that are not deleted; `PIM_REGISTRATIONS_PER_ADDRESS` (3) is how many accounts one address makes in a day. Unset, `PIM_REGISTRATION` is whatever the admin's switch says (`POST /api/admin/registration`, `{"open": true}`); set, it decides and the switch is refused. The first account, the admin's, needs the setup link in the Gate's log (`POST /auth/setup-link`) whatever the mode. A registration nobody makes a passkey for lapses after a day and gives back its username, its invite and its place under the cap; its setup code lasts the day.
- **Usernames** are 3 to 32 lowercase letters, digits and single hyphens between them, and not one of about seventy reserved names (`admin`, `support`, `pim`, `api`, ...). Names made before this rule keep working; a name is never given to a second person once its account has lived.
- **Sign-in providers** are `PIM_GOOGLE_CLIENT_ID` and `_SECRET`, `PIM_GITHUB_CLIENT_ID` and `_SECRET`, and `PIM_OIDC_ISSUER`, `_CLIENT_ID`, `_CLIENT_SECRET` and `_NAME`. A provider with only some of them stays off and Settings says what is missing.
- **Models:** `PIM_DEFAULT_MODEL`, `PIM_MODELS` (the allow-list: of the gateway's models, people may choose these and the default), `PIM_UTILITY_MODEL`, `PIM_MEMORY_MODEL`, `PIM_IMAGE_MODEL` and `PIM_MEMORY_LINES`. The limits are `PIM_LIMIT_*` and the rate limits `PIM_RATE_*`.
- **Email** is sent through your own SMTP server: `PIM_SMTP_URL` (`smtps://user:password@host:465`; `smtp://host:25` upgrades to TLS when the server offers it, and a password is sent only over TLS or to the same machine) and `PIM_EMAIL_FROM` (an address that server lets Pim send as). Both are needed; Settings → Deployment shows them, with the password hidden. Each person confirms one address in Settings with a code, and Pim emails only that address (`docs/reference.md`, Email). Set them for the Gate and the Runner alike (`env_file` does).

## A computer on the same machine

A personal computer is how agents get a shell, files, a browser and a desktop: `computer/pim-computer.ts` dials out to the stack's public address (`/api/computer/connect`, WebSocket) with a `pimc_` token and answers the Relay's calls. It is **outside the control-plane security boundary**: it runs arbitrary commands, so it never gets a database, NATS, object-store, key-ring or control-plane credential, and nothing in the stack trusts it beyond what its own owner's space may do. Two ways to run one beside the stack; both pair the same way.

1. **Pair.** Sign in, open Settings → Computer, choose to connect a computer, and copy the `pimc_…` token (shown once; `POST /api/computer`). One person has one computer: pairing another replaces it. The token is `pimc_<owner>_<secret>`, because the triggers runtime on the computer binds to its space from its token alone.
2. **Run it, either:**
   - **Compose profile `local-computer`** (the stack's own host, in a container): `deploy/compose/pim-computer.sh pimc_…`, or `PIM_API_TOKEN=pim_… deploy/compose/pim-computer.sh` to pair and run in one step (it calls `POST /api/computer` with a personal API token and replaces the person's computer). The script writes `PIM_COMPUTER_URL` and `PIM_COMPUTER_TOKEN` into `deploy/compose/.env`, builds the computer's own image, starts it and waits until it has connected; `pim-computer.sh stop` stops it. By hand: set those two variables and `deploy/compose/pim.sh --profile local-computer up -d --build pim-computer`. `PIM_COMPUTER_URL` is the stack's address *as the container reaches it*: for the plain-HTTP trial stack `http://caddy:8088` (Caddy joins the container's own network there, because its published port is bound to 127.0.0.1, which a container cannot reach through the host's address; `compose.local.yaml`), for a real hostname its public `https://` address, with `PIM_COMPUTER_HOST_ALIAS` set to that hostname so it resolves to the Docker host when the host has no hairpin NAT (the script does both).
     The `pim-computer` service builds `deploy/Dockerfile.computer` (Node, `computer/` and a headless Chromium; none of the server), has no `env_file`, joins none of the stack's networks (its own `computer` network), runs as the unprivileged `node` user with a read-only root and no capabilities, and writes only to two volumes: `pim-files` (`/workspace`, the person's files) and `pim-computer-home` (`/home/node`, the browser's profile and the computer's state, so sign-ins and trigger spools survive a restart). Chromium runs with `--no-sandbox` through `/usr/local/bin/pim-chromium`, because its own sandbox needs user namespaces the container's dropped capabilities deny; the container is the boundary. The Pim image also carries `computer/`, which the Gate serves at `/pim-computer.ts` and, for an installed computer's triggers runtime, at `/triggers-host.ts`, `/triggers-runtime.ts` and `/triggers-adapters/*.ts`.
   - **Directly on the host** (a laptop, or a server where you want a real desktop): `curl -fsSL https://pim.example.com/install.sh | sh -s -- computer pimc_…` installs Node.js if needed and a user service, or in the foreground `PIM_URL=https://pim.example.com PIM_COMPUTER_TOKEN=pimc_… node computer/pim-computer.ts --root ~/pim`.
3. Settings → Computer shows it online. An agent's tools there run at once, without approval: `shell`, `file_delete`, desktop actions and browser form submissions as well as reading, writing and editing files under `/workspace`, opening pages and clicking links. With no computer connected every one of these tools answers "unavailable" immediately, and chat is unaffected.

**What the container does and does not give.** Files, `shell`, the agents' browser (opening pages, clicking, form posts behind an approval, screenshots) and taking the browser over (`/api/browser/live`: pictures of the page, pointer, keys, typed text, address, back, forward, reload) all work in it. The image runs displayd with a virtual display for each chat (Xvnc, openbox and an accessibility bus; pim-computer starts it itself), so each chat's browser has a screen of its own and a person can watch and take over it. The **desktop tools** do not work: `desktop_look`, `desktop_read` and `desktop_act` need Cua's `cua-spacesd` or its per-display driver (`cua-env-driver`), whose binaries are not shipped in this image, so they answer that there are no desktop tools. A display runs without the driver, and starts using it where `/usr/local/bin/cua-env-driver` (or `DISPLAYD_DRIVER_BIN`) exists. A computer that runs `cua-spacesd` without displayd (as a managed computer does) serves one desktop that every chat shares: the tools fall back to it, and a chat's browser takeover to the shared browser. Run the computer on the host (the second way) where you want a real desktop.

**Triggers on the computer.** `poll` and `stream` triggers run on it, as its user, in `/workspace` unless the trigger names a folder. A trigger is enabled only under a grant the person made for exactly its source (`POST /api/triggers/<id>/computer-grant`, which keeps the digest of the source's configuration; changing the command, folder or interval makes the grant `not_current`, and nothing runs until it is made again) and for the computer paired now. The Gate that holds the computer's socket speaks `triggers.v1` for it (`packages/v2-server/src/computer-triggers.ts`, docs/triggers-runtime.md): it reconciles the granted triggers every few seconds when they changed and every 40 s to renew the lease, checks each observation again against the trigger, its grant and its condition (a poll fires on an edge, a stream on each line that matches), and acknowledges it only once the occurrence is in the chat's inbox. What reaches the chat is that the trigger fired and why, never what was observed. Revoking the grant (`DELETE`, which also pauses the trigger) stops the observer at the next reconcile. `process` sources need a managed launcher nothing writes yet, and `file` sources are not observed; they can be granted but are never sent to a computer. The spool is in `~/.pim-computer/triggers` on the computer; a re-paired computer is a new runtime and every grant is then `not_current`.

**What this is not.** A container is not a sandbox for arbitrary agent code: commands in `pim-computer` run in that container on the host's kernel, with outbound network access and whatever you mount into it. Do not mount the Docker socket, `/`, or the stack's directories. Untrusted code that should be contained belongs in the `coding` profile's sandboxes, not here. **Managed computers** (`pim-host`, a computer made for every person) and `hostopsd` host operations are not part of this deployment: `/api/admin/computer-host` reports none paired and refuses to pair one.

The Runner reaches a computer over NATS (`pim.v2.relay.<owner>.rpc`), connecting when an agent first uses a computer tool, so the `runner` role needs `PIM_NATS_URL` (it already has it) and the Gate or `relay` container that holds the computer's socket must be running. `PIM_COMPUTER_SOURCE` overrides where the Gate reads `pim-computer.ts` from (default `/app/computer/pim-computer.ts` in the image).

## Coding workspaces on Compose

The `coding` profile runs what coding threads and harness sign-ins need: `sandbox-manager` (one gVisor container per workspace), `egress-proxy` (a workspace reaches only the hosts it is allowed, over HTTPS), `docker-socket-proxy` (the only service that holds the Docker socket, with no exec) and `workspace-image` (builds `pim-workspace:local` from `workspace-agentd/`, which carries the Claude Code, Codex and Mistral Vibe CLIs). The host needs Docker with gVisor registered as the `runsc` runtime; the manager refuses to start without it, and `docker ps` shows it healthy once it has run a probe container under `runsc`.

1. In `.env` set `PIM_CODING_MANAGER_URL=http://sandbox-manager:8080` (the gate and forge roles then offer workspaces and harness sign-ins; without it a sandbox harness answers 503 and Settings → Coding says so) and, if a coding thread's pi turns use the deployment's model, `PIM_CODING_DEFAULT_MODEL` (`provider/model`; `gateway/<id>` is the OpenAI-compatible gateway of `PIM_AI_GATEWAY_*`). `init-env.sh` makes `PIM_CODING_SIGNING_KEY` and `PROXY_ADMIN_TOKEN`; the signing key must be the same for the gate and the forge role, or the grants the forge issues to a workspace are refused by the gate.
2. `COMPOSE_PROFILES=coding deploy/compose/pim.sh up -d --wait`. An admin then gives a person a coding grant in Settings → Coding access (the same as `GET`, `POST` and `DELETE /api/admin/coding-grants`), which also shows which harnesses this deployment can run; the grant names the repositories the person may use (`acme/*`, `acme/app`, or `*`). A pool exists (`default`, made when the manager is configured). Without a pool, an Amp thread needs none, and an agent that names no harness gets Amp when Amp is set up. A grant only permits; push, pull request and merge still ask the person each time (a thread's own branch is nonetheless pushed when each of its turns ends, as in v1, unless `PIM_CODING_AUTOPUSH=0`). The promotion gives a person who had coding threads in v1 a grant of their own (start, steer, and push, pull request and merge with their yes, on any repository); everyone else is granted by an admin. When a turn ends the work in its checkout is committed as a checkpoint on the thread's branch, so a push, the diff and the bundle that restores an idle thread's next sandbox carry what the agent left uncommitted. A repository's setup script (Settings → the repository, or `.pim/setup.sh` in it) runs after each new checkout and a failure is shown on the thread (`environment_failed`); there are no environment snapshots, so every new sandbox sets up again. A repository is matched the same however it is spelled (`acme/app`, `github.com/acme/app`, a URL): a pattern without a host covers any host, and one with a host covers that host alone.
3. A workspace clones through Pim's git broker at `PIM_PUBLIC_URL`, so that must be an https address the egress proxy can reach. On a machine with no such address (a trial), set `PIM_CODING_BROKER_URL=http://front.pim.internal:8088` and `PIM_CODING_INTERNAL_HOSTS=front.pim.internal:8088` (Caddy's name on the internal network, and a plain-HTTP forward the proxy allows to nothing else), and run Caddy on `:8088` (`PIM_LOCAL=1 deploy/compose/pim.sh` uses `compose.local.yaml` with an https `PIM_PUBLIC_URL`).

Settings → Coding signs a harness in: Claude Code (a URL and a pasted code) and Codex (a URL and a device code) run the CLI's own sign-in in a short-lived workspace and keep what it saves in the person's vault, sealed under the key ring; Amp and Mistral Vibe take an API key, write-only. A sign-in is held in the gate's memory, so a gate restart ends it and deletes its workspace. A person who connects a harness resumes their threads that stopped for want of it. Public repositories are read without a git host; pushing needs the GitHub App or Gitea (`PIM_GITEA_*`), and Gitea's status answers `configured: false` without them.

## Stuck chats and the Runner's guards

A chat whose turn cannot finish ends with an error instead of staying busy. Each guard has a setting on the `runner` role, in milliseconds:

- `PIM_MODEL_STALL_MS` (default 120000): a model stream that sends nothing for this long is cut off; before any output the request goes to the next model of the chat's list, otherwise the chat ends with "The model timed out".
- `PIM_TOOL_TIMEOUT_MS` (default 600000): a tool call that has not returned by then ends with an error result, and a call also ends at once when the person stops the chat, whatever the tool's own work is doing.
- `PIM_RUN_STALL_MS` (default 600000, 0 turns it off): the run watchdog. A run whose tasks and live document have not changed for this long, and that is not parked for an approval, a retry or a sleep, is stopped, and the chat says so.
- `PIM_STOP_GRACE_MS` (default 10000): how long a stop (the web app's stop button, or the watchdog) waits for the run to end. A run that ignores its abort signal then has its partition recycled: the Runner closes the Harness and hands the lease back, and the next claim's recovery settles the aborted calls under a newer epoch, so a stuck run's late writes are fenced.

Provider cooldowns are shared between Runners (`pim_runtime.provider_cooldowns`, migration 0666); a request that fails for load or a refused credential cools the model for 30 seconds or 2 minutes, and a ChatGPT plan's usage limit leaves it until the reset the error gives, or for a backoff that grows with each limit in a row (5 and 15 minutes, 1, 3 and 6 hours). The approval policy defaults to `majordomo` (`PIM_APPROVAL_POLICY`). Every model request is counted against the person's daily limits when it is sent (`pim_app.runner_reserve_model_request`, migration 0699), and each chat's calls are in `pim_app.model_calls` with the chat, the agent and the cache tiers. The approval policy's `auto` (30 seconds unless the person sets another) is applied by the `maintenance` role's timeout sweep; `majordomo` is applied by the Runner's review loop (`approval-review.ts`, migration 0665), which escalates a review that did not finish in 5 minutes.

## Managed computers and host operations

Two programs of the operator's run **on the Docker host, beside the stack and never in it**. Both dial out to the stack's public address with a machine credential of their own, exactly as `pim-computer` does, and neither is a role of the Pim image: the stack never holds the Docker socket, and arbitrary shell never runs in the Gate, the Runner, Live, PostgreSQL, NATS or the object store, nor with their credentials. The Docker socket belongs to the host's user, who runs these.

### The computer host (`pim-host`): a computer for every person

Admin: Settings → Deployment → Computers → pair (`POST /api/admin/computer-host`) shows a `pimh_…` token once; only its digest is kept (a `token_consumers` row of the admin, scope `host:sync`). Forgetting it revokes the token and leaves the computers it made running. The host asks the Gate for work at `POST /api/computer-host/sync` every 5 seconds and reports what it did. A person who looks at Settings → Computer, or asks for one (`POST /api/computer` with `{"managed": true}`, also "Try again" after a failure), gets a request; the host makes a computer for them, named `pim-o-<owner>`, and the computer connects as any paired computer does and is the person's only: a `pimc_` token made when the host takes the request (so no computer token is ever stored in the clear; a request the host took and never reported is given again after 20 minutes, with a new token that replaces the old), valid for that owner's `/api/computer/connect` and nothing else. The person's `shell`, files, browser and desktop tools reach it over the Relay, running without approval as on a computer of their own; the person cannot remove or replace it while they are here; when their account is deleted the host, which sees the machine in its listing, removes it and its files.

```sh
# The host, on the Docker host (a shell as a user in the docker group), with the token from Settings:
PIM_URL=http://localhost:8088 PIM_COMPUTER_URL=http://host.docker.internal:8088 PIM_HOST_TOKEN=pimh_… \
  node computer/pim-host.ts --backend docker --image pim:v2-local
# or as the user's service: curl -fsSL https://pim.example.com/install.sh | sh -s -- host pimh_… --backend docker --image <the Pim image>
```

`--backend docker` keeps each computer as a container of the Pim image (`node /app/computer/pim-computer.ts` as the unprivileged `node` user, a read-only root, no capabilities, `no-new-privileges`, CPU, memory and process limits, a volume `<name>-files` for `/workspace`, on a bridge network `pim-computers` that is none of the stack's networks, the token in docker's environment and on no command line). `--computer-url` is the Pim's address **as a container reaches it**: `https://pim.example.com`, or for the plain-HTTP trial stack an address a container can reach (the trial publishes Caddy on `127.0.0.1` only, which a container cannot reach: publish it on the Docker host's address). Without `--backend docker` the host is v1's: Cua desktops (VMs where there is KVM, or Cua containers), which needs Cua on the host. **A container is not a sandbox for arbitrary agent code**: what an agent runs there runs on the host's kernel with network access; hardening limits what it can do to the host, not what it can reach.

### Host operations (`hostopsd`)

The admin's majordomo and Pimbot (and only they: another agent, a member's agent, a delegated task, the app, the API and an MCP client are refused, and every refusal is kept) can look after the machine with the tools `hostops_stats`, `_logs`, `_restart`, `_set_slot_limit`, `_update`, `_deploy`, `_rollback` and `_exec`, and read with `hostops_status`, `_audit` and `_op`; they are offered to the admin's agents only. **Every operation that changes or runs something on the host asks the admin first; reading the host's stats (`hostops_stats`) and a service's logs (`hostops_logs`) does not, since only the admin's own agents can ask, the daemon takes secrets out of what it returns, and the request is audited** (an approval filed in the app with the exact operation and arguments, never covered by a standing approval, one approval for one operation; v1 asked only for `exec`), and the service checks the application's own record of the approval, not what a tool says. The daemon dials out with a credential of its own (`pimhostops_…`, digest only), long-polls `/api/hostops/agent/poll`, runs one operation from a fixed list that it validates again, and posts `/api/hostops/agent/result`. Every request, refused or not, and every state change is in the audit log (Settings → Deployment, and `hostops_audit`; 10,000 rows, secrets taken out, a command's output kept to its last 3,000 characters). Operations the host never takes expire after 10 minutes; one it never reports fails at its deadline.

```sh
# The daemon, on the Docker host, as an unprivileged user in the docker group that has a checkout of the repository:
HOSTOPSD_STACK=compose HOSTOPS_URL=https://pim.example.com HOSTOPS_TOKEN=pimhostops_… \
  PIM_CHECKOUT=/srv/pim PIM_COMPOSE_DIR=/srv/pim/deploy/compose node sandbox-manager/hostopsd/hostopsd.js
```

Get its credential from Settings → Deployment → Host operations → Issue credential, or let the host enroll itself: set `PIM_HOSTOPS_ENROLL_TOKEN` (else `PIM_CODING_MANAGER_TOKEN`, as v1) in `.env`, then `POST /api/hostops/agent/enroll` with it as the bearer returns a credential (rotating the old; a revoke by the admin sticks until they issue another). `HOSTOPSD_STACK=compose` makes the operations about the Compose stack: `restart` and `logs` take one of its services (`caddy postgres pgbouncer nats seaweedfs gate live runner forge maintenance canvas relay pim-computer sandbox-manager hostopsd`) through `deploy/compose/pim.sh`; `stats` reads load, memory, disk, Docker and the stack's containers; `update [TAG]` runs `deploy/compose/pim.sh update` (pull the channel's published image, back up, pin it in `.env` by digest, `up -d --wait`, and go back to the previous image when that fails) and reports the one line it prints, `{"event":"pim.update","from":…,"to":…,"result":"updated|unchanged|rolled_back"}`, as its result; `deploy <ref>`, for a host that builds from a git checkout, fetches, checks it is a fast-forward (a commit hash goes anywhere), builds `deploy/Dockerfile.v2` as the `PIM_IMAGE` the stack's `.env` names, and runs `pim.sh up -d --wait` (migrations first), going back to the previous commit on its own when the build or the health wait fails (`rolled_back`); `rollback <commit>` does the same without the safety net. **Database migrations are not undone by a rollback.** `exec` runs one `/bin/sh -c` command as the daemon's user with only `PATH`, `HOME` and `LANG`, with a timeout (at most 300 seconds) and output cut to the last 64 KiB, with the daemon's own credentials and every value in the stack's `.env` taken out of what it reports. The daemon's user is in the docker group, which is root on the host: approve a command only when you would type it as root yourself. `set_slot_limit` needs the `coding` profile's sandbox manager.

### Versions and updates

The image knows its own version and commit: `deploy/Dockerfile.v2` takes the build arguments `PIM_VERSION` and `PIM_REVISION` (the publishing workflow passes them; a local build is `dev` at an unknown revision, and a `deploy` through hostopsd passes the commit it built), keeps them as the image's `org.opencontainers.image.version` and `.revision` labels and as environment variables, and Settings → Deployment → Version shows them to the admin. The instance follows the channel `PIM_CHANNEL` in `.env` (`stable` by default; `edge`, or a tag such as `2.1`). The maintenance role reads that tag's labels from GHCR's anonymous registry API (`ghcr.io/ajac-zero/pim`, or `PIM_UPDATE_IMAGE`) at most every six hours (three after a failure) and keeps the answer in `instance_settings`; the screen compares it with what runs, so for an `X.Y.Z` version it offers a higher one and for any other (an edge image) a different commit, with the release page or the commit as its notes link. `PIM_UPDATE_CHECK=off` makes no request, and a local build is never offered an update. The admin sees **Update available** with an **Update now** button when a host daemon is connected, which asks for confirmation and queues one `update` as that admin's approval for that call (the audit log keeps it as `admin`); one deploy, rollback or update runs at a time, and the screen follows it until it ends. Without a daemon it shows `./deploy/compose/pim.sh update` to run on the host instead. The majordomo can do the same with `hostops_update`, which asks like every other operation.

## Kubernetes

Kustomize: `kustomize build deploy/k8s | kubectl apply -f -` (needs CloudNativePG, an ingress controller and cert-manager). `overlays/openbao` takes the Secrets from OpenBao or Vault through External Secrets; `overlays/monitoring` adds the PodMonitor, the `PrometheusRule` and the Grafana dashboard (build it with `--load-restrictor LoadRestrictionsNone`, because the dashboard JSON lives in `deploy/observability/`).

- One Deployment per role, each with a PodDisruptionBudget, and an HPA for all but `maintenance`. The Runner has `terminationGracePeriodSeconds: 150`, a `preStop` that calls `/drain`, and an HPA that scales down one pod per two minutes after a ten-minute quiet window, because every Runner that leaves is a lease handoff.
- PostgreSQL is a CloudNativePG `Cluster` of three, with the same roles and logins declared in `managed.roles` (the NOLOGIN roles first, then each login with `inRoles`; the order CloudNativePG reconciles them in was not observed), with Barman object-store base backups, WAL archiving and a 30-day retention for point-in-time recovery, and a PgBouncer `Pooler` in transaction mode. CloudNativePG uses Barman for this, not pgBackRest.
- **Durability against availability is a choice and the manifest states it** (`deploy/k8s/base/postgres.yaml`). It sets `synchronous: { method: any, number: 1, dataDurability: required }`: a commit waits for one standby, so a primary failure loses no committed transaction, and writes stop if no standby can confirm. `dataDurability: preferred` keeps the cluster writable without a standby and can lose the commits only the old primary had. With no `synchronous` block, replication is asynchronous and a primary failure can lose the last commits. Backups and WAL archiving protect against losing the whole cluster, with a recovery point as old as the archive lag. Nothing here claims that failover is lossless on asynchronous replication.
- NATS Core runs as a three-node cluster without JetStream: it carries commit events from Runners to Live and is never a source of truth. A missed message is recovered from PostgreSQL by cursor.
- Untrusted sandbox compute lives in the `pim-sandboxes` namespace, on a node pool with the taint `pim.dev/untrusted=true`, under `runtimeClassName: gvisor` (Kata or an agent-sandbox class works the same way). The control-plane namespace denies all ingress by default and admits only labelled peers: PostgreSQL, the Pooler and NATS accept control-tier pods and nothing else. The sandbox namespace denies all traffic by default and allows DNS, the Gate's port 8080 (where the git broker and the model gateway are) and the public internet except private, link-local and cluster ranges. Both ends enforce it; a test checks that no sandbox rule names PostgreSQL, NATS or a Runner.
- Secrets: nothing in `base/` is a Secret. Envelope keys are mounted as files, never environment variables.

## Cutover from the Cloudflare deployment

The fence procedure is `docs/architecture/inventory/C-cutover-fence-entrypoints.md` §10 (read in full). This is how the tools map onto its ten steps. Nothing here pushes, deploys or touches a live host: those steps are the operator's, and each tool runs against what it is pointed at.

| Fence step | Tool or action |
|---|---|
| 1-4 Inventory, readiness of destructive paths, close registration, suspend accounts | Operator, with existing controls. The importer treats accounts suspended with the reason `cutover fence` as active again; the admin is never suspended. |
| 5 Fence ingress with an invalid `PIM_RUNTIME` | Operator, existing control. |
| 6 Stop the alarms | Deploy the fence Worker (option B): its configuration is `packages/v2-ops/src/fence-worker/wrangler.jsonc`, a file kept by hand with the legacy Worker's names, bindings, classes and migrations (as they were at the git tag `v1-final`), which `test/fence.test.ts` checks for consistency; it must match what is deployed, so compare it with the production `wrangler.jsonc` before deploying. Deploy it from `packages/v2-ops` (`pnpm exec wrangler deploy -c src/fence-worker/wrangler.jsonc`). Deploy with `--durable-objects-code-update-mode immediate`. |
| 7 Verify old code is gone | `GET /fence/v1/do/<binding>/<name>/probe` on the Directory, Gallery, a sample of Pim and CodingThread ids, and the WorkspaceCatalog; each must answer from the shell. |
| 8 Stop what is outside the Worker | `POST /fence/v1/do/WorkspaceContainer/<id>/destroy` (off unless `FENCE_ALLOW_CONTAINER_DESTROY=true`); the rest is the operator's. |
| 9 Snapshot and compare | `node scripts/v2-migrate/run.mjs export`, then compare `cf_agents_jobs` row counts across two exports more than two minutes apart. |
| 10 Hold the fence | Keep the fence Worker deployed until activation. |

**The fence Worker** exports the nine legacy classes under their exact names (`Pim`, `Auth`, `Directory`, `Gallery`, `CodingSchedulerDO`, `CodingThreadDO`, `HostOps`, `WorkspaceContainer`, `WorkspaceCatalog`) and `ContainerEgress`; copies the bindings, `migrations` and `containers` blocks without a `deleted_classes` or `exports` entry; never runs `agents` `Lifecycle` (a job with no callback is dropped as done by that scheduler); consumes every alarm without reading or writing storage or re-arming it; answers everything else `503 Maintenance`; and, behind `FENCE_EXPORT_TOKEN` (32 characters or more, compared in constant time), serves read-only dumps of every table (paged), key-value entry and alarm of any object, the R2 buckets, and `OAUTH_KV`. An export route without the token looks like any other path.

**Export, then import and verify** (`node scripts/v2-migrate/run.mjs <command>`):

```sh
export FENCE_EXPORT_TOKEN=... APP_CREDENTIALS_KEY=... PIM_KEY_BACKUP_PASSPHRASE=...
run.mjs export --url https://pim.example.test --out /secure/snapshot --cutover-at 2026-11-20T03:00:00Z
export PIM_KEK_CURRENT=k1 PIM_KEK_k1=$(openssl rand -base64 32)
run.mjs import --snapshot /secure/snapshot --database-url postgres://pim_migrator:... --objects-dir /var/pim-objects \
        --cutover-id cut-2026-11-20 --report /secure/report --legacy-rp-id pim.example.test --new-rp-id pim.example.test
run.mjs rehearse --out /tmp/rehearsal        # the same pipeline on a synthetic snapshot and a throwaway PostgreSQL
```

What the importer does, and what it refuses to:

- Checks every file of the snapshot against the manifest's SHA-256 before it reads any.
- Splits each space's single pi history into **conversation-family partitions**: the home partition holds conversation 1 and what attaches to it; every fork closure, and each plain chat, continuation, delegated task, trigger chat and group-chat seat, is a family of its own. Numeric conversation, entry, task and document ids are never renumbered; each tenant keeps one id sequence continuing above its highest id; each partition continues its commit sequence above its own highest.
- Keeps UUID chat ids mapped to their numeric conversations; keeps explicit settings and overrides row for row (nothing `unset` becomes an override); keeps passkeys, identities, token hashes and recovery codes exactly.
- Moves every secret under `EnvelopeCrypto` (AES-256-GCM, per-value data key wrapped by a named key-encryption key, tenant and name bound as authenticated data) and **keeps the legacy ciphertext beside it**: native-app credentials opened with `APP_CREDENTIALS_KEY`, plaintext provider and compute credentials, the Directory's `cookie_key` and `salt`, push secrets, the MCP OAuth key-value tokens. `legacy_rows` holds a reference, never the secret. The legacy keys themselves go into a passphrase-sealed key backup written beside the snapshot by `export`; keep it away from this host. Coding-vault blobs are kept verbatim: they are sealed under a key derived from `cookie_key`, which is why `cookie_key` is preserved.
- **Quiesces** (`planQuiescence`): every non-terminal `pi.tool` task and every pending, or decided-without-a-result, approval becomes a `needs_reconciliation` operation and a held task, with the arguments reduced to a digest; queued trigger firings likewise; a CLI coding turn cut off by the fence likewise. Schedule occurrences at or before the cutover are recorded as missed and never fired, and the first cron, interval or once occurrence strictly after the cutover is armed, so the first Runner boot has no catch-up to do (cron in a time zone other than UTC is marked `recompute`). A remote coding session (`agent-hosted`) is adopted by its remote id with its start recorded as `succeeded` under the key the client deduplicates on, so it is never started again.
- Refuses a second cutover in the same database, a changed snapshot under the same cutover id, and an import after activation; re-running the same import changes nothing.
- Warns when the WebAuthn rp id would change: passkeys are bound to the hostname.

**The auditor** reads the snapshot and the database independently and compares them: row counts of every source table (typed or kept), record-level hashes of entries, tasks and document revisions, passkey ids and public keys byte for byte, used recovery codes, partition integrity (no entry, fork or task across partitions, every fork point an entry of its parent, id and commit sequences above every id), the visible transcript of **every conversation** resolved through fork ancestry on both sides, explicit settings key by key, no plaintext secret left in `legacy_rows`, every object's SHA-256 and size re-read from the object store, and the quiescence invariants. It writes `cutover-report.json` and `cutover-report.md`; do not start a Runner unless the verdict is PASS.

**Before activation** the new system has not served anyone: rollback is to redeploy the previous Worker version, set `PIM_RUNTIME` and `PIM_REGISTRATION` back, unsuspend each suspended account, and expect alarms to resume from stored rows (the Scheduler, Directory and HostOps recompute their alarms on their next call; **this was not observed**, see the audit's open question 6). Throw the new database and bucket away. **After activation** there is no automatic rollback: writes in the new system have no way back into Durable Objects. The choices are to fix forward, or to restore the pre-activation backup of the new system (below) and accept the loss of everything after it, and to re-run the fence on the old system only if its data is still the wanted one.

## Rehearsal on a real v1 Worker, and the live cutover runbook

`node scripts/v2-migrate/rehearse-local.mjs all --database-url postgres://<superuser>@<host>/postgres` rehearses the whole cutover on one machine, against a **real v1 Worker** (the preview, `wrangler dev`) instead of the synthetic snapshot. v1 is no longer in this branch, so it needs a checkout of the git tag `v1-final` with its dependencies installed and its web app built, named by `PIM_V1_CHECKOUT` (`git worktree add ../pim-v1 v1-final && (cd ../pim-v1 && pnpm install --frozen-lockfile && pnpm build)`); the script reads the Worker's `wrangler.jsonc`, `wrangler.preview.jsonc`, `preview/worker.ts` and `web/dist` from there, and fails at once, saying so, without it. It also needs PostgreSQL (`packages/v2-runtime/scripts/ensure-postgres.sh`), `PIM_NATS_BIN` (`packages/v2-server/scripts/ensure-nats.sh`) and this checkout's `node_modules`; it touches no Cloudflare account, host or cloud service. Phases (run any subset by name; state is kept in `--work`, default `/tmp/pim-rehearsal`):

| Phase | What it does |
|---|---|
| `v1` | Starts the v1 preview on fresh state and fills it through its real API (`populate-v1.mjs`): two accounts (one admin) with a passkey whose private key the rehearsal keeps, API tokens, settings, a profile, chats (a fork, a chat cut off mid-tool behind a pending approval), agents with instructions, a skill with a file and two versions (written through its approval), memories, a goal with steps, scheduled tasks, a note, an app with two versions, an uploaded image, a custom model provider with an API key, a circle. It then takes a digest of what v1 serves. |
| `fence` | Stops v1 and runs the fence Worker (`packages/v2-ops/src/fence-worker`, its classes, bindings and migrations taken from the production `wrangler.jsonc`) on the **same** Durable Object, R2 and KV state; ordinary paths answer 503 and the export routes need the token. |
| `export` | `run.mjs export` through the fence Worker. |
| `import` | Creates the database, runs every SQL band, `run.mjs import` with its audit, then `promote` with the deployment's keys (`PIM_KEK_*`), the importer's object directory (`PIM_LEGACY_OBJECTS_DIR`) and the S3 settings, so credentials and files are carried over. |
| `serve` | NATS, an S3 server, and the Gate, Live and Runner as separate processes on `NOBYPASSRLS` role logins. Skip it with `--public-url` to point `verify` at another stack, such as Compose (`--ingress-secret` if its proxy needs one). |
| `verify` | `verify-v2.mjs`: signs in with the old passkey and the old API tokens, then checks through the stack's API that every item is present and belongs to the right person (chat histories and fork ancestry, agents and instructions, skills with files and versions, memories, goals, triggers aimed at the new chat ids and not caught up, note, app versions, image bytes, provider with a key that is never returned, circle, profile), that a new message in an imported chat (including the one cut off mid-tool) is answered by a Runner using the imported provider and its imported key, that the cut-off tool call did not run again, and, with the database URL, the explicit settings and that no credential is in clear anywhere. Exit status 0 only if all pass. |
| `rollback` | Stops the new stack and the fence Worker, starts v1 again on the same state and compares the digest, then waits to see whether the schedule that fell due while fenced fires. Nothing is deleted; the new database is left for the operator to discard. |

Its output counts the credentials carried and lists any that did not open.

**A passkey on a changed hostname** (rehearsed: the stack at `http://127.0.0.1:8088`, the v1 passkey made for `localhost`; `verify-v2.mjs` runs this branch whenever the stack's host is not the passkey's). A passkey is bound to the host it was made for. The new stack asks for its own host's passkeys, a browser does not offer the old one, and an assertion signed for the old host is refused. Nothing is lost: accounts, chats, tokens and recovery codes all come across, and **API tokens keep working**. What the person does: on the new address, open the sign-in page, choose **Lost your passkey?**, enter the username and one of the recovery codes saved when the account was made (the app shows them once), and confirm the new passkey; the code is spent (each works once), and from then on the new passkey signs in. Someone with no recovery code left uses a sign-in provider already linked to the account, or the operator issues an admin recovery claim (`issueClaim("admin_recovery")`) for an admin. So tell people before the cutover to find their recovery codes (Settings → Account shows how many are left; **make new ones while still on the old Pim if none are left**), or keep the old hostname. The import's audit warns `The WebAuthn rp id changes`; `PIM_LEGACY_RP_ID` keeps the old marks on the promoted passkey rows (the promote step takes it from `compose-import.sh`).

**Why the first verify run once failed with `Connection error` (found and fixed).** The Runner builds an owner's model catalog, with each provider's address and key, when it opens a chat's partition, and a partition stays resident while chats in it are active. The harness changed the imported provider's address to the Docker gateway while a partition was still resident with the old one, so the first message called the old address inside the container and no connection ever reached the stand-in; once the partition was released (after about 30 s idle) the next run passed. Reproduced on demand (send a message under the old address, change it, verify at once: root chat fails with no connection seen). The catalog now follows provider changes: it is rebuilt whenever a message sets the chat's model, and the models the harness holds read through it (`agent-host.ts`, regression test `agent-host-catalog.test.ts`). With the populate's `--provider-host` no row is edited by hand any more.

### Live cutover runbook

1. **Destination prerequisites.** The Compose stack (or Kubernetes) is up and healthy with an **empty** database, its migrator done, a bucket, NATS, `PIM_KEK_CURRENT`/`PIM_KEK_<id>` keys set (a backup of the key ring kept apart from the database), and `PIM_PUBLIC_URL` on the **same hostname** as the old Pim so passkeys keep working (on another hostname every person must use a recovery code once: see "A passkey on a changed hostname"). Set the OAuth clients of the native connectors that were connected (`GOOGLE_GMAIL_*`, `GOOGLE_DRIVE_*`, `SPOTIFY_*`) before promoting, so their tokens can be renewed. Choose `PIM_DEFAULT_MODEL` (`provider/model`) and make sure that provider exists on the new stack: every imported chat that names a model the new deployment lacks is moved to it. Run the full rehearsal first (`rehearse-local.mjs all`, then `verify-v2.mjs` against the Compose stack on a copy).
2. **Announce downtime, then fence** (the table above, steps 1-5): close registration, suspend accounts with the reason `cutover fence`, set an invalid `PIM_RUNTIME`; deploy the fence Worker (`wrangler deploy -c src/fence-worker/wrangler.jsonc --durable-objects-code-update-mode immediate`, from `packages/v2-ops`); probe every class; stop containers.
3. **Back up the old side**: export (below) is the backup; also keep `APP_CREDENTIALS_KEY`, `cookie_key` and every Worker secret, sealed with `PIM_KEY_BACKUP_PASSPHRASE` as `run.mjs export` writes them.
4. **Export** twice more than two minutes apart and compare `cf_agents_jobs` counts (nothing may be moving), then `FENCE_EXPORT_TOKEN=... run.mjs export --url <fence> --out <dir> --cutover-at <fence verified time>`.
5. **Import and audit**: `run.mjs import ... --legacy-rp-id <host> --new-rp-id <host>`; the verdict must be PASS and no warning about a changed rp id. Read `cutover-report.md`.
6. **Promote**: `PIM_DATABASE_URL=<schema owner> PIM_RP_ID=<host> PIM_CUTOVER_AT=<epoch ms> PIM_DEFAULT_MODEL=... PIM_LEGACY_OBJECTS_DIR=<importer objects dir> PIM_S3_*=... PIM_KEK_*=... node --import tsx packages/v2-server/src/main.ts promote`. Read its `skipped` list: it names what was not promoted and why. On Compose, steps 5 and 6 are one command, `scripts/v2-migrate/compose-import.sh <dir with snapshot/> <old hostname> [provider/model]`, which keeps the app stopped until both are done.
7. **Verify on the stack before anyone is let in**: `verify-v2.mjs --public-url <stack> --expect <expectations> ...` needs a populated rehearsal's expectations file, so for the real data check by hand: the admin signs in with a passkey, chats and forks read, agents, skills, memories, goals, triggers (time triggers count from the activation; computer-bound ones are paused), notes, apps, the provider answers.
8. **Thread adoption and reconciliation**: remote Amp threads are adopted by their remote id and never started again; every pending approval and cut-off tool call is a `needs_reconciliation` operation in `pim_ops.external_operations`: decide each by hand before enabling anything that could repeat it.
9. **Activate**: start the Runners, lift the maintenance page, unsuspend nobody who was not suspended by the fence. From here there is **no** automatic rollback.
10. **Rollback before activation**: stop the new stack; deploy the previous Worker version; restore `PIM_RUNTIME` and `PIM_REGISTRATION`; unsuspend the fenced accounts. Deleting the new database and bucket is the operator's later choice. The local rehearsal shows the old Worker, unfenced, serving the same data; the same on Cloudflare is not yet observed.

**Run on Cloudflare (2026-11-17, `pim.ajac-zero.com` to a Compose stack at `agent.ajac-zero.com`).** One space: 290,437 Durable Object rows (60,566 pi entries, 48,833 tasks), 298 coding threads, 281 R2 objects; the snapshot was 730 MB. The fence Worker replaced the `pim` Worker (previous version `449dc034-67c2-4634-9aad-9113c6bcf6ce`, the rollback target) with its KV, R2 and Durable Object bindings inherited and the custom domain kept. The real export found what the rehearsals could not, each fixed: a page of 1,000 rows counted every table first and the fence Worker was cut off (pages no longer count, and a failed page is asked for again smaller); one space's dump is more than a JavaScript string holds (large tables are written as `dos-rows/` chunk files, one row per line); hundreds of coding threads took over an hour one at a time (eight at a time now) and a dropped connection ended the export (reads are retried); records holding U+0000, which jsonb refuses (stored as U+FFFD, and the audit compares the same way); trigger subscription secrets and coding workspace records were left in clear (sealed now; transcript-like rows, an approval's arguments and coding events, are kept as written, as chat transcripts are); chat links whose chat row v1 had deleted (not carried as chats, and the audit no longer expects them); the person's own Anthropic Messages endpoint was run as an OpenAI-compatible one (its `api` is kept and honoured); and the person's chosen default, fallback and utility models were not promoted. The audit passed 8,490 of 8,490 checks; a new chat answered through the person's own gateway and through the ChatGPT plan.

## Backup and restore

`scripts/v2-backup/run.mjs backup|restore|post-restore`. The tested engine is a **physical base backup through the low-level API** (`pg_backup_start`, copy, `pg_backup_stop`) with archived WAL, so a restore can stop at the end of the backup or at any chosen instant after it, plus every object with its SHA-256 and the key material's names and fingerprints. For Compose, `scripts/v2-backup/compose-backup.sh <dir>` takes a logical `pg_dump` (with owners and grants) and a copy of the bucket with SHA-256 sums, and `scripts/v2-backup/compose-restore.sh <dir> [restore-id]` stops the app, restores both, migrates, runs `migrator post-restore` (the safety pass below) and starts the app again; `scripts/v2-compose/smoke.sh` runs both on every CI push and checks that a message written after the backup is gone, the image is back and chat still answers. Keep `deploy/compose/.env` (it holds the key ring) in its own backup. On Kubernetes, CloudNativePG's Barman backups and WAL archive are the equivalent and `ScheduledBackup` runs them daily.

**The restore hazard is real and the safety pass exists for it.** A restored database is older than the world. Operations it shows as pending may already have run after the backup; operations in flight may have finished or half-finished. Before any Runner starts, `post-restore` moves every `pending` and `in_flight` external operation, and every effect named in a journal of effects known to the outside world (`--known-effects`), to `needs_reconciliation`; holds unfinished tool tasks; turns every schedule whose time has passed into `recompute` with the missed time recorded; and marks the restore `reconciled`. Runners refuse to start until then. The database alone cannot know what happened after the backup, so keep an effects journal outside it (provider-side logs, or the failed database's last rows) and pass it in. The pass is idempotent.

Restore order: stop every Runner; `restore`; start PostgreSQL; `post-restore`; check; start Runners. The key ring must come from its own backup: a database restored without it cannot open any sealed secret.

## Open items

1. **Landing tables.** They live in `pim_ops` until the application and runtime workstreams define their own in `pim_app` and `pim_runtime`; then the importer's targets move and RLS policies (`owner_id = pim_current_owner_id()`) apply. The external-operation ledger and the Runner's obligations in [The role contract](#the-role-contract) are this workstream's proposal for the runtime workstream to accept.
2. **Legacy table shapes.** The exporter dumps every table whatever its name, so it does not depend on them; the importer's typed promotion (accounts, Auth tables, pi tables, chats) and the quiescence rules read `pim_approvals`, `pim_trigger_*`, `cf_agents_jobs`, `coding_thread` and the pi tables by the names in the audited commit. The first rehearsal on a real export (above) corrected several of them; one on the production deployment, before the cutover, should still come first.
3. **S3.** The application, the promotion and the Compose backup scripts use SeaweedFS over S3; the physical-backup tool (`scripts/v2-backup/run.mjs`) and the importer's object directory still use a directory-backed store.
4. **Rollback after a fence.** Observed locally (a schedule that fell due during the fence fired after the unfence); not observed on Cloudflare (audit open question 6).
5. **Coding-thread pi stores** are kept row for row, not split: each has its own id space, so they cannot share the tenant's id sequence.
