# @pim/v2-app

Pim's portable application backend: Node.js, PostgreSQL (schema `pim_app`) and any S3-compatible object store. No Cloudflare runtime. It implements the interfaces in `@pim/v2-contracts`: `Authorizer`, `EnvelopeCrypto`, `ObjectStore`, `CommandSubmission`, `ExternalOperationRecord`, `CodingGrant` and `StandingApproval`.

- `migrations/0200–0206` (the application band; `0001_foundation.sql` in `@pim/v2-contracts` comes first, and `src/migrate.ts` applies both into `public.pim_schema_migrations`): accounts, credentials, sessions and tokens, grants, conversations and the command ledger, the agent domain, sharing, objects, Canvas and Relay. Every tenant table is `FORCE ROW LEVEL SECURITY`, keyed on `public.pim_current_owner_id()`, the transaction-local `pim.owner_id`; secret lookups (a token hash, a credential id) set `pim.lookup` for the one row they name. `src/db.ts` is the only way in, and it sets both per transaction, so pooled and PgBouncer-fronted connections never carry a tenant over. The application logs in as a member of `pim_gate` and must be neither superuser nor `BYPASSRLS`; the migration owner is a different role.
- `Authorizer` (`src/authz.ts`): one decision point for HTTP, WebSockets, MCP and agent tools. A principal passes only if its owner is alive (403 suspended, 410 deleting or deleted), its token scope allows the action, the owner's role and grants allow it, and, for push and merge, a StandingApproval record covers it (otherwise the answer is `approval_required`). A delegated principal is decided on its origin, and every owner in the chain must be alive.
- `KeyringCrypto` (`src/crypto.ts`): a data key per value wrapped under a rotatable key (AES-256-GCM, context bound in), rotation, and `importLegacyKey` for what the Cloudflare build sealed with `APP_CREDENTIALS_KEY` and `cookie_key`.
- `Gate` (`src/gate.ts`): stateless HTTP. A chat command is accepted into `accepted_commands` and `command_inbox` in one short transaction and answered at once; the Runner claims `CommandSubmission`s from the inbox later. `fork`, `unarchive` and `delegate` change metadata only; the Runner creates the pi conversation of a fork when its first command arrives. `src/main.ts` starts the Gate from `loadProcessConfig`.
- Sign-in (`src/signin.ts`, `webauthn.ts`, `oauth.ts`, `mcp.ts`, `routes/auth.ts`): passkeys (EdDSA, ES256, RS256 SPKI; relying party id is the hostname; user handle is base64url of the owner id), setup, recovery and device-link codes, Google, GitHub and OpenID Connect sign-in with `(issuer, subject)` unique across the instance, and Pim as the OAuth 2.1 server for `/mcp` (PKCE S256, one-hour access and thirty-day refresh tokens in `token_consumers`, guests refused). Sessions are server-side rows: `__Host-pim-session` on https, `pim_session` only on plain http, and `?token=` only on a WebSocket upgrade, never on published or app paths.
- Domain services and `routes/domain.ts`: agents and skills, providers (keys sealed), connectors (tool discovery is default-off; webhooks verified by HMAC), usage costs, triggers (over `@pim/triggers`' spec and time engine), apps, circles, shared chats, people, bots, visits, templates, and account export and deletion.
- `Objects`, `Canvas`, `Relay`: S3 objects with ranges, Yjs notes with fenced leases, and the computer registry. A missing computer is a `CapabilityUnavailableError` for the tools that need one and nothing else. `src/sockets.ts` upgrades `/api/computer/connect` (a `pimc_` computer, protocol 1 or 2), `/api/computer/screen`, `/api/browser/live`, `/api/notes/live` (y-websocket sync on Canvas) and apps' WebSockets; `routes/hosted.ts` relays `/hosted/<owner>/<id>/<token>/…` and `<label>.<apps origin>` to a backend on the computer. The Relay holds a computer's socket in the process it connected to, so it runs where the Gate does (`all-in-one`) until a cross-process route exists.

Tests start a real PostgreSQL (`embedded-postgres`) and an S3-protocol server (`s3rver`): `pnpm --filter @pim/v2-app test`.
